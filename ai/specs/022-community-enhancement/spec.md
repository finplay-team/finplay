# Spec: 커뮤니티 고도화 (종목 기준 분류 · 대댓글 · 사진 첨부)

> PRD 근거: COM-004, COM-005, COM-006 (신설, 2차 MVP). 이 ID들의 상세는 PRD 본문에 별도 절을 두지 않고 이 spec이 정본이다 (`ai/prd.md` 4절 머리말의 EDU-PRACTICE-*·FEED-* 패턴을 따름).
> 선행: `008-community` (게시물 CRUD·평면 댓글·소유권, COM-001~003). `002-auth-account`.
> plan.md·tasks.md는 이슈별로 착수 직전 작성한다. 이슈 3개로 분리 진행 — 이슈 1개 = 그룹 1개(COM-004/005/006), spec은 공유한다 (2026-08-06 확정, `docs/team-conventions.md`의 "이슈 하나 = spec 하나" 원칙에 대한 예외).
> 관련 이슈: #246 (COM-004 종목 기준 분류), #247 (COM-005 대댓글), #248 (COM-006 사진 첨부).

## 개요

`008-community`가 제공한 최소 커뮤니티(텍스트 게시물, 평면 댓글, 소유권 기반 권한)에 세 가지를 더한다: 게시물에 종목을 태그해 종목 기준으로 필터링하는 기능(COM-004), 댓글에 1단계 대댓글을 추가하는 기능(COM-005), 게시물에 이미지를 첨부하는 기능(COM-006). 세 그룹은 서로 독립적으로 구현 가능하며 각각 별도 이슈로 진행한다.

## 사용자 시나리오

- 사용자는 게시물을 작성할 때 특정 종목(주식 또는 코인)을 선택적으로 태그한다.
- 사용자는 커뮤니티 목록을 특정 종목으로 필터링해 그 종목 이야기만 모아 본다.
- 사용자는 댓글에 답글을 달아 대댓글을 남긴다.
- 사용자는 대댓글에는 다시 답글을 달 수 없다 (1단계 제한).
- 사용자는 게시물 작성 시 이미지를 첨부한다.
- 사용자가 남의 대댓글·첨부 이미지를 지우려 하면 거부당한다 (COM-003 소유권 규칙 그대로 적용).
- (COM-005, 2026-08-11 Issue #277 추가) 이 소유권 규칙은 "남의 댓글·대댓글을 직접 지우려는 시도"에만 적용된다. 자신의 부모 댓글을 삭제했을 때 그 밑에 달린 남의 대댓글이 표시상 영향받는 것은 이 규칙이 막는 대상이 아니다 — 대댓글 자체는 삭제되지 않고 내용 그대로 보존되며, 부모만 tombstone 처리(표시 변경)되어 맥락이 사라질 뿐이다. 즉 tombstone은 "삭제"가 아니라 부모 자신의 삭제 행위가 낳는 표시 변경이라 자식 소유자의 삭제 권한을 침해하지 않는다 (상세 설계는 `plan.md` "COM-005 부모 댓글 tombstone 전환" 절, Decision Gate 참고).

## 요구사항

### COM-004 종목 기준 분류

- [ ] 게시물 작성·수정 시 종목(MKT-001 범위의 주식 16종·코인 12종)을 선택적으로 하나 태그할 수 있다. 태그는 nullable — 미태그 게시물도 계속 허용한다.
- [ ] 태그하는 종목은 존재하는 활성 심볼이어야 한다. 존재하지 않거나 비활성인 심볼을 태그하면 400 `VALIDATION_ERROR`.
- [ ] 게시물 목록 조회에 `instrumentId` 쿼리 파라미터를 추가한다. 지정하면 그 종목이 태그된 게시물만, 지정하지 않으면 COM-001과 동일하게 전체를 최신순 페이지네이션으로 반환한다.
- [ ] 게시물 단건·목록 응답에 태그된 종목의 식별자·심볼·표시명을 포함한다. 태그가 없으면 해당 필드는 null.
- [ ] 게시물당 태그 가능한 종목은 최대 1개다 (다중 태그는 이 그룹에서 제외).

### COM-005 대댓글

- [ ] 로그인 사용자는 기존 댓글(부모)에 대댓글(자식)을 작성한다.
- [ ] 대댓글에는 다시 답글을 달 수 없다 — depth는 부모(0단계)·자식(1단계) 2단계로 고정한다. 자식 댓글에 답글 요청이 오면 400 `VALIDATION_ERROR`.
  - 근거: 무한 depth는 조회·정렬 복잡도를 키우고 커뮤니티 첫 고도화 단계의 실사용 패턴(짧은 대화 스레드)에 비해 과설계다. 1단계 제한으로 트리 재귀 없이 "부모 댓글 + 그에 속한 자식 목록"만으로 조회를 끝낼 수 있다.
- [ ] 게시물 상세의 댓글 목록 조회는 부모 댓글을 오래된 순으로 나열하고, 각 부모 댓글 밑에 그 자식 대댓글을 오래된 순으로 함께 포함한다 (COM-002의 정렬 규칙을 부모·자식 각각에 적용).
- [ ] 본인 댓글·대댓글만 삭제할 수 있다 (COM-003 그대로 적용). 자식이 있는 부모 댓글의 삭제 처리 방식(함께 삭제 vs 내용만 블라인드 처리)은 plan에서 확정한다.

### COM-006 사진 첨부

- [ ] 게시물 작성 시 이미지 파일을 1장 첨부할 수 있다. 첨부는 선택 사항 — 미첨부 게시물도 계속 허용한다.
- [ ] 게시물당 첨부 가능한 이미지는 최대 1장이다 (여러 장 첨부는 이 그룹에서 제외).
- [ ] 허용 형식·최대 파일 크기는 plan에서 확정한다 (예: JPEG·PNG·WEBP, 5MB 이하 후보).
- [ ] 허용 형식·크기를 벗어나면 400 `VALIDATION_ERROR`.
- [ ] 게시물 단건·목록 응답에 첨부 이미지가 있으면 접근 가능한 URL(또는 식별자)을 포함한다. 없으면 null.
- [ ] 게시물 삭제 시 첨부 이미지도 함께 제거한다 (고아 파일 방지).

## 비즈니스 규칙

- COM-004~006 모두 COM-003 권한 규칙(조회는 인증 사용자, 수정·삭제는 소유자만, 타인 콘텐츠 변경 403 `FORBIDDEN`)을 그대로 상속한다. 새 권한 체계를 만들지 않는다.
- 종목 태그(COM-004)는 MKT-001이 관리하는 종목 마스터를 참조로만 쓴다 — 이 spec에서 종목 데이터를 새로 만들지 않는다.
- 기존(008-community 시점) 게시물·댓글은 종목 태그 없음·자식 댓글 없음·이미지 없음 상태로 하위 호환된다. 마이그레이션으로 값을 채우지 않는다.

## 범위 제외

**종목 기준 분류 (COM-004)**
- 게시물당 다중 종목 태그.
- 종목별 통계(태그 게시물 수, 인기 종목 랭킹 등).
- 태그 종목이 비활성화된 뒤 기존 게시물의 태그 처리 정책 (plan에서 별도 확정 없이는 유지).

**대댓글 (COM-005)**
- 대댓글의 대댓글 (2단계 이상 depth).
- 댓글·대댓글 수정 (008-community와 동일하게 계속 제외).
- 댓글 좋아요·신고.

**사진 첨부 (COM-006)**
- 게시물당 이미지 다중 첨부.
- 댓글·대댓글에 이미지 첨부.
- 이미지 리사이징·CDN 캐싱·워터마크 등 후처리.
- 동영상·GIF 등 이미지 외 미디어.

## Decision Gate

- **이미지 저장 방식** (COM-006): 이 프로젝트는 현재 로컬 파일시스템도 객체 스토리지도 인프라에 구성돼 있지 않다 (`compose.yaml`은 MySQL·Redis만 정의, ADR에도 파일 업로드 관련 결정이 없음). 로컬 파일시스템 저장(개발 편의, 배포 시 재검토 필요) vs 객체 스토리지(S3 호환, 초기 인프라 비용) 중 하나를 이슈 착수 시 plan.md에서 확정한다.
- **허용 이미지 형식·최대 크기**: 위 저장 방식 결정과 함께 plan.md에서 확정한다.
- **부모 댓글 삭제 시 자식 처리**: **확정 — tombstone(표시 변경) 채택** (2026-08-11, Issue #277로 아래 원 결정을 대체). 부모 댓글(최상위 댓글, `parentComment == null`) 삭제 시 — 자식 유무와 무관하게, hard delete로 분기하지 않고 — 행을 실제로 지우지 않는다. 대신 `content`를 "삭제된 댓글입니다"로, 작성자 표시를 "(삭제됨)"으로 치환해 보여준다. 자식(대댓글) 자신을 삭제하는 경우는 기존과 동일하게 hard delete를 유지한다 — 대댓글에는 더 하위 자식이 없어 보존할 대상이 없기 때문이다. 자식이 모두 나중에 개별 삭제(hard delete)되어도 tombstone된 부모 행은 정리하지 않고 영구 보존한다.
  - **원 결정 (2026-08 초 작성, 대체됨)**: ~~부모 댓글 삭제 시 `ON DELETE CASCADE`로 자식 대댓글도 함께 삭제한다.~~ (`V25` 마이그레이션으로 구현·머지됨.)
  - **대체 사유**: Issue #277에서 CASCADE가 부모 댓글 작성자 본인의 삭제 행위만으로 다른 회원 소유의 자식 대댓글까지 지워버려, 위 "사용자 시나리오"의 소유권 규칙("남의 대댓글을 지우려 하면 거부당한다")과 함께 성립하는 근거가 plan.md에 "DB 제약으로 구현 단순화"라는 기술적 이유뿐이었다는 점을 지적받았다. tombstone 전환으로 자식 데이터(작성 사실)를 보존하면서도 소유권 규칙과의 정합성을 명시적으로 확보한다.
  - 상세 설계(신규 Flyway 마이그레이션, 엔티티·서비스·응답 DTO 변경)는 `plan.md`의 "COM-005 부모 댓글 tombstone 전환 (이슈 #277)" 절 참고.

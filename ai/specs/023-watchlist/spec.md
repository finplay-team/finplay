# Spec: 관심목록 (Watchlist)

## 개요
사용자가 주식·코인 종목을 관심목록에 등록·조회·해제할 수 있는 실제 서비스 기능이다. 서버 재시작이나 다중 인스턴스 배포에도 상태가 유실되면 안 되므로 MySQL에 영속화한다.

## 기존 `education`/`favorite` 튜토리얼 기능과의 관계 (중요 — 혼동 주의)

`ai/api-routes.md`에는 이미 `POST/GET/DELETE /api/favorites`가 있고 `com.finplay.api.favorite` 패키지로 구현되어 있다. 그러나 이 기능은:

- `ai/specs/016-investment-education-policy`의 3단계 투자 실습 튜토리얼 전용이다(요구사항 EDU-PRACTICE-002).
- `ai/adr/0012-tutorial-state-in-memory.md`에 따라 **의도적으로 서버 힙 메모리(`ConcurrentHashMap`)**에 저장하며, 재시작·다중 인스턴스 시 유실을 사용자가 감수한 결정이다.
- DB 테이블 `favorites`는 V19 마이그레이션으로 이미 DROP되어 더 이상 존재하지 않는다.
- 거래 불가 종목(`instrument.tradable == false`) 등록을 `INSTRUMENT_NOT_TRADABLE`(409)로 막는다 — 실습에서 다음 단계(매수)로 이어지는 선행 조건이기 때문이다.

이번 spec은 **완전히 별개의 실제 서비스 기능**이다. 튜토리얼 코드·ADR-0012·`favorites` 라우트는 이 spec에서 건드리지 않는다. 같은 라우트를 재사용하면 두 기능(하나는 인메모리·튜토리얼 전용, 하나는 DB 영속·실사용)이 뒤섞이므로 **새 도메인 패키지 `com.finplay.api.watchlist`, 새 라우트 `/api/watchlist-items`, 새 테이블 `watchlist_items`**를 쓴다 (근거는 plan.md 참고).

| 구분 | 기존 (education/favorite) | 신규 (이 spec) |
|---|---|---|
| 목적 | 3단계 투자 실습 튜토리얼의 선행 확인 단계 | 실제 서비스 관심목록 |
| 패키지 | `com.finplay.api.favorite` | `com.finplay.api.watchlist` |
| 라우트 | `/api/favorites` | `/api/watchlist-items` |
| 저장소 | 서버 힙 메모리 (ADR-0012) | MySQL (`watchlist_items` 테이블) |
| 재시작 내구성 | 유실됨 (의도된 동작) | 유실되지 않음 |
| 거래 불가 종목 등록 | 거부 (409 `INSTRUMENT_NOT_TRADABLE`) | 허용 — 관심목록은 매수 선행 조건이 아니라 순수 조회/알림 목적의 정보이므로 거래 가능 여부와 무관하게 등록할 수 있다 |
| 요구사항 ID | EDU-PRACTICE-002 (완료) | 이 spec 신설 (아래 "PRD 대조" 참고) |

## PRD 대조 (미확정 사항 — 반드시 확인 필요)

`ai/prd.md`에는 이 기능(실사용 관심목록)에 대응하는 요구사항 ID가 없다. PRD 본문이 다루는 "즐겨찾기"는 전부 EDU-PRACTICE-002(튜토리얼)뿐이다. 이 spec은 오케스트레이터 요청에 따라 신규 기능으로 진행하되, 임의로 PRD ID를 만들어 붙이지 않고 **WATCH-001~003(이 spec 로컬 식별자, PRD 미등재)**로 부른다. PRD에 반영할지, 반영한다면 어느 절(1차 MVP/2차 MVP)에 넣을지는 사람 판단이 필요하다.

## 사용자 시나리오
- 인증 사용자는 거래 가능 여부와 무관하게 주식·코인 종목을 본인 관심목록에 등록할 수 있다. (WATCH-001)
- 인증 사용자는 본인 관심목록을 등록 최신순으로 조회할 수 있다. 시장(`STOCK`|`CRYPTO`)으로 필터링할 수 있다. (WATCH-002)
- 인증 사용자는 본인 관심목록에서 종목을 해제할 수 있다. (WATCH-003)

## 요구사항
- [ ] (WATCH-001) 인증 사용자가 존재하는 종목 ID로 관심목록 등록을 요청하면 201과 등록 정보(종목 정보 포함)를 반환한다.
- [ ] (WATCH-001) 이미 본인 관심목록에 있는 종목을 다시 등록하면 409로 거부한다.
- [ ] (WATCH-001) 존재하지 않는 종목 ID로 등록을 요청하면 404로 거부한다.
- [ ] (WATCH-002) 인증 사용자가 목록을 조회하면 본인이 등록한 항목만, 등록 최신순(동시각은 항목 ID 내림차순)으로 반환한다. `market` 쿼리 파라미터로 STOCK/CRYPTO 필터링이 가능하다.
- [ ] (WATCH-002) 관심목록이 비어 있으면 200과 빈 배열을 반환한다(오류 아님).
- [ ] (WATCH-003) 인증 사용자가 본인 소유 관심 항목을 해제하면 204를 반환하고 이후 목록 조회에서 제외된다.
- [ ] (WATCH-003) 존재하지 않거나 타인 소유인 항목을 해제하려 하면 404로 거부한다(소유 여부를 노출하지 않고 존재 자체를 숨긴다).
- [ ] 서버 재시작 후에도 등록된 관심목록이 그대로 조회된다(MySQL 영속화 확인 — 통합 테스트 대상).

## 비즈니스 규칙
- 사용자·종목 조합은 유일하다 — 동일 사용자가 같은 종목을 중복 등록할 수 없다(DB unique 제약이 최종 방어선).
- 동시에 같은 사용자가 같은 종목을 등록하는 두 요청이 경합하면 하나만 성공(201)하고 나머지는 409를 받는다. 둘 다 성공해 중복 행이 생기지 않는다.
- 관심목록 등록은 종목의 `tradable` 상태를 검사하지 않는다(위 대조표 참고). 종목이 실제로 존재하는지만 확인한다.
- 해제는 본인 소유가 아니거나 존재하지 않는 항목이면 동일하게 404를 반환해 타인 소유 여부를 구분하지 못하게 한다.

## 범위 제외
- 관심목록 항목의 순서 변경(드래그 정렬), 그룹/폴더링 기능.
- 관심 종목의 가격 변동 알림/푸시.
- 목록 조회의 커서 페이지네이션 — 이 spec에서는 사용자당 목록 크기가 크지 않다고 가정하고 전체 목록을 한 번에 반환한다(정렬만 적용). 향후 대량 등록이 문제가 되면 별도 spec에서 페이지네이션을 추가한다.
- PRD §3 "구현 현황" 표에 이 기능을 어떤 요구사항 ID·차수로 등재할지는 사람 결정 사항으로 남긴다(위 "PRD 대조" 참고).

## 완료 조건
- [ ] 등록·목록(필터 포함)·해제 API가 위 요구사항대로 동작하는지 슬라이스 테스트로 확인한다.
- [ ] 중복 등록 방지가 DB 제약 + 서비스 예외 변환으로 동작하는지 단위/통합 테스트로 확인한다.
- [ ] 서버 재시작(테스트 컨텍스트 재기동 시나리오)에도 데이터가 유지되는지 Testcontainers 통합 테스트로 확인한다.
- [ ] `ai/api-routes.md`·`docs/api-contracts.md`에 새 라우트가 반영된다(별도 커밋에서 controller 구현 시).

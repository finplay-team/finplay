# Spec: 코인 체결 집계와 1분봉 Redis 캐싱

> 단계: **1차 고도화**. 이슈 #242.
>
> PRD 근거: **MKT-010**(`ai/prd.md`, PR #241로 반입). 선행 근거: MKT-003(빗썸 WebSocket 실시간 시세), MKT-004(시세 장애 시 주문 거부), MKT-008(코인 캔들 빗썸 REST 중계), C-005(외부 연동은 Fake로 자동 테스트하고 실제 호출은 외부 스모크로 구분 보고).
>
> 선행 spec: `003-market-data`(코인 WebSocket 피드·빗썸 REST 캔들), `013-candle-interval`(interval 4종 확장). **이 spec은 003의 "코인 1분봉을 저장·캐시하지 않는다" 계약과 "서버는 틱을 분봉으로 집계하지 않는다" 결정을 대체한다** — 003·013의 해당 문장은 지우지 않고 이력 표시만 남긴다.
>
> **왜 003을 고치지 않고 새 폴더인가**: 003은 1차 MVP 범위로 이미 완료된 spec이고 그 "저장·캐시 없음" 문장은 당시 계약을 기록한 이력이다. 013도 같은 이유로 후속 폴더를 썼다.

## 개요

코인 1분봉을 **서버가 빗썸 체결 스트림으로 직접 만들어 Redis에 캐싱**한다. `interval=1m` 캔들 조회는 먼저 이 캐시를 보고, 없는 구간만 기존 빗썸 REST 경로로 보충한다.

지금은 코인 캔들 조회가 요청마다 빗썸 REST를 호출하고 캐시가 없다(`BithumbRestCandleProvider` — 클래스 주석에 "저장·캐시 없음" 명시). 게다가 MKT-008은 분 이하 실시간 갱신을 "프론트가 이 API를 짧은 주기로 재조회"로 설계했다. 그래서 **차트를 켜 둔 사용자 수 × 재조회 주기**만큼 외부 호출이 나가고, 빗썸이 느려지거나 막으면 우리 차트도 함께 죽는다.

반면 빗썸 WebSocket은 **사용자 수와 무관하게 연결 한 줄**로 이미 실시간 시세를 받고 있다. 이 유입으로 분봉을 만들면 외부 호출량을 사용자 수에서 떼어낼 수 있다.

## 착수 전 확인한 사실 (2026-08-06, 실제 빗썸 연결)

이 spec의 설계는 아래 실측 위에 서 있다. 추정이 아니다.

- **`ticker` 채널로는 분봉을 만들 수 없다.** 지금 `BithumbWebSocketFeedClient`가 구독 중인 채널이며, `volume`·`highPrice`·`lowPrice`·`openPrice`가 오긴 하지만 개별 체결이 아니라 구독 시 지정한 `tickTypes:["30M"]` 그대로 **최근 30분 롤링 구간의 집계 스냅샷**이다. 1분 버킷으로 쪼갤 수 없다.
- **`transaction` 채널에는 체결 단위 데이터가 있다.** `contPrice`(체결가)·`contQty`(체결 수량)·`contDtm`(체결시각, 밀리초)·`buySellGb`(매수/매도 구분)가 체결 건별로 온다. **1분봉의 OHLCV를 만들 수 있는 유일한 경로다.**
  ```json
  {"type":"transaction","content":{"list":[{"updn":"dn","contDtm":"2026-08-06 15:37:40.154998","contAmt":"14999","contQty":"0.00016332","contPrice":"91839000","buySellGb":"2","symbol":"BTC_KRW"}]}}
  ```
- **`content.list`는 배열이다.** 한 메시지에 체결이 여러 건 묶여 올 수 있다.
- **한 연결에서 두 채널을 동시에 구독할 수 있다.** 구독 메시지를 두 번 보내면 `Filter Registered Successfully`가 두 번 오고 두 종류 메시지가 모두 수신된다. 연결을 새로 열 필요가 없다.
- **`BithumbTickerMessageParser`의 기존 필드 추정은 실제 응답과 일치한다** — `content.symbol`·`content.closePrice`·`content.date`·`content.time` 4개 모두 확인. 이슈 #104가 남긴 Decision Gate(ticker 필드 미확정)는 이로써 해소됐다.
- **ticker 수신 간격이 이미 stale 임계에 근접해 있다.** BTC 기준 30초 측정에서 ticker 최대 공백이 6.0초(단독)·7.0초(transaction 동시 구독)였다. `PriceStore`의 stale 기준은 10초이므로 **현재도 여유가 3~4초뿐**이다. 이 spec은 이 여유를 줄이지 않아야 하며, 오히려 늘리는 방향으로 설계한다(아래 요구사항 참조).

## 사용자 시나리오

- 회원은 코인 차트에서 `interval=1m`을 요청해 지금까지와 **똑같은 형태의** 1분봉 배열을 받는다 — 데이터 출처가 바뀐 것을 알 수 없다.
- 회원이 차트를 켜 두고 화면이 실시간으로 갱신되는 동안, 서버는 빗썸 REST를 호출하지 않는다.
- 빗썸 REST가 장애여도 회원은 최근 구간(우리가 만든 봉)의 차트를 계속 볼 수 있다.
- Redis가 죽어도 회원은 기존과 동일하게(빗썸 REST 경유) 차트를 볼 수 있다 — 코인 차트가 완전히 멈추지 않는다.
- 회원의 코인 주문 체결·현재가 조회는 이 변경으로 **동작이 달라지지 않는다**.

## 요구사항

### 체결 수신

- [ ] `BithumbWebSocketFeedClient`가 기존 `ticker` 구독에 더해 **`transaction` 채널도 구독**한다. 같은 연결에서 구독 메시지를 두 번 보낸다(실측 확인됨). 연결을 추가로 열지 않는다.
- [ ] **기존 `ticker` 구독을 제거하지 않는다.** ticker는 현재가(`PriceStore.saveTick`)·주문 체결 트리거(`CryptoPriceUpdatedEvent` → LMT-002)를 물고 있어, 이를 건드리면 주문 경로가 함께 바뀐다. 이번 범위는 캔들이며 주문 경로는 무변경이다.
- [ ] **`transaction` 체결도 `PriceStore.saveTick`으로 현재가를 갱신한다.** `contPrice`는 실제 체결가이므로 유효한 현재가다. `saveTick`은 이미 "수신시각이 저장값보다 이전이면 무시"하므로 두 채널이 함께 써도 과거 값이 최신을 덮지 않는다(MKT-003 규칙 재사용). **이는 부수효과가 아니라 의도된 개선이다** — 위 실측대로 ticker 단독 공백이 최대 6~7초라 stale(10초) 여유가 얇은데, 두 경로가 함께 갱신하면 공백이 줄어 `PRICE_UNAVAILABLE` 위험이 낮아진다.
- [ ] `content.list`의 **모든 원소**를 처리한다. 첫 원소만 읽고 나머지를 버리지 않는다.
- [ ] 파싱 실패는 기존 ticker와 같은 정책이다 — 예외를 밖으로 던지지 않고 로그만 남긴 뒤 그 메시지를 건너뛴다(연결 유지, 다른 심볼 수신 방해 없음).
- [ ] 체결 메시지 파싱은 **한 클래스에만** 둔다(`BithumbTickerMessageParser`와 같은 격리 원칙). 실제 응답이 달라지면 그 지점만 고친다.

### 1분봉 집계

- [ ] 체결을 **`contDtm`의 분 단위로 버킷팅**해 OHLCV를 만든다.
  - `open` = 그 분의 **첫** 체결가
  - `high` = 그 분 체결가의 **최대**
  - `low` = 그 분 체결가의 **최소**
  - `close` = 그 분의 **마지막** 체결가
  - `volume` = 그 분 `contQty`의 **합**
- [ ] `sourceTime`은 그 분의 시작 시각(`초·나노 = 0`)이며 **KST**다. `contDtm`은 KST 벽시계 문자열이므로 UTC 변환을 하지 않는다(빗썸 `to` 파라미터가 KST라는 PR #164 실측과 같은 원칙).
- [ ] **체결이 하나도 없는 분은 봉을 만들지 않는다.** 0으로 채운 봉·직전 종가로 채운 봉을 만들지 않는다(013의 "값이 0인 봉과 봉이 없는 것은 다르다" 규칙 승계).
- [ ] **진행 중인(아직 끝나지 않은) 분봉도 조회에 포함한다** — MKT-008의 코인 규칙 그대로다. 주식과 반대이며 의도된 차이다.
- [ ] **늦게 도착한 체결 처리(확정)**: 이미 지난 분에 속하는 체결이 뒤늦게 오면 **그 분의 봉을 갱신하지 않고 버린다.** 이미 응답으로 나간 값과 어긋나지 않게 하기 위함이며, `PriceStore.saveTick`의 "과거 틱은 최신을 덮지 못한다"와 같은 방향이다. 버린 건수는 로그로 남겨 관측 가능하게 한다.
- [ ] **분 경계 확정 주체(2026-08-06 PR #255 리뷰로 실제 구현에 맞게 정정)**: 별도 스케줄러도, 별도의 "확정" 상태·이벤트도 두지 않는다. `CryptoCandleStore.recordTrade`가 **매 체결마다** 서버의 현재 시각(Clock)과 그 체결이 속한 분을 비교해 현재 분보다 이전이면 버린다(바로 위 "늦게 도착한 체결 처리"와 같은 가드, `tradeMinute < currentMinute`). 그 결과로 지난 분의 봉은 더 이상 갱신되지 않아 값이 자연히 멈추지만, 이건 "다음 분의 첫 체결이 확정시켜서"가 아니라 **"현재 시각이 그 분을 지나면 그 분으로의 쓰기 자체가 막혀서"**다 — 특정 심볼에 다음 분 체결이 안 와도 이전 분이 미확정 상태로 남는 문제가 원천적으로 생기지 않는다. 스케줄러를 안 쓰는 이유: ① 서버가 두 대일 때 중복 확정을 막을 장치가 추가로 필요하다, ② 기본 프로필의 `@Scheduled`가 이미 12개라 스레드 풀을 또 늘려야 한다(`application.yml` 주석 참조), ③ 체결이 없어 봉이 없는 것은 위 규칙상 정상이다.

### Redis 저장

- [ ] 만든 봉은 **Redis에만** 저장한다. **새 MySQL 테이블·Flyway 마이그레이션을 만들지 않는다**(MKT-008의 "코인 캔들 전용 테이블을 만들지 않는다" 원칙 유지).
- [ ] 키 조립은 `PriceStore`와 같은 원칙으로 **한 클래스 안에서만** 한다. 다른 계층이 키 문자열을 알지 않는다.
- [ ] **기존 `price:crypto:<symbol>`(최신가 Hash)·`price:crypto:<symbol>:snapshots`(분당 샘플 ZSET)와 별개 키를 쓴다.** 셋은 목적이 다르다 — 최신가 1건 / 분당 가격 샘플(변동 감시용) / OHLCV 분봉(차트용).
- [ ] **동시 갱신에 값이 깨지지 않아야 한다.** 체결 하나에 high·low·close·volume 여러 값을 각각 읽고-비교하고-쓰는 사이 다른 체결이 끼어들면 값이 유실된다. 원자적으로 처리한다(구현 방식은 plan에서 확정).
- [ ] **TTL을 건다.** 무한정 쌓지 않는다. 응답 상한이 200봉이므로 그보다 여유 있는 범위만 보관하고, 그보다 오래된 구간은 빗썸 REST가 담당한다. 정확한 값은 plan에서 확정한다.

### 조회 경로

- [ ] `interval=1m` 코인 조회는 **먼저 Redis 캐시를 보고, 없는 구간만 빗썸 REST로 보충**한다.
- [ ] 응답 계약은 **바뀌지 않는다** — `CandleResponse`(`sourceTime`·`open`·`high`·`low`·`close`·`volume`), 시각 오름차순, 최대 200개, 진행 중 분봉 포함. 소비자는 출처가 바뀐 것을 알 수 없다.
- [ ] 캐시 구간과 빗썸 구간을 이어붙일 때 **같은 `sourceTime`의 봉이 중복되거나 사이가 비지 않아야** 한다. 겹치면 **우리 봉을 우선**한다(우리 데이터가 더 최신이며 진행 중 봉을 담고 있다).
- [ ] **Redis 장애 시 빗썸 REST로 자동 폴백**한다. 코인 차트가 Redis 하나에만 의존하는 단일 장애점이 되지 않는다.
- [ ] **빗썸 REST 장애 시에도 캐시에 있는 구간은 정상 응답**한다. 단, 요청 범위가 캐시 밖까지 걸쳐 있고 그 부분을 못 채우면 기존대로 502 `MARKET_DATA_PROVIDER_ERROR`다 — 빈 배열 200으로 성공을 위장하지 않는다(MKT-008 원칙).
- [ ] **`1d`·`1w`·`1M`은 이번 범위가 아니다.** 계속 빗썸 위임(MKT-009) 그대로다.

### 측정 (PRD §10 Decision Gate 충족)

- [ ] **착수 전 현재 빗썸 REST 호출량을 실측해 기록한다.** PRD §10에 "관측 전에 임의의 캐시 계층이나 TTL 숫자를 넣지 않는다"는 Decision Gate가 있고, 이 작업이 바로 그 캐시 계층이다. 게이트를 폐기하지 않고 충족시킨다.
- [ ] 구현 후 **같은 기준으로 다시 측정해 대조**한다. 실측 없이 "호출이 줄었다"고 주장하지 않는다(C-005).

## 비즈니스 규칙

- **코인 시세의 정본은 여전히 빗썸이다.** 우리 캐시는 정본을 대체하는 것이 아니라 최근 짧은 구간을 보완한다. 캐시가 유실되면 빗썸에서 다시 받으면 된다.
- **우리 봉과 빗썸 봉의 값이 완전히 같을 수는 없다.** 빗썸이 어떤 체결까지 그 분에 넣는지 정확히 알 수 없고, 우리 서버가 꺼져 있던 동안의 체결은 받지 못했다. 억지로 맞추려고 서버에서 보정하지 않는다(MKT-008의 "캔들과 현재가를 맞추려고 보정하지 않는다"와 같은 원칙).
- **서버가 꺼져 있던 구간은 우리 데이터가 불완전하다.** 그 구간은 빗썸 REST가 담당한다.
- **주문 체결가 계약은 이 spec으로 바뀌지 않는다.** 체결은 계속 `PriceStore`의 유효한 최신가로만 이루어진다. 우리가 만든 분봉을 체결가로 쓰지 않는다.
- **캐시는 파생값이지 원장이 아니다.** 유실돼도 회원 자산·주문·체결에 영향이 없다.

## 범위 제외

- **일봉·주봉·월봉 자체 집계** — MKT-009 그대로 빗썸 위임 유지.
- **코인 캔들 MySQL 영구 저장** — Redis 캐시까지만. 새 테이블·마이그레이션 없음.
- **코인 전용 SSE·WebSocket push** — PRD에서 제외한 범위. 프론트 재조회 방식 유지. (다만 이 작업이 그 재조회를 싸게 만들어 push 도입의 선행 조건이 된다.)
- **주식 실시간 틱 집계** — 주식은 재생 방식이라 완전히 다른 문제(MKT-007, KIS 실시간 후속).
- **`ticker` 구독 제거·현재가 경로 재설계** — ticker는 그대로 둔다. transaction을 현재가에 **더하는** 것까지만 한다.
- **비정상 경로 검증(재연결 중 체결 유실, 장시간 단절 후 복구, 다중 서버 경합 실측)** — 1차 고도화 전체가 끝난 뒤 통합 QA 단계에서 다룬다.
- **응답 상한 200 조정·페이지네이션** — 기존 계약 유지. **(이력) 페이지네이션·커서 도입은 2차 고도화(이슈 #473, `048-candle-history-pagination`)에서 도입됨 — 상한 200 자체는 그대로 유지.**

## 완료 조건

- [ ] `transaction` 채널 구독이 추가되고, 기존 `ticker` 구독·현재가·주문 경로가 **회귀 없이** 동작한다.
- [ ] 체결 목록(`content.list`)의 원소가 여러 개일 때 **전부** 집계에 반영된다 — 첫 원소만 처리하지 않는다.
- [ ] 집계 단위 테스트가 통과한다 — 같은 분의 체결들로 첫 체결가=open·최대=high·최소=low·마지막=close·수량합=volume이 산출되고, 분이 바뀌면 새 봉이 생기며, 체결 없는 분에는 봉이 생기지 않는다.
- [ ] 늦게 온 체결(이미 지난 분)이 **무시되고** 기존 봉이 바뀌지 않는다.
- [ ] **동시성 테스트가 통과한다** — 스레드 여러 개가 같은 심볼에 동시에 체결을 넣어도 `volume` 합계가 정확하고 어떤 체결도 유실되지 않는다. 실제 Redis(Testcontainers)로 검증한다. **이 테스트가 이 작업의 핵심 검증이며 mock으로 대체하지 않는다**(ADR-0003).
- [ ] `interval=1m` 조회가 캐시 구간을 Redis에서 읽고, 캐시 밖 구간만 빗썸을 호출한다 — 호출 여부를 테스트로 검증한다.
- [ ] 캐시 구간과 빗썸 구간이 이어질 때 **`sourceTime` 중복·누락이 없다.**
- [ ] Redis 장애 시 빗썸 REST로 폴백해 200을 반환한다.
- [ ] 빗썸 REST 장애 시 캐시 구간만으로 응답 가능한 요청은 200이고, 캐시 밖을 채워야 하는 요청은 502다.
- [ ] `interval=1d`·`1w`·`1M`과 주식 캔들 전체가 **회귀 없이** 동작한다.
- [ ] 빗썸 REST 호출량 **before/after 실측치**가 기록된다.
- [ ] 자동 테스트는 Fake로 수행하고, 실제 빗썸 연결 검증은 **외부 스모크로 구분해** 보고한다(C-005).
- [ ] `docs/api-contracts.md`의 코인 캔들 절이 "저장·캐시하지 않는다" 서술과 상충하지 않게 갱신된다(같은 커밋).
- [ ] `ai/prd.md` §3 구현 현황의 MKT-010 행이 갱신된다(근거 칸에 PR 번호).
- [ ] `ai/specs/003-market-data`·`013-candle-interval`의 "코인은 저장·캐시 없음" 서술에 이력 표시가 남는다.
- [ ] `./gradlew build` 통과.

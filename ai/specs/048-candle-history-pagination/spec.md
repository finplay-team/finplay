# Spec: 캔들 차트 과거 구간 탐색 — 과거 방향 커서 페이지네이션

> 단계: **3차 MVP(팀 회의 표현: 2차 고도화)**. 이슈 #473.
>
> PRD 근거: 이 기능은 PRD에 대응 요구사항이 없어 **`CANDLE-PAGE-*`를 신설하고 이 spec이 정본으로 소유한다** — 아래 "§요구사항 ID 소유 (확정)" 절 참조. 선행 근거: MKT-008(코인 1분봉 빗썸 REST 중계, "한 요청의 최대 개수 200"), MKT-009(캔들 기간 확장 `1m·1d·1w·1M`), MKT-010(코인 1분봉 Redis 캐시·`since` 워터마크), MKT-002(주식 과거 거래일 재생), MKT-005(개장 전 폴백), C-005(외부 연동은 Fake로 자동 테스트하고 실제 호출은 외부 스모크로 구분 보고).
>
> 선행 spec: `003-market-data`(캔들 API 최초 계약), `013-candle-interval`(interval 4종 확장·**200개 상한 계약화**·`from`/`to` 해석), `027-crypto-tick-candle-cache`(코인 1분봉 캐시·위임 병합), `038-stock-quote-last-known-hold`(`marketStatus=CLOSED` 장외 폴백), `018-order-list-pagination`(이 저장소의 커서 페이지네이션 선례 — `content`/`nextCursor`/`hasNext` 3필드, `{시각}_{id}` 커서 문자열).
>
> **이 spec은 013·027의 "봉 개수 상한 200의 조정, 페이지네이션·커서 도입"·"응답 상한 200 조정·페이지네이션" 범위 제외 문장을 대체한다** — 두 spec의 해당 문장은 지우지 않고 "2차 고도화(이슈 #473, 048)에서 도입됨" 이력 표시만 남긴다. 013·027은 이미 완료된 spec이고 그 문장들은 **당시 계약을 기록한 이력**이다. 003→013, 006→018, 013→027이 모두 같은 이유로 후속 폴더를 썼다.
>
> **200개 상한 자체는 유지한다.** 이슈 #155가 읽기 비용 방어 목적으로 넣은 결정이며 이 spec은 그것을 되돌리지 않는다 — 요청 1건당 상한은 그대로 두고 "그 앞 구간을 이어서 받는" 계약만 추가한다.
>
> **문서 동기화 상태**: 계약은 아래 "§확정된 계약 결정"에서 모두 확정됐다. `ai/api-routes.md`·`docs/api-contracts.md`·`ai/prd.md` §3 갱신은 구현 착수 시 컨트롤러 변경과 같은 커밋에서 한다(CLAUDE.md 규칙 7·10). 현재 두 문서에는 "200개를 넘는 구간을 이어붙이는 페이징은 1차 범위가 아니다"가 남아 있다.
>
> **이 spec은 배포 순서가 계약의 일부다.** 응답이 맨 배열에서 봉투로 바뀌는 breaking change이고, `dev` 머지가 곧 배포이며(ADR-0021) 프론트는 S3에서 따로 배포되므로(ADR-0022), 프론트 선행 배포 없이 백엔드를 머지하면 그 순간 운영 차트가 깨진다. CANDLE-PAGE-027~029 참조.

## 개요

캔들 API `GET /api/instruments/{instrumentId}/candles`에 **과거 방향 커서 페이지네이션**을 추가한다. 지금은 프론트가 차트를 왼쪽으로 밀어도 200개 이전 구간을 더 요청할 방법이 계약에 없다 — `from`·`to`만 있고 "이 봉보다 더 과거를 달라"고 말할 파라미터가 없다.

- **코인 1분봉**: 과거 조회 자체는 이미 동작한다(`CachedCryptoCandleProvider`가 `from`·`to`를 실제 달력 시각 그대로 쓴다). 막고 있는 것은 빗썸 REST의 한 번에 200개 응답 상한뿐이다.
- **집계봉(`1d`·`1w`·`1M`, 주식·코인 공통)**: 집계 결과에서 **항상 최신 200개만 남기고 그 이전을 버린다**(`StockReplayService.MAX_AGGREGATED_CANDLES = 200`, `subList(size - 200, size)`). 데이터가 없어서가 아니라 꺼낼 계약이 없다.

**데이터는 이미 있다.** `stock_candles`에는 여러 거래일치 1분봉이 쌓여 있고 일·주·월봉은 그 1분봉을 요청 시점에 실시간 집계해 만든다. 새 테이블도, 집계 결과 사전 저장도 필요 없다.

**커서 계약은 코인 1m과 집계봉이 완전히 같은 형태여야 한다** — 프론트가 `interval`이나 시장에 따라 다른 페이징 코드를 타면 이 작업의 의미가 없다.

## 사용자 시나리오

- 회원은 코인 차트를 왼쪽으로 끝까지 밀어 200봉 이전 구간을 이어서 볼 수 있다.
- 회원은 주식·코인 일봉 차트를 왼쪽으로 밀어 최신 200버킷 이전의 과거 일봉을 볼 수 있다. 주봉·월봉도 같다.
- 회원이 페이지를 이어받을 때 **경계에서 봉이 중복되거나 빠지지 않는다** — 차트에 같은 봉이 두 번 그려지거나 한 칸이 비지 않는다.
- 회원이 데이터의 맨 끝(우리가 가진 가장 오래된 봉)까지 밀면 차트가 "더 이상 없음"을 알고 로딩을 멈춘다 — 무한히 빈 요청을 반복하지 않는다.
- 회원은 커서를 쓰지 않고 예전처럼 요청해도 지금까지와 같은 최신 구간을 받는다 — 봉이 담기는 그릇(봉투)만 바뀌고 보이는 차트는 그대로다.
- 회원은 배포 도중에도 차트가 깨진 화면을 보지 않는다 — 프론트가 배열·봉투 두 형태를 모두 받아들이게 된 뒤에 백엔드가 배포되기 때문이다.
- 회원의 코인 차트는 서버 캐시 구간과 빗썸 위임 구간의 경계를 넘어갈 때도 봉이 어긋나지 않는다.

## 요구사항

> ID는 아래 "§요구사항 ID 소유"에서 확정한 대로 이 spec이 정본으로 소유하는 `CANDLE-PAGE-*`다.

### 공통 커서 계약 (코인 `1m` · 집계봉 `1d`·`1w`·`1M` 동일)

- [ ] **CANDLE-PAGE-001** `GET /api/instruments/{instrumentId}/candles`가 선택 파라미터 **`cursor`**를 받는다. 값은 **직전 페이지에서 가장 오래된 봉의 `sourceTime`을 ISO-8601 `LocalDateTime` 문자열로 그대로 적은 것**이다(예: `2026-08-19T09:00:00`). 불투명 토큰이 아니며 응답의 `sourceTime`과 같은 타입·같은 표기다.
- [ ] **CANDLE-PAGE-002** `cursor`를 생략하면 **값·개수·정렬·`from`/`to` 해석·"봉이 없음" 조건·오류 계약이 지금과 완전히 동일**하다. 바뀌는 것은 봉 배열을 감싸는 **응답 형태(봉투)뿐**이며, 그 형태 변경은 CANDLE-PAGE-027~029의 배포 순서로 무중단 처리한다. `cursor`는 동작에 대해 순수 추가(additive) 파라미터다.
- [ ] **CANDLE-PAGE-003** 커서의 의미는 **"이 시각의 봉보다 더 과거의 봉을 달라"**이며 **상한 배타(exclusive)**다 — 커서와 같은 `sourceTime`의 봉은 다음 페이지에 포함되지 않는다. (기존 `to`가 포함(inclusive)인 것과 반대이며, 그래야 이전 페이지 마지막 봉을 그대로 커서로 넘겨도 중복이 생기지 않는다.)
- [ ] **CANDLE-PAGE-004** 응답은 커서 유무와 무관하게 **시각 오름차순**이며, 한 응답의 봉 개수 상한은 **200개**다(013의 계약 유지). 커서는 이 상한을 늘리거나 우회하는 수단이 아니다.
- [ ] **CANDLE-PAGE-005** 응답은 **항상 봉투**이며 필드는 `content`(봉 배열)·`nextCursor`(다음 커서, 없으면 `null`)·`hasNext`(boolean) **3개**다 — `OrderListResponse`·`TradeListResponse`·`JournalListResponse`와 같은 형태·같은 이름. 커서 유무와 무관하게 같은 형태를 반환한다(요청에 따라 배열/봉투가 갈리지 않는다). 소비자는 "더 과거가 있는가"와 "다음 커서"를 추측 없이 읽는다.
- [ ] **CANDLE-PAGE-006** 다음 커서로 이어 조회하면 **중복·누락 없이** 이전 페이지의 가장 오래된 봉 바로 앞에서 이어진다.
- [ ] **CANDLE-PAGE-007** 더 이상 과거 데이터가 없으면 `hasNext=false`·`nextCursor=null`로 명시적으로 알린다. 소비자는 `content`가 비는 것을 기다려 종료를 판정하지 않는다. `hasNext`는 **"이번 페이지의 `content`가 200개로 꽉 찼는가"**로 판정하며, 그 결과 **마지막 페이지가 정확히 200개면 `content`가 빈 페이지가 한 번 더 나오고 거기서 `hasNext=false`가 된다** — 버그가 아니라 계약이므로 소비자는 빈 페이지 1회를 정상으로 받아들인다. **유일한 예외는 주식 `1m`으로, 봉이 200개여도 `hasNext=false`다**(CANDLE-PAGE-026 — 이어받을 과거 구간 자체가 이 spec의 범위 밖이기 때문이며, 필드 이름·형태는 동일하므로 CANDLE-PAGE-008의 균질 계약은 유지된다).
- [ ] **CANDLE-PAGE-008** 커서 계약(파라미터 이름·형식·응답 필드·"더 있음" 판정 규칙·데이터 끝 동작)은 **코인 `1m`과 집계봉 `1d`·`1w`·`1M`이 완전히 동일**하다. `interval`별·시장별로 다른 필드나 다른 의미를 두지 않는다.
- [ ] **CANDLE-PAGE-009** ISO-8601 `LocalDateTime`으로 파싱되지 않는 `cursor`는 400 `VALIDATION_ERROR`다 — 조용히 무시하고 첫 페이지를 돌려주지 않는다(`GET /api/orders`·`GET /api/trades`의 커서 파싱 실패와 같은 계약).
- [ ] **CANDLE-PAGE-010** 커서 검증 순서는 기존 검증 순서를 깨지 않는다 — `interval`(400) → `instrumentId` 존재(404) → 시장 종류 → `from`/`to`·커서 순으로 판정한다. 잘못된 `interval`은 커서가 유효해도 여전히 400이고, 없는 종목은 여전히 404다.
- [ ] **CANDLE-PAGE-011** 기존 오류 계약은 그대로다 — 없는 `instrumentId`는 404 `NOT_FOUND`, `from > to`는 400 `VALIDATION_ERROR`, 코인 외부 조회 실패는 502 `MARKET_DATA_PROVIDER_ERROR`, 인증 실패는 401 `UNAUTHORIZED`. 커서 도입으로 새 오류 코드를 만들지 않는다.
- [ ] **CANDLE-PAGE-012** `cursor`와 `from`·`to`를 함께 보내면 **`cursor`가 상한을 덮어쓴다** — `to`는 무시되고(400이 아니다) `cursor`가 배타 상한이 되며, `from`은 하한으로 계속 유효하다. **"`to`와 `cursor`가 동시에 오면 `to`가 무시된다"를 `docs/api-contracts.md`에 명시한다** — 조용한 무시는 문서화되지 않으면 프론트가 원인을 못 찾는다.
  - **착수 시 확정할 세부 1건**: `to`가 무시되는 상황에서 `from > to`(400, CANDLE-PAGE-011)를 여전히 검증할지, 아니면 `from`과 `cursor`만 비교할지. 이 spec은 어느 쪽도 단정하지 않으며 plan 작성 시 결정해 계약 문서에 적는다.

### 코인 `1m` — 캐시·위임 경계

- [ ] **CANDLE-PAGE-013** 커서로 과거 방향 연속 조회가 실제로 이어진다 — 빗썸 REST의 200개 응답 상한 아래에서 페이지를 반복해 받아도 봉이 끊기지 않는다.
- [ ] **CANDLE-PAGE-014** **Redis 캐시 구간(MKT-010)과 빗썸 REST 위임 구간이 커서 경계에서 어긋나지 않는다** — 커서가 `since` 워터마크(그 심볼의 캐시 신뢰 시작점) 앞뒤 어디에 놓여도 같은 `sourceTime`의 봉이 중복되거나 사이가 비지 않는다. 겹치면 기존 규칙대로 **우리 봉을 우선**한다(027).
- [ ] **CANDLE-PAGE-015** 커서가 `since`보다 과거를 가리키면 그 구간은 전량 빗썸 REST가 담당한다 — 캐시가 없다는 이유로 빈 배열을 만들지 않는다.
- [ ] **CANDLE-PAGE-016** 빗썸이 그 구간에 봉을 주지 않으면(상장 이전 등) 데이터 끝으로 판정한다. 502로 만들지 않는다 — 조회 실패(타임아웃·비정상 상태코드·파싱 불가)와 "그 구간에 데이터가 없음"은 다르다. 조회 실패는 기존대로 502다.
- [ ] **CANDLE-PAGE-017** Redis 장애 시 기존대로 빗썸 REST 전량 위임으로 폴백하며, 이때도 커서 페이징이 동작한다(단일 장애점 방지 원칙 유지).

### 집계봉 `1d`·`1w`·`1M` — 기준점 이동

- [ ] **CANDLE-PAGE-018** `narrowRangeStart`가 "최신 200버킷"을 역산해 조회 하한을 좁히는 최적화이므로, **커서가 주어지면 그 역산 기준점이 커서 위치로 옮겨간다.** 커서를 준 요청이 여전히 최신 200버킷 구간만 읽고 잘라 버리면 이 기능은 동작하지 않는다.
- [ ] **CANDLE-PAGE-019** 요청 1건이 읽는 봉은 여전히 최대 200개다 — 커서 기준으로 **그보다 과거 방향 최신 200버킷**을 반환한다. `subList`로 잘라 버리던 구간이 이제 다음 페이지로 나온다.
- [ ] **CANDLE-PAGE-020** **집계 결과를 저장하지 않는다** — 새 테이블·새 Flyway 마이그레이션·집계 캐시를 만들지 않고 `stock_candles` 1분봉 실시간 집계 구조를 유지한다.
- [ ] **CANDLE-PAGE-021** **공개 상한(reveal bound)은 커서로 우회되지 않는다.** 커서는 과거 방향으로만 이동하므로 공개 상한과 충돌하지 않아야 하지만, 커서가 공개 상한보다 미래를 가리켜도 응답은 공개 상한 아래로만 채워진다 — 미공개 분봉이 어떤 커서 값으로도 새어 나가지 않는다(013의 규칙 유지).
- [ ] **CANDLE-PAGE-022** 오늘 `READY` 재생세션이 없을 때의 기존 동작(200 + 봉 없음 → `content: []`, 또는 `marketStatus=CLOSED`면 038의 장외 폴백)은 커서 유무와 무관하게 유지된다. 이때 `hasNext=false`·`nextCursor=null`이다.
- [ ] **CANDLE-PAGE-023** 거래일이 없는 주·월은 여전히 응답에 넣지 않으며(빈 봉으로 채우지 않음), 반환된 봉의 `sourceTime`이 달력상 연속임을 보장하지 않는다. **따라서 소비자는 "봉 사이가 비어 있음"을 데이터 끝으로 오해하면 안 되고, `hasNext`(CANDLE-PAGE-005·007)로만 판정한다.**
- [ ] **CANDLE-PAGE-024** 코인 집계봉(`1d`·`1w`·`1M`)도 같은 커서 계약을 따른다 — 빗썸 위임 구조는 그대로이고 커서가 위임 요청의 상한으로 전달된다.

### 주식 `1m` — 동작 무변경 (형태만 봉투)

- [ ] **CANDLE-PAGE-025** 주식 `interval=1m`이 **어떤 봉을 주는지는 한 글자도 바뀌지 않는다** — 단일 재생 거래일 고정, `from`·`to`의 날짜 성분 무시·시각 성분만 사용, 미마감 분봉 제외, 세션 미준비 시 200 + 봉 없음, 038 장외 폴백 전부 그대로다. 유일한 변화는 그 봉들이 `content`에 담겨 나온다는 것뿐이다(CANDLE-PAGE-005의 균질 봉투).
- [ ] **CANDLE-PAGE-026** 주식 `1m`은 `cursor`를 **받되(400이 아니다) 항상 `hasNext=false`·`nextCursor=null`**로 응답한다. `content`는 커서 없는 요청과 동일한 단일 재생 거래일 구간이며 **과거 거래일로 넘어가지 않는다.** 프론트는 분기 없이 같은 페이징 코드를 쓰고 "여기서 끝"임을 안다.

### 배포 순서 (breaking change 무중단 전환)

- [ ] **CANDLE-PAGE-027** **1단계 — 프론트 선행 배포.** `FinPlay` 레포가 캔들 응답을 `data.content ?? data`로 읽어 **배열·봉투 두 형태를 모두 처리**하도록 바꾸고 먼저 배포한다. 이 배포는 백엔드 변경 없이 현재 운영(배열 응답)에서 그대로 동작해야 한다.
- [ ] **CANDLE-PAGE-028** **2단계 — 백엔드 배포.** 1단계 배포가 운영에 반영된 것을 확인한 **뒤에** 이 spec의 백엔드 변경을 `dev`에 머지한다. `dev` 머지가 곧 배포이므로(ADR-0021) 순서를 뒤집으면 그 순간 운영 차트가 깨진다 — 프론트는 S3에서 따로 배포되어(ADR-0022) 백엔드와 동시에 갱신되지 않는다.
- [ ] **CANDLE-PAGE-029** **3단계 — 폴백 제거.** 봉투 응답이 운영에서 안정화된 뒤 프론트의 `?? data` 폴백을 제거해 응답 형태가 봉투 하나로 수렴한다. 이 단계는 별도 프론트 작업이며 백엔드 변경을 동반하지 않는다.

## 비즈니스 규칙

- **커서는 읽기 상한을 늘리는 수단이 아니다.** 요청 1건이 읽는 봉은 항상 최대 200개다(이슈 #155의 읽기 비용 방어 결정 유지). 커서는 그 상한을 여러 번에 나눠 이어받게 할 뿐이다.
- **공개되지 않은 주식 분봉은 어떤 커서 값으로도 새어 나갈 수 없다.** 커서는 조회 상한을 과거로 옮기는 값이지 공개 상한을 올리는 값이 아니다.
- **집계 봉은 여전히 파생값이지 정본이 아니다.** 정본은 주식 1분봉(`stock_candles`)과 빗썸 응답이며, 페이징을 위해 집계 결과를 저장하지 않는다. 주문 체결가 계약(ORD·LMT)은 이 spec으로 바뀌지 않는다.
- **코인 시세의 정본은 여전히 빗썸이다.** 우리 Redis 캐시는 최근 짧은 구간만 보완하므로, 과거 방향으로 갈수록 응답은 사실상 전부 빗썸 위임이다.
- **"봉이 없음"과 "더 이상 데이터가 없음"은 다르다.** 거래일이 없는 주·월, 체결이 없는 분은 봉이 없을 뿐 데이터 끝이 아니다. **`content` 안의 봉 사이가 달력상 비어 있는 것은 데이터 끝의 신호가 아니며**, 끝은 오직 `hasNext=false`로 판정한다. 마지막 페이지가 정확히 200개였다면 **빈 `content` + `hasNext=false` 페이지가 한 번 나오는 것이 정상**이다(CANDLE-PAGE-007).
- **커서 없는 기존 요청의 "내용"은 절대 바뀌지 않는다 — 바뀌는 것은 "형태"뿐이고, 그 형태 변경은 배포 순서로 흡수한다.** 봉투 도입은 응답 형태를 바꾸는 breaking change이므로 "기존 소비자가 아무것도 바꾸지 않아도 된다"는 성립하지 않는다. 대신 **프론트가 배열·봉투 둘 다 받아들이도록 먼저 배포되고(CANDLE-PAGE-027), 그 뒤에 백엔드가 배포되며(028), 안정화 후 폴백을 걷어낸다(029)** — 이 순서를 지키는 한 회원이 깨진 화면을 보는 순간은 없다. 값·개수·정렬·`from`/`to` 해석·오류 계약은 어느 단계에서도 그대로다(CANDLE-PAGE-002).
- **커서 계약은 `interval`·시장에 대해 균질하다.** 프론트는 하나의 페이징 코드로 4개 `interval` × 2개 시장을 다룬다.

## 범위 제외

- **주식 `1m`의 과거 거래일 조회** — 아래 별도 절 참조. 이 spec에서 하지 않는다.
- **미래 방향(더 최신) 페이지네이션** — 차트 오른쪽 끝은 항상 최신이며 기존 무커서 요청이 그 역할을 한다.
- **200개 상한 자체의 조정과 `limit` 파라미터** — 이슈 #155 결정을 유지하고 **`limit`은 두지 않는다.** 한 응답은 항상 최대 200개다.
- **새 캔들 테이블·집계 결과 사전 저장·집계 캐시** — `stock_candles` 실시간 집계 구조를 유지한다. 성능 문제가 실측되면 별도 이슈로 다룬다.
- **프론트엔드 무한 스크롤 UI** — 별도 레포(`FinPlay`) 작업이다.
- **코인의 1분 외 짧은 간격(3·5·10·15·30·60·240분)** — 013이 제외한 범위 그대로다.
- **`GET /api/instruments/{id}/price-moves`·SSE·현재가 등 다른 시세 엔드포인트** — 이 spec은 캔들 조회 하나만 다룬다.

### 주식 `1m` 과거 거래일 조회를 제외하는 이유 (기술적 제약이 아니다)

주식 `1m`을 뺀 것은 구현이 어려워서가 아니라 **재생(replay) 모델에 시간축이 두 개**라 "차트에서 하루 왼쪽"이 무엇인지 아직 정의되지 않았기 때문이다.

- 주식은 실시간이 아니라 "과거 어느 거래일(`sourceTradingDate`)의 분봉을 오늘 09:00~15:30에 맞춰 재생"하는 구조다(MKT-002). `getRevealedCandles`는 `from`·`to`의 날짜 성분을 버리고 `LocalTime`만 쓰며, 거래일은 재생세션의 `sourceTradingDate`로 고정된다.
- 그래서 축이 둘이다 — **서비스 날짜 기준 어제**인가, **원본 거래일 기준 이전 거래일**인가. 둘은 일치하지도 않는다: 개장 전 폴백(MKT-005) 때문에 어제 세션이 재생한 거래일이 오늘 것의 바로 직전이 아닐 수 있다(`StockReplayService` 253~256행 주석).
- 집계봉은 이미 **원본 거래일 축**을 쓰기로 확정돼 있어(013) 이 논쟁이 없고, 그래서 이번 범위에 들어온다.

**주식 `1m` 과거 조회는 어느 축을 차트의 시간축으로 삼을지 결정하는 별도 ADR이 먼저 필요하다.** 그 ADR 없이 구현하면 "차트를 왼쪽으로 밀었을 때 나오는 어제"가 무엇인지 서버·프론트·QA가 서로 다르게 이해하게 된다. 이 spec은 그 결정을 선점하지 않는다.

## 요구사항 ID 소유 (확정)

**`CANDLE-PAGE-001~029`는 이 spec이 정본으로 소유하고, PRD에는 §3 "구현 현황" 행만 추가한다.** `MKT-009`·`MKT-010`은 이미 **완료**로 닫혀 있어(§3 표, PR #151) 그 행을 다시 여는 대신 새 ID를 쓴다 — 완료 행을 되돌리면 §3 표의 "무엇이 실제로 동작하는가"가 흐려진다.

- 근거: 이 저장소에는 **PRD 요구사항 절 없이 spec이 ID의 정본**인 선례가 여러 건이다 — `WATCH-001~003`(023), `TRADESHARE-001~004`(046), `QUOTE-HOLD-001~007`(038), `LIKE-001·002`·`SORT-001`(045), `COLLECT-STAB-001~005`(035), `PRICE-NOSTALE-001~004`(036). PRD §3 주석이 이 패턴을 인정한다.
- 근거: 이 작업은 새 제품 요구사항이 아니라 **기존 계약(MKT-008·009·010)의 조회 방식 확장**이다. PRD에 새 절을 만들면 캔들 계약이 네 군데로 흩어진다. 성격상 `MKT-*`(시세를 어디서 가져오는가)보다 `PORT-003`(주문 목록 커서 페이지네이션)에 가깝다.
- 이름 근거: 기능명이 ID에 드러나 §3 표에서 ID로 바로 검색된다(이슈 #410이 지적한 문제와 같은 종류).

**PRD §3 판정은 "완료"**이며, 근거 칸에 PR 번호와 함께 **"주식 `1m` 과거 거래일 조회는 별도 ADR·이슈"**를 명시한다 — 이 spec의 범위는 처음부터 주식 `1m`을 포함하지 않으므로 "일부 완료"는 이 spec에 대한 판정으로 부정확하다.

## 확정된 계약 결정

검토에서 다음이 확정됐다. 구현·리뷰·QA는 이 절을 계약의 근거로 삼는다.

- **응답 형태 — 항상 봉투.** `content`/`nextCursor`/`hasNext` 3필드로 바꾼다(`OrderListResponse`·`TradeListResponse`·`JournalListResponse`와 동일 형태). 커서 유무에 따라 배열/봉투가 갈리면 같은 엔드포인트가 두 형태를 갖고 프론트 타입이 유니온이 되며, 헤더나 별도 엔드포인트(`/candles/history`)는 저장소에 선례가 없거나 같은 데이터에 두 경로를 만든다.
  - **이것은 이미 배포된 응답 계약을 바꾸는 breaking change다.** 018이 `GET /api/orders`에서 같은 판단을 했지만 그때와 달리 여기는 **운영 중인 차트 화면**이 걸려 있어, 형태 변경 비용을 **배포 순서**(CANDLE-PAGE-027~029)로 지불한다: 프론트가 `data.content ?? data`로 배열·봉투를 모두 받게 먼저 배포 → 백엔드 배포 → 안정화 후 폴백 제거. `dev` 머지가 곧 배포이고(ADR-0021) 프론트는 S3에서 따로 배포되므로(ADR-0022) 순서를 지키지 않으면 백엔드 배포 순간 운영 차트가 깨진다.
- **커서 파라미터 이름 — `cursor`.** 저장소 전반의 페이징 파라미터 이름이 이미 `cursor`로 통일돼 있다.
- **커서 형식 — 그 페이지 가장 오래된 봉의 `sourceTime`(ISO-8601 `LocalDateTime`).** 캔들에는 `id`가 없어 형제 API의 `{시각}_{id}`를 쓸 수 없고, 저장소의 커서는 전부 사람이 읽는 문자열이며, `sourceTime`은 이미 응답에 있어 프론트가 별도 상태를 들 필요가 없다. 불투명 토큰이 아니므로 소비자가 임의 시각을 넣어도 동작한다(성격이지 결함이 아니다).
- **커서 + `from`/`to` — 커서가 상한(`to`)을 덮어쓴다.** `from`은 하한으로 계속 유효하다. 차트 사용 패턴("이 봉 이전을 200개 더")에 가장 자연스럽다. 대신 **"`to`와 커서가 동시에 오면 `to`가 무시된다"를 계약 문서에 반드시 명시**한다(CANDLE-PAGE-012).
- **주식 `1m`에 커서 — 받되 항상 `hasNext=false`·`nextCursor=null`.** 400으로 막으면 프론트가 `interval`별로 분기해야 해 균질 계약(CANDLE-PAGE-008)이 깨지고, 조용히 무시하면 프론트가 "왜 안 넘어가지"를 원인 없이 겪는다. 이 방식이면 나중에 별도 ADR로 주식 `1m` 과거 조회가 열려도 `hasNext`만 `true`가 되어 프론트 변경이 없다.
- **`limit` 파라미터 — 두지 않는다.** 항상 최대 200개. 이번 이슈의 목적은 "더 과거를 볼 수 있게"이지 "적게 받게"가 아니고, 형제 API의 `limit`(1~100·기본 20)과 범위·기본값이 달라지는 것도 피한다.
- **`hasNext` 판정 — "이번 페이지가 200개 꽉 찼는가".** 201개를 조회해 판정하면 빈 페이지가 없어지지만 **빗썸 응답 상한이 200이라 코인에서는 그 방식이 불가능**하고, 그러면 판정 규칙이 시장별로 갈려 CANDLE-PAGE-008(균질 계약)을 위반한다. 그 대가로 **마지막 페이지가 정확히 200개면 빈 페이지가 1회 더 나오는 것을 계약으로 명시**한다(CANDLE-PAGE-007).
- **PRD §3 판정 — "완료"**, 근거 칸에 PR 번호와 "주식 `1m` 과거 거래일 조회는 별도 ADR·이슈"를 함께 적는다.
- **요구사항 ID — `CANDLE-PAGE-*`를 이 spec이 소유**(위 "§요구사항 ID 소유" 참조).

### 아직 확정하지 않은 것 — 코인의 데이터 끝

빗썸이 상장 이전 구간을 어떻게 응답하는지(빈 배열인지 오류인지)는 **여전히 확인되지 않았다.** 확인 없이 "빈 응답 = 끝"으로 단정하면 일시적 빈 응답을 영구 종료로 오해할 수 있다. 착수 시 **외부 스모크로 관측해 관측한 그대로** 계약에 기록한다(C-005·013의 `to` 경계 관측과 같은 방식). 추측으로 적지 않는다.

## 완료 조건

- [ ] **커서 없는 기존 요청이 값 회귀 없이 동작한다 — 바뀌는 것은 형태뿐이다.** 4개 `interval` × 주식·코인 전 조합에서 **값·개수·정렬·`from`/`to` 해석·"봉이 없음" 조건·오류 계약이 이전과 동일**하고, 차이는 **그 봉 배열이 `content`로 감싸진 것뿐**임을 회귀 테스트로 고정한다(이전 배열 응답과 `content`를 비교).
- [ ] **응답 봉투** — 모든 응답이 `content`/`nextCursor`/`hasNext` 3필드이며, 커서 유무·`interval`·시장에 따라 형태가 갈리지 않는다.
- [ ] **첫 페이지** — 커서 없이 요청하면 최신 구간 최대 200개를 받고, `hasNext`·`nextCursor`로 "더 과거가 있음"이 표현된다(코인 `1m`·집계봉 각각).
- [ ] **이어받기** — 응답이 준 다음 커서로 재요청하면 **직전 페이지의 가장 오래된 봉 바로 앞에서** 이어지고, 두 페이지를 합친 결과에 `sourceTime` **중복이 0건·누락이 0건**이다. 커서 없이 넓은 범위를 한 번에 조회한 결과(상한 안일 때)와 집합·순서가 일치한다.
- [ ] **데이터 끝 경계** — 우리가 가진 가장 오래된 봉까지 페이징하면 `hasNext=false`·`nextCursor=null`이 오고, 그 이후 재요청해도 무한 루프가 생기지 않는다. **마지막 페이지가 정확히 200개일 때 빈 `content` 페이지가 1회 더 나오고 거기서 `hasNext=false`가 되는 동작**이 테스트로 고정된다(CANDLE-PAGE-007).
- [ ] **커서 상한 배타** — 이전 페이지 마지막(가장 오래된) 봉의 `sourceTime`을 커서로 넘겼을 때 그 봉이 다음 페이지에 다시 나오지 않는다.
- [ ] **읽기 상한 유지** — 커서를 준 요청도 한 번에 200개를 넘겨 반환하지 않는다(#155 결정 유지).
- [ ] **집계봉 기준점 이동** — 커서가 주어지면 `narrowRangeStart`의 역산 기준이 커서 위치로 옮겨가고, 커서 이전 구간의 버킷이 실제로 반환된다(커서 없이는 `subList`로 버려지던 구간). 단위 테스트로 검증한다.
- [ ] **공개 상한 우회 불가** — 어떤 커서 값으로도 주식의 미공개 분봉이 집계 결과에 섞이지 않는다. `READY` 세션 없음·09:01 이전·재생거래일 이후 `trading_date` 케이스가 커서 유무와 무관하게 013의 계약을 유지한다.
- [ ] **코인 캐시·위임 경계** — 커서가 `since` 워터마크 앞·뒤·정확히 그 위치일 때 각각 `sourceTime` 중복·누락이 0건이다. Redis 장애 시 전량 위임 폴백에서도 페이징이 동작한다.
- [ ] **주식 `1m`** — `cursor`를 보내도 400이 아니고 `hasNext=false`·`nextCursor=null`이며, 단일 재생 거래일 계약이 유지되고 과거 거래일로 넘어가지 않는다(CANDLE-PAGE-026).
- [ ] **커서 + `to` 동시 지정** — `to`가 무시되고 `cursor`가 상한이 되며 `from`은 하한으로 유효함이 테스트로 고정되고, 그 사실이 `docs/api-contracts.md`에 적힌다(CANDLE-PAGE-012).

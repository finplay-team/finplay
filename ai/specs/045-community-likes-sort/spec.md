# Spec: 커뮤니티 좋아요·인기순 정렬

> PRD 근거: 명시적 요구사항 ID 없음(신설) — 토스증권 벤치마킹에서 도출, 사용자 확정(2026-08-18). `ai/prd.md` COM-001("수익 인증 분류, 거래 첨부, 좋아요, 신고는 1차에서 제외한다", 869행)과 "1차 명시적 제외 범위" 절(273행, "수익 인증 게시물·좋아요·신고·대댓글")이 좋아요를 1차 제외 항목으로 명시하고, 267행은 "관리자 기능, 수익 인증·좋아요·신고·대댓글 ... 은 2026-08-04 현재도 구현되지 않았다"고 적어 이 spec 작성 시점까지 미구현 상태임을 코드로도 확인했다(`GET /api/community/posts` 응답·컨트롤러 어디에도 좋아요 관련 필드·엔드포인트가 없음, `ai/api-routes.md` 37행에 정렬 파라미터 없음).

## 개요

커뮤니티 게시물에 좋아요 기능을 추가하고, 게시물 목록 정렬을 최신순(기존, 기본값)과 인기순(좋아요 수 기준) 중에서 선택할 수 있게 한다. 인기순 정렬이 좋아요 수를 기준으로 계산되므로 두 요구사항은 의존관계이며, 하나의 spec으로 묶어 진행한다.

## 사용자 시나리오

- 로그인 사용자는 게시물에 좋아요를 표시하거나 취소한다. 게시물 하나에 회원 1인당 좋아요는 최대 1개다.
- 사용자는 본인이 작성한 게시물에도 좋아요를 표시할 수 있다.
- 게시물 조회 응답(목록·단건)에는 그 게시물이 받은 좋아요 총 개수와, 요청자 본인이 좋아요를 표시했는지 여부가 함께 나온다.
- 사용자는 게시물 목록을 조회할 때 정렬 기준을 최신순(생략 시 기본값) 또는 인기순(좋아요 많은 순) 중에서 고른다.
- 사용자는 정렬 기준과 종목 필터(`instrumentId`, COM-004)를 함께 사용할 수 있다.

## 요구사항

### LIKE-001 좋아요 표시·취소

- [ ] 로그인 사용자는 게시물에 좋아요를 표시(`POST`)하거나 취소(`DELETE`)할 수 있다.
- [ ] 게시물 하나에 회원 1인당 좋아요는 최대 1개다.
- [ ] 본인이 작성한 게시물에도 좋아요를 표시할 수 있다 (근거는 "비즈니스 규칙" 참고).
- [ ] 이미 좋아요한 상태에서 다시 표시를 요청하면 오류 없이 현재 상태를 반환한다(멱등).
- [ ] 좋아요한 적 없는 상태에서 취소를 요청해도 오류 없이 처리한다(멱등).
- [ ] 존재하지 않는 게시물에 좋아요 표시·취소를 요청하면 404.

### LIKE-002 좋아요 개수·표시 여부 노출

- [ ] 게시물 목록·단건 조회 응답에 그 게시물의 좋아요 총 개수를 포함한다.
- [ ] 게시물 목록·단건 조회 응답에 요청자 본인이 좋아요를 표시했는지 여부를 포함한다.
- [ ] 좋아요는 게시물에만 적용한다 — 댓글·대댓글 조회 응답에는 좋아요 관련 필드를 추가하지 않는다.

### SORT-001 목록 정렬 전환

- [ ] `GET /api/community/posts` 조회 시 정렬 기준을 최신순 또는 인기순 중에서 선택할 수 있다.
- [ ] 정렬 기준을 지정하지 않으면 기존과 동일하게 최신순으로 동작한다(하위 호환 — 기존 클라이언트는 변경 없이 그대로 동작해야 한다).
- [ ] 인기순은 좋아요 개수 내림차순이다. 좋아요 개수가 같으면 최신 게시물이 먼저 나온다(동률 처리).
- [ ] 지원하는 값 외의 정렬 기준을 지정하면 400.
- [ ] 정렬 기준은 종목 필터(`instrumentId`)와 함께 사용할 수 있다 — 필터링된 결과 안에서 정렬만 바뀐다.

## 비즈니스 규칙

- **본인 게시물에도 좋아요를 허용한다.** 회원당 게시물 1개당 최대 1회로 이미 상한이 있어 자기 좋아요로 얻는 이득이 "그 게시물을 읽은 회원이 한 명 더 있는 것"과 실질적으로 다르지 않다. 요구되지 않은 차단 로직을 추가하지 않는다. 이 spec의 좋아요는 보상·랭킹과 연결하지 않는다 — 그 전제가 바뀌면(좋아요에 보상·랭킹을 연동) 이 판단도 다시 검토해야 한다.
- 게시물 삭제 시 그 게시물의 좋아요 데이터도 함께 제거한다(고아 데이터 방지 — COM-006 이미지 삭제와 동일 원칙).
- 좋아요 개수가 정렬 기준으로 쓰이므로, 회원당 상한(게시물당 1개)이 실제로 지켜져야 정렬 결과가 조작되지 않는다 — 애플리케이션 로직뿐 아니라 DB 유니크 제약으로도 강제한다.
- 댓글·대댓글에는 좋아요를 적용하지 않는다 — 이 spec의 대상이 아니다(범위 제외 항목이 아니라 애초에 다루지 않는 대상).

## 범위 제외

- 신고 기능. PRD가 좋아요와 신고를 같은 문장에서 1차 제외로 묶어뒀지만, 이 spec은 좋아요·정렬만 다룬다.
- 댓글·대댓글 좋아요.
- 좋아요를 누른 회원 목록 조회(누가 좋아요했는지 노출하는 API).
- 좋아요 발생 시 알림. NOTI 계열은 3차 MVP로 이동된 상태이며 이 spec에서 연동하지 않는다.
- 정렬 기준 추가(댓글 많은 순 등) — 최신순·인기순 2종만 다룬다.
- 프론트엔드 정렬 토글·좋아요 버튼 UI — 별도 레포(`finplay-frontend`) 작업.

## 완료 조건

- [ ] 로그인 사용자가 다른 회원 게시물에 좋아요를 표시 → 응답의 좋아요 개수가 1 증가하고 본인 표시 여부가 true로 바뀐다.
- [ ] 같은 사용자가 같은 게시물에 다시 좋아요를 요청 → 오류 없이 동일한 상태(개수 불변, 본인 표시 여부 true)를 반환한다.
- [ ] 좋아요를 취소 → 개수가 1 감소하고 본인 표시 여부가 false로 바뀐다.
- [ ] 좋아요한 적 없는 상태에서 취소를 요청 → 오류 없이 처리된다(204).
- [ ] 사용자가 본인 게시물에 좋아요를 표시 → 정상 처리된다(차단되지 않음).
- [ ] 존재하지 않는 게시물에 좋아요 표시·취소를 요청 → 404.
- [ ] 좋아요 개수가 서로 다른 게시물 여러 개를 만들고 인기순으로 조회 → 좋아요 많은 순으로 반환된다.
- [ ] 좋아요 개수가 같은 게시물들을 인기순으로 조회 → 최신 게시물이 먼저 나온다(동률 처리).
- [ ] 정렬 기준을 생략하고 조회 → 기존과 동일하게 최신순으로 반환된다(회귀 확인).
- [ ] 정렬 기준과 종목 필터를 함께 지정해 조회 → 그 종목이 태그된 게시물만 지정한 정렬로 반환된다.
- [ ] 지원하지 않는 정렬 기준 값을 지정 → 400.
- [ ] 게시물을 삭제 → 그 게시물에 달렸던 좋아요 데이터도 함께 제거된다(고아 행 없음).

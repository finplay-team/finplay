# Spec: 주식 일봉 3년치 아카이브 수집

- 대응 이슈: [#506](https://github.com/finplay-team/finplay-backend/issues/506)
- 요구사항 ID: MKT-011 (`ai/prd.md`)
- 차수: 2차 고도화(3차 MVP)

## 개요

주식 차트의 일봉·주봉·월봉(MKT-009)은 지금 `stock_candles`(1분봉)을 **조회 시점에 집계**해서 만든다(`StockCandleAggregator`). 그래서 **일봉 차트의 깊이가 1분봉 보관 기간에 그대로 묶여 있다** — MKT-005가 1분봉을 최근 20영업일만 보관하므로 정책대로면 일봉은 최대 20개, 주봉 4~5개, 월봉 1~2개다. 장기 추세를 볼 수 있는 차트가 아니다.

KIS **국내주식기간별시세**로 최근 3년치 일봉을 **별도 테이블**에 수집·보관해 장기 차트에 필요한 데이터 깊이를 확보한다.

**이 spec은 수집과 저장까지다.** 캔들 조회 API를 이 아카이브에 연결하는 일은 재생 모델의 공개 상한과 충돌하는 결정이 선행돼야 해서 후속으로 분리했다(§범위 제외).

## 두 데이터의 구분 (이 spec을 읽기 전에 먼저 볼 것)

주식 캔들 데이터는 이제 **성격이 다른 둘**이 된다. 문서·코드·화면에서 섞어 부르지 않는다.

| | 1분봉 (`stock_candles`) | 일봉 아카이브 (이 spec) |
|---|---|---|
| 봉 단위 | 1분 | 1일 |
| 목적 | **재생(replay)** — 과거 어느 거래일을 오늘 09:00~15:30에 다시 트는 원본 (MKT-002) |  **장기 차트 조회** — 실제 달력 날짜의 과거 추세 |
| 수집 엔드포인트 | `inquire-time-dailychartprice` (`FHKST03010230`) | `inquire-daily-itemchartprice` (`FHKST03010100`) |
| 수집 범위 | 직전 영업일 하루치 | 최초 3년 전량 + 이후 일 1건 증분 |
| 보관 기간 | **최근 20영업일** (MKT-005, 롤링 윈도우) | **최근 3년** (누적 아카이브) |
| 삭제 | 20영업일 초과분 정리 대상 (이슈 #83) | 3년 초과분만 정리 대상 |

**20영업일 보관 정책은 1분봉에만 적용된다.** 이 spec은 그 정책을 바꾸지 않는다 — 3년치 1분봉을 보관하는 것이 아니다(16종 × 390분 × 750일 ≈ 468만 행이며, 재생 모델에 그만한 깊이가 필요하지도 않다).

## 사용자 시나리오

- 운영자는 최초 1회 전량 적재를 트리거해 주식 종목의 최근 3년치 일봉을 적재할 수 있다.
- 서버는 매 영업일 1회 직전 영업일 일봉을 종목별 1건씩 자동으로 덧붙인다.
- 한 종목의 수집이 실패해도 나머지 종목의 적재는 그대로 완료된다.
- (후속 spec) 회원은 주식 차트를 3년 범위까지 과거로 넘겨볼 수 있다.

## 요구사항

- [ ] **STOCK-DAILY-001** 수집 경로는 KIS 국내주식기간별시세(`inquire-daily-itemchartprice`, `tr_id=FHKST03010100`, 일봉 구분)다. 기존 1분봉 수집 경로(`FHKST03010230`)를 **대체하지 않고 병존**한다 — 재생용 1분봉 수집은 그대로 돈다.
- [ ] **STOCK-DAILY-002** 1회 호출 반환 건수에 상한이 있으므로, 조회 구간을 **날짜 커서로 역방향 분할**해 연속 호출하고 이어붙인다. 응답이 비거나 커서가 진행하지 않으면 중단하며, 무한 루프를 막는 페이지 수 상한을 둔다.
- [ ] **STOCK-DAILY-003** 수집 대상은 `instruments`의 `market=STOCK`인 종목이다.
- [ ] **STOCK-DAILY-004** 보관 기간은 **최근 3년**이다(영업일 기준 약 750건/종목).
- [ ] **STOCK-DAILY-005** 일봉은 **별도 테이블**에 저장하고 `stock_candles`에 넣지 않는다. 두 테이블은 보관 정책이 반대이므로(20영업일 삭제 vs 3년 누적) 같은 테이블에 두면 1분봉 정리 작업(이슈 #83)이 아카이브를 지운다.
- [ ] **STOCK-DAILY-006** `UNIQUE(instrument_id, trading_date)`로 동일 일봉의 중복 저장을 막는다. 배치를 재실행해도 중복되지 않는다(멱등).
- [ ] **STOCK-DAILY-007** 최초 전량 적재는 **수동 트리거로 1회**, 이후에는 **일 1회 증분**(직전 영업일)이다. 이미 저장된 과거 일봉은 다시 조회하지 않는다.
- [ ] **STOCK-DAILY-008** 종목 단위로 실패를 격리한다 — 한 종목의 수집 실패가 다른 종목의 적재를 막지 않는다.
- [ ] **STOCK-DAILY-009** KIS 레이트리밋(초당 호출 제한)에 대응한다. 기존 1분봉 클라이언트가 이미 가진 재시도 정책을 재사용하고, 종목 간 호출에도 간격을 둔다.
- [ ] **STOCK-DAILY-010** 수집 시도 이력(성공·부분성공·실패, 실패사유, 수집시각)을 기록한다. 저장에 실패한 경우도 남긴다.
- [ ] **STOCK-DAILY-011** 다중 인스턴스에서 같은 배치가 겹쳐 돌지 않는다 — 기존 수집 락(`StockCollectionLock`)을 재사용한다.
- [ ] **STOCK-DAILY-012** 자동 테스트는 **Fake 클라이언트**를 사용한다. 실제 KIS Open API 호출 검증은 외부 스모크로 **구분해 보고**한다 (C-005).

### 착수 시 확인할 항목 (Decision Gate)

- [ ] **수정주가 처리.** 3년 구간에는 액면분할·병합이 들어갈 수 있어 원주가 그대로면 차트에 인위적인 급등락이 생긴다. KIS 응답의 수정주가 옵션(`FID_ORG_ADJ_PRC`) 의미를 **실제 호출로 확인한 뒤** 어느 값을 저장할지 정한다. 확인 전까지 임의로 확정하지 않는다 — MKT-005가 분봉 timestamp 기준에서 같은 방식으로 처리한 선례를 따른다.
- [ ] **응답 필드명.** `output2`의 일봉 필드명(일자·시가·고가·저가·종가·거래량)을 실제 호출 1회로 확인하고 매핑을 확정한다.

## 비즈니스 규칙

- **과거 일봉은 확정된 기록이다.** 한 번 저장한 거래일의 일봉은 수정·재수집하지 않는다. 같은 거래일이 다시 들어오면 기존 행을 바꾸지 않는다.
- 가격은 `BigDecimal`, 거래량은 정수로 다룬다 — `double`·`float`를 쓰지 않는다 (C-003).
- 원본 응답을 그대로 내려주거나 다운로드하게 하지 않는다. 정규화된 일봉 필드만 저장·노출한다 (C-006).
- KIS 과거 데이터는 공공데이터로 확인되어 제3자 표출에 별도 서면 허가가 필요하지 않다 (C-006). **C-007의 Decision Gate는 실시간 시세 한정이므로 이 spec의 대상이 아니다.**

## 범위 제외

- **캔들 조회 API 연결.** `1d`·`1w`·`1M`의 데이터 소스를 이 아카이브로 바꾸는 것은 이번 범위가 아니다. 주식은 과거 거래일을 재생하는 구조라 집계 캔들에 **공개 상한**이 걸려 있는데(`StockReplayService` — `sourceTradingDate` 이후 거래일을 내려주지 않는다), 실제 달력 기준 3년치를 그대로 붙이면 **재생 중인 "오늘"의 미래 봉이 노출된다.** 이 시간축 결정이 선행돼야 한다 — 이슈 [#506](https://github.com/finplay-team/finplay-backend/issues/506) 결정 1·2, 이슈 #495(주식 `1m` 시간축)와 같은 계열이다.
- **1분봉 보관 정책 변경.** `stock_candles`의 20영업일 롤링 윈도우는 그대로 둔다(MKT-005).
- **코인 일봉.** 계속 빗썸 위임이다(MKT-009). 이 spec은 주식만 다룬다.
- **3년보다 과거 구간**, 상장폐지·거래정지 종목의 특수 처리, 3년 초과분 정리(cleanup) 배치 — 3년치가 쌓이기 전에는 삭제 대상이 생기지 않는다.
- 실시간 시세 (C-007, 여전히 범위 밖).

# ADR-0017: 코인 변동 카드의 근거 기사는 CryptoPriceMoveWatcher가 매칭 실패 시 온디맨드로 수집한다

- 상태: 승인됨
- 날짜: 2026-08-10
- 관계: 이슈 #285. `ai/specs/012-ai-feedback` FEED-003·005의 "근거가 없으면 카드를 만들지 않는다" 규칙은 그대로 두고 §뉴스 매칭 범위·§C-1 수집 계약의 빈틈(30분 수집 주기 vs 매 분 탐지)을 메운다. ADR-0014(코인 감시 Redis 락)의 락 범위를 확장한다. ADR-0002(레이어 구조)를 따르며 `com.finplay.api.feedback` 패키지 안에서 해결한다.

## 맥락

코인 뉴스 수집은 `feedback.news.collect-cron`(`0 0/30 * * * *`)으로 30분마다 돌고, 코인 감시는 `feedback.batch.crypto-watch-cron`(`30 * * * * *`)으로 매 분 돈다. **탐지가 수집보다 30배 빠르다.** 그래서 변동이 터진 직후에는 관련 기사가 아직 `market_news_items`에 없는 것이 정상이고, 그 시각에 탐지된 카드는 `NewsMatcher.matchCrypto`가 근거 0건을 돌려주는 순간 `CryptoPriceMoveWatcher.watchOne()`이 그냥 버린다.

근거 없는 문장을 만들지 않는다는 규칙(FEED-003) 자체는 옳다. 문제는 **기사가 세상에 없어서 0건인 경우**와 **기사는 있는데 아직 DB에 안 들어와서 0건인 경우**를 구분하지 못한다는 것이다. `crypto.match-before-minutes`(35분)로 근거창을 넓혀도 "마지막 수집 이후 발행된, 실제로 변동을 설명하는 기사"는 여전히 없다 — 오히려 변동과 무관한 30분 전 기사가 근거로 붙을 여지만 생긴다.

튜터 피드백 "체결가가 일정 % 변하면 **그 시점에** 뉴스를 끌어와 붙이기"의 "그 시점에" 부분이 아직 구현돼 있지 않다. 탐지(이슈 #225, PR #236)는 이미 있다.

이 경로는 **조회 경로가 아니라 배치 경로**라 사용자가 응답을 기다리지 않는다 — 네이버 API 호출 1~2초가 응답 지연으로 드러나지 않는다(ADR-0015가 조회 경로 캐시에서 fail-open을 택한 것과 반대 방향의 같은 구분). 호출량도 z-score 게이트 → 락 → 쿨다운 → 일일 상한을 **전부 통과한 뒤에만** 발생하므로 `feedback.crypto.daily-limit`(6) × 코인 종목 수로 상한이 걸린다.

`NewsMatcher` 클래스 주석은 "이미 저장된 기사를 읽기만 한다. 수집기·수집 크론·질의어·제목 필터를 알지 못한다"고 명시적으로 선언하고 있다. 이 경계를 지키면서 온디맨드를 붙일 자리를 골라야 한다.

## 결정

**`CryptoPriceMoveWatcher.watchOne()`이 근거 매칭이 비어 있을 때 수집을 직접 트리거하고 한 번 재매칭한다. `NewsMatcher`는 손대지 않는다.**

1. **위치**: `NewsMatcher`는 "저장된 것만 읽는다"는 선언을 그대로 유지한다. 주식 경로(`match()`)는 이 변경의 영향을 받지 않는다. 온디맨드 트리거는 `CryptoPriceMoveWatcher`에 둔다 — 이 클래스는 이미 "탐지·쿨다운·근거 매칭·서술·저장을 전부 담는다"고 선언돼 있어(재생 시간축·개장 전 배치가 없어 별도 확정 서비스로 쪼갤 경계가 없다), "필요 시 수집을 트리거한다"를 더하는 것이 그 선언의 자연스러운 연장이다.
2. **새 메서드**: `NewsCollectionService`에 종목 하나만 수집하는 메서드(가칭 `collectForInstrument(Instrument instrument)`)를 추가한다. 기존 `collectNews()`의 종목별 루프 본문(제목 필터용 `sameMarketNames` 조립 → `newsCollector.collect(...)` → `save(...)`)을 종목 하나에 대해 그대로 재사용한다. `sameMarketNames`는 `instrumentService.getInstrumentEntities(Market.CRYPTO)`로 같은 시장 전체 이름을 조립한다 — 배치와 같은 제목 필터링 규칙을 유지해야 온디맨드로 수집된 기사도 같은 오염 방지가 적용된다.
3. **흐름**: `watchOne()`은 락 획득 → 쿨다운 → 일일 상한 → **첫 매칭** → 비어 있으면 `collectForInstrument` 호출 → **재매칭(1회만)** → 그래도 비어 있으면 카드를 만들지 않고 종료(FEED-003 그대로). 재시도를 1회로 제한하는 이유는, 이번 호출로도 못 찾으면 그 시각 기사가 정말 없다고 보는 것이 합리적이고 — 다음 분 감시 틱이 다시 열려 있어 이번 틱에서 반복할 이유가 없기 때문이다.
4. **락 범위 확장 (ADR-0014 갱신)**: 온디맨드 수집·재매칭은 Redis 락을 쥔 상태(쿨다운 확인 이후 ~ 저장 이전)에서 일어난다. ADR-0014가 "락 범위는 쿨다운 확인 → 일일 상한 확인 → 뉴스 근거 매칭 → LLM 호출 → 카드 저장까지"라고 명시한 것에 **"필요 시 온디맨드 수집"이 매칭과 재매칭 사이에 추가된다.** TTL(45초)은 바꾸지 않는다. 이 두 호출은 락 안에서 독립적으로 비교할 대상이 아니라 **순차로 더해진다** — 첫 매칭이 비면 온디맨드 수집(네이버 API 타임아웃 연결 5초 + 읽기 10초, 최악 15초)이 먼저 끝난 뒤에야 LLM 호출(타임아웃 20초)이 시작된다. 최악 경로는 **15초 + 20초 = 35초 ≤ TTL 45초, 여유 10초**다. 매칭이 처음부터 성공하는 경로(온디맨드 수집 없음)는 기존 여유(25초, LLM 타임아웃 기준 약 2배)가 그대로 유지된다 — 줄어드는 것은 온디맨드 수집이 실제로 트리거되는 경로뿐이다.
5. **실패 처리는 새 코드가 필요 없다.** `NaverNewsCollector.collect`는 실패 시 예외 대신 빈 목록을 돌려주는 기존 계약을 그대로 따르고, `watch()`의 종목별 `try/catch(RuntimeException)`(기존 코드, `watch()` 105행 근방)이 이미 그 종목만 건너뛰고 나머지를 계속하는 것을 보장한다. `collectForInstrument`가 새 예외를 던지지 않는 한 이 방침이 그대로 적용된다.
6. **중복 저장 방지도 새 메커니즘이 필요 없다.** `market_news_items`의 `UNIQUE(instrument_id, url)` 제약과 `NewsCollectionService.save()`의 기존 URL 조회·대조 로직을 그대로 타므로, 온디맨드로 저장한 기사를 30분 뒤 배치가 다시 가져와도 중복 행이 생기지 않는다.
7. **본문 미저장·공시 미매칭**은 기존 `collect()`·`matchCrypto()` 계약이 이미 지키고 있어 그대로 상속된다(C-004, §C-3) — 새로 막을 것이 없다.

## 결과

**좋은 점**

- 매칭 실패 시에만, 게이트를 다 통과한 뒤에만 호출되므로 호출량이 통제된 상태를 유지한다(일일 상한 × 종목 수로 상한이 그대로 걸린다).
- `NewsMatcher`와 주식 경로가 전혀 바뀌지 않아 영향 범위가 최소화된다.
- 기존 실패 격리·중복 방지·본문 미저장 방침을 그대로 재사용해 새로 검증할 안전장치가 거의 없다.
- 근거창 확대라는 완화책이 아니라 "탐지가 수집보다 30배 빠르다"는 구조적 간극 자체를 좁힌다.

**받아들이는 대가**

- `CryptoPriceMoveWatcher`가 `NewsCollectionService`(수집기)를 새로 알게 된다 — 탐지기와 수집기 사이에 새 결합이 생긴다. 클래스 주석의 "탐지·쿨다운·근거 매칭·서술·저장을 전부 담는다"는 선언에 "필요 시 수집 트리거"가 추가된다.
- Redis 락 보유 시간이 늘어난다 — 매칭 실패 시 네이버 API 호출(최악 15초)이 락 구간 안에 들어간다. 그 시간 동안 다른 인스턴스는 같은 종목만 못 건드리고(종목 단위 락, ADR-0014) 다른 11종목 감시는 막히지 않는다.
- 네이버 API 호출량이 늘어난다 — 기존 30분 배치(코인 종목 수 × 1회/30분)에 온디맨드(최대 일일 상한 × 종목 수)가 더해진다. 일일 총량이 상한 안에 드는지는 배포 전 계산이 필요하다(§후속).

## 대안과 기각 사유

**(a) `NewsMatcher` 안에서 수집 호출**

"이미 저장된 기사만 읽는다"는 명시적 선언을 정면으로 깬다. 주식 경로(`match()`)도 같은 클래스를 쓰므로 온디맨드와 무관한 주식 카드 생성 경로까지 영향권에 든다. 매처가 "무엇을 언제 수집할지"까지 판단하게 되면 §C-2(근거창)와 §C-1(수집 정책)의 책임이 한 클래스에 섞인다. 기각.

**(b) 새 협력자 클래스 신설**

기존 두 클래스를 안 건드려 ADR이 필요 없다는 장점이 있다. 그러나 이 클래스를 쓰는 소비자는 `CryptoPriceMoveWatcher` 하나뿐이다. ADR-0014·0015가 이미 "소비자가 하나뿐이면 일반화하지 않는다(YAGNI)"는 기준을 반복 적용해 왔다(`CryptoWatchLock` 신설 시점, `RedisLock` 추출을 실제 두 번째 소비자가 생긴 뒤로 미룬 것). 여기서 다른 기준을 쓸 이유가 없다. 사실상 결정 2·3의 오케스트레이션 코드를 별도 파일로 옮기는 것에 가까워 결합은 그대로 남고 클래스만 하나 는다. 기각.

**(c) 이번 이슈에서는 손대지 않고 `crypto.match-before-minutes`(근거창)만 더 넓힌다**

이슈 본문이 이미 기각한 안이다. "마지막 수집분"은 포함되지만 수집 이후 발행된, 변동을 실제로 설명하는 기사는 여전히 없고, 오히려 변동과 무관한 과거 기사가 근거로 붙을 여지만 생긴다. 기각.

## 후속

- 재시도 1회 제한이 실무에서 부족하면(네이버 색인 지연이 재매칭 시점을 넘는 경우) 조정 여지를 남긴다 — 이 값은 실측이 아니라 추정이므로 배포 후 카드 생성 성공률을 보고 재검토한다.
- 네이버 API 일일 호출량이 배치 + 온디맨드 합산으로 상한을 넘지 않는지 배포 전 계산해 이 ADR 또는 `ai/specs/012-ai-feedback/spec.md`에 실측치를 남긴다.
- `ai/prd.md` §3 FEED-005·006 코인 분기 행은 구현이 끝나는 커밋에서 갱신한다(CLAUDE.md 규칙 10) — 이 ADR 자체는 갱신 대상이 아니다.

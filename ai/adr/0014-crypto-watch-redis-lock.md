# ADR-0014: 코인 변동 감시의 다중 인스턴스 중복 방지는 Redis 분산 락으로 한다

- 상태: 승인됨 — 락 범위는 [ADR-0017](0017-crypto-news-ondemand-collection.md)(§결정4)이 "근거 매칭 → 필요 시 온디맨드 수집 → 재매칭" 구간을 추가해 확장한다. 그 외 결정은 유효.
- 날짜: 2026-08-06
- 관계: `ai/specs/012-ai-feedback` §탐지 알고리즘(코인)·§C-9의 구현을 구체화한다. 이슈 #244. ADR-0002(레이어 구조)를 따르며 기존 `com.finplay.api.feedback` 패키지 안에서 해결한다.

## 맥락

`CryptoPriceMoveWatcher.watch()`는 매 분 코인 12종목을 감시해 임계치를 넘으면 카드를 만든다. 지금은 서버 1대라 Spring `@Scheduled` cron이 같은 메서드의 겹침을 프레임워크 차원에서 막아준다(실측·소스 확인 완료 — 이슈 #244 1단계). **다중 인스턴스 전환이 예정돼 있고**, 전환 순간 이 보장이 사라진다.

두 인스턴스가 같은 분에 같은 코인의 임계치 초과를 동시에 감지하면.

1. 둘 다 쿨다운·일일 상한을 확인하는데 아직 카드가 없어 **둘 다 통과**한다.
2. 둘 다 뉴스 근거를 매칭하고 **LLM을 호출**한다 — 비용이 두 배로 나간다.
3. 둘 다 저장하는데 코인 카드는 `window_start`가 `NULL`이라 `UNIQUE(instrument_id, origin_trade_date, event_type, window_start)`가 MySQL의 NULL 비교 특성상 걸리지 않는다(실측 확인 완료, `PriceMoveEventRepositoryTest`) — **중복 카드가 남는다.**

이 저장소의 기존 동시성 제어는 전부 **DB 비관적 락**이다(`AccountRepository`·`OrderRepository`·`HoldingRepository`·`PracticeProgressRepository`). DB 락은 다중 인스턴스에서도 유효하지만(DB는 공유 자원이다) **저장 시점 이후만 막는다** — LLM 호출은 그 전에 이미 양쪽에서 일어난 뒤라 비용 중복은 못 막는다.

**LLM 호출 비용까지 막으려면 저장 훨씬 이전, 즉 쿨다운을 확인하기 전에 잠가야 한다.** 여러 인스턴스가 동시에 봐야 하는 시점의 락이라 DB 락(그 시점엔 잠글 행이 없다 — 카드가 아직 안 만들어졌다)이 아니라 **인스턴스 간 공유 상태**가 필요하다. Redis는 이미 이 저장소에 있다(`PriceStore` — 코인 최신 시세·수신시각·연결상태). 다만 **락 용도로 쓴 적은 없다** — 이 결정이 새 용도를 여는 것이라 ADR 대상이다(CLAUDE.md 규칙 2).

## 결정

**`CryptoPriceMoveWatcher.watchOne()`이 임계치 게이트(z-score)를 통과한 직후 — 쿨다운을 확인하기 전 — 종목 단위로 Redis 락을 얻는다. 얻지 못하면 그 종목은 이번 틱을 건너뛴다(대기하지 않는다).**

- **락 키**: `feedback:crypto-watch:lock:{instrumentId}`. 종목별로 독립적이라 한 종목의 처리가 다른 종목을 막지 않는다.
- **락 범위**: 쿨다운 확인 → 일일 상한 확인 → 뉴스 근거 매칭 → LLM 호출 → 카드 저장까지 전부 감싼다. 얻지 못한 인스턴스는 이미 다른 인스턴스가 이 종목을 처리 중이라고 보고 조용히 넘어간다 — 이번 분을 놓쳐도 다음 분에 다시 감시하므로 재시도 대기열이 필요 없다.
- **구현은 Redisson 등 새 라이브러리를 추가하지 않고 기존 `StringRedisTemplate`(`spring-boot-starter-data-redis`, 이미 의존성에 있음)로 직접 만든다.**
  - 획득: `SET key value NX PX ttl` 한 번의 원자적 명령(`opsForValue().setIfAbsent(key, token, ttl)`). `token`은 호출마다 새로 만드는 임의 문자열(예: `UUID.randomUUID()`)로, 이 인스턴스·이 시도가 건 락임을 식별한다.
  - 해제: 저장한 `token`이 지금도 이 키의 값과 같을 때만 지운다(Lua 스크립트로 GET-비교-DEL을 원자적으로 묶는다 — "check-then-delete"가 두 명령이면 그 사이에 TTL 만료 후 다른 인스턴스가 잡은 락을 지울 수 있다).
  - TTL은 `feedback.crypto.watch-lock-ttl-seconds`(신설, 기본값 45) — LLM 호출 p95 3.12초·최대 4.06초(#198 실측)는 평상시 기준이고, `feedback.llm.timeout-seconds`(20)가 락 안에서 걸릴 수 있는 실제 최악 시간이다. TTL을 그 최악값의 약 2배(여유 25초)로 잡아 뉴스 매칭·DB 쓰기까지 더해도 충분한 여유를 두면서, 인스턴스가 락을 쥔 채 죽어도 45초 뒤엔 스스로 풀려 특정 코인이 영구히 막히지 않는다.
- **위치**: `com.finplay.api.feedback.service.CryptoWatchLock` 하나만 새로 만든다. 이 이슈의 유일한 소비자이므로 범용 `DistributedLockService`로 미리 일반화하지 않는다(YAGNI) — 재사용이 실제로 필요해지면(예: #245) 그때 추출한다.
- **spec 갱신**: `ai/specs/012-ai-feedback/spec.md`의 "코인 카드의 중복을 실제로 막는 것은 유니크가 아니라 쿨다운·일일 상한이다" 문장을 "다중 인스턴스에서는 Redis 락(§ADR-0014)이 우선 방어선이고, 쿨다운·일일 상한은 그 다음 방어선이다"로 갱신한다.

## 결과

**좋은 점**

- LLM 호출 자체가 중복되지 않는다 — 카드뿐 아니라 **비용**을 막는다. (a) DB 락이나 (b) 유니크 수정 단독으로는 못 막는 부분이다.
- 새 인프라(Redis)를 추가하는 게 아니라 이미 있는 것의 용도를 하나 늘리는 것이라 배포 구성 변경이 없다.
- 종목 단위 락이라 한 종목의 LLM 호출이 오래 걸려도 다른 11종목의 감시를 막지 않는다.

**받아들이는 대가**

- **이 저장소 동시성 제어의 첫 Redis 락 사례**가 된다 — DB 비관적 락과 패턴이 하나 늘어난다. 다음에 비슷한 문제를 만나는 사람이 "왜 여기는 DB 락이 아니라 Redis인가"를 물을 수 있어 이 ADR과 §후속의 판단 기준(비용 절감이 목적일 때만)을 남긴다.
- Redis가 죽어 있으면 `setIfAbsent`가 예외를 던진다. **락 획득 실패로 처리해 그 틱을 건너뛴다** — 코인 감시 전체가 죽지 않게 하되, Redis 장애 중에는 카드 생성이 전부 멈춘다(원장에는 영향 없음, 부가 기능이므로 허용 범위로 판단).
- 단일 Redis 인스턴스 기준 락이다 — Redis 자체를 다중화(센티널/클러스터)하면 페일오버 순간의 락 유실 가능성이 이론상 있다(Redlock 알고리즘이 다루는 문제). **이 저장소는 Redis도 단일 인스턴스**이므로 지금은 해당 없고, Redis를 다중화하는 시점에 재검토 대상으로 남긴다.
- TTL 이후 락이 스스로 풀리므로, 만약 처리가 TTL(45초)보다 오래 걸리면 다른 인스턴스가 같은 종목을 다시 시작할 수 있다. 락 안에서 도는 LLM 호출의 타임아웃(`feedback.llm.timeout-seconds`, 20초)이 최악 시간이므로 TTL과의 실질 여유는 약 2배(25초)다 — 평상시 처리 시간은 수 초라 대부분의 경우 여유가 훨씬 크고, 최악 기준 2배도 실무적으로는 충분하다고 판단했다.

## 대안과 기각 사유

**(a) DB 비관적 락** (`InstrumentRepository.findByIdForUpdate`, 이 저장소의 기존 방식)

새 인프라가 없고 선례가 많다. 그러나 **잠글 대상(카드 행)이 저장 시점 전에는 존재하지 않아**, 종목 행을 대신 잠그더라도 그 시점은 이미 카드를 만들기로 결정한 뒤(쿨다운·일일 상한 통과 후)이거나, 더 일찍 잠그려면 종목 행에 임계치 계산·근거 매칭·LLM 호출까지 걸리는 긴 트랜잭션을 얹어야 한다 — DB 커넥션을 초 단위로 점유하는 것은 이 저장소의 다른 락 사용 패턴(계좌 잔액 갱신처럼 밀리초 단위)과 성격이 다르다. 무엇보다 **LLM 중복 호출을 막지 못한다**는 것이 결정적 기각 사유다.

**(b) 유니크 제약을 실제로 걸리게 만든다** (코인 `window_start`에 값 채우기, #180 패턴)

마이그레이션 하나로 끝나 가장 가볍다. 그러나 **저장 시점에만 작동해 LLM 중복 호출을 막지 못하고**, spec §C-9(코인은 `window_start` NULL — 자정 넘김 문제 회피)와 정면 충돌해 그 근거 자체를 다시 검토해야 한다. (a)와 조합하면 #180과 같은 이중방어가 되지만, 두 방식 다 LLM 비용 문제를 놓친다는 점은 그대로다.

**(a)+(b) 조합**

이 저장소의 기존 패턴과 완전히 일치하고 새 인프라가 없다는 장점은 있다. 그러나 위 두 기각 사유(LLM 비용 중복 미방지)가 조합해도 사라지지 않는다. **다중 인스턴스 전환의 목적이 트래픽·비용 분산인데, 그 인스턴스들이 같은 LLM 호출을 중복으로 내는 것은 전환의 이점을 깎아먹는다**고 판단해 기각했다.

## 후속

- `feedback.crypto.watch-lock-ttl-seconds` 기본값(45)은 실측 근거가 아니라 여유 마진 추정이다. 다중 인스턴스 배포 후 실제 처리 시간을 재고 조정한다. **조정할 때는 `feedback.llm.timeout-seconds` 대비 하한을 함께 확인한다** — TTL이 그 값보다 작으면 LLM 호출이 타임아웃까지 가는 동안 락이 스스로 풀려 다른 인스턴스가 같은 종목을 다시 시작한다. 두 값이 서로 다른 record(`FeedbackCryptoProperties`·`FeedbackLlmProperties`)에 있어 기동 시점 교차 검증은 하지 않으므로(기동 검증은 `< 1`만 본다), 이 하한은 사람이 확인해야 한다.
- #245(요약·브리핑 캐시)가 같은 부류의 문제(캐시 만료 순간 요청 쏠림)를 다룬다. 여기서 만든 `CryptoWatchLock`을 그대로 재사용할지, 조회 경로 특성(빈도가 훨씬 높음)에 맞춰 별도로 설계할지는 #245에서 다시 판단한다 — 같은 방식을 강제하지 않는다.
- Redis 자체를 다중화하는 시점에 위 "받아들이는 대가"의 페일오버 유실 가능성을 재검토한다.

# ADR-0021: `dev` 머지 이후는 사람이 손대지 않는다 — GitHub Actions가 블루-그린 배포를 끝까지 수행한다

- 상태: 승인됨
- 날짜: 2026-08-12
- 관계: 이슈 #345. 배포 **실행 방식**의 정본. 배포 **아키텍처**는 [ADR-0020](0020-managed-service-deployment.md)이 정본이며 이 ADR은 그 구조를 바꾸지 않고 그 위에서 도는 파이프라인만 정한다. [ADR-0013](0013-issue-triggered-agent-harness.md) §범위 밖의 **"자동 배포" 제외를 대체한다** — 같은 줄에 묶여 있던 **"자동 머지" 금지는 대체하지 않고 그대로 유지한다**(그쪽은 같은 ADR §승인·머지가 실제로 결정한 것이다). [ADR-0005](0005-local-agent-orchestration.md)는 이 금지의 근거로 널리 인용돼 왔지만 **본문에 그런 문장이 없다** — §맥락 표 참고. 마이그레이션 제약은 [ADR-0004](0004-flyway-migrations.md)에 조건을 추가한다(§결정 7).

## 맥락

ADR-0020이 상태를 EC2 밖으로 빼고 블루-그린 구조를 결정했다. 인프라 파일(`compose.bluegreen.yaml`, `deploy/nginx-blue.conf`·`nginx-green.conf`)도 이슈 #332에서 작성됐다. **그런데 그것을 움직이는 것은 아직 전부 사람이다** — `deploy/README.md`의 절차는 EC2에 접속해 `docker compose ... up -d --build`를 치고, 헬스체크를 눈으로 확인하고, ALB 콘솔에서 리스너를 바꾸는 순서로 돼 있다.

### 블루-그린이 되면서 수동 배포의 성격이 바뀌었다

단일 스택 시절의 수동 배포는 명령 한 줄(`docker compose -f compose.deploy.yaml up -d --build`)이었다. 틀릴 자리가 거의 없었다.

블루-그린은 다르다. 사람이 매번 지켜야 하는 순서가 다섯 단계다.

1. 지금 **어느 색이 라이브인지** 확인한다 (이 정보는 ALB 리스너에만 있고, EC2에는 두 색이 동시에 떠 있을 수 있다)
2. 유휴 색을 새 코드로 기동한다
3. 유휴 색이 healthy가 될 때까지 기다린다
4. ALB 타깃 그룹을 전환한다
5. 이전 색을 **내리지 않고** 남긴다 (롤백 경로)

1번을 틀리면 라이브 색을 재기동하게 되고, 그 순간 무중단 배포가 아니라 **다운타임 있는 배포보다 나쁜 상태**(사용자 요청이 재기동 중인 스택으로 계속 흘러간다)가 된다. 3번을 건너뛰고 4번을 하면 아직 뜨지 않은 스택으로 트래픽을 넘긴다. 이 다섯 단계는 사람이 매번 정확히 반복하기에는 상태 의존적이고, **틀렸을 때의 대가가 사용자 요청 실패**다. 순서와 상태 판별은 기계가 더 잘하는 종류의 일이다.

### EC2에서 이미지를 만드는 것이 블루-그린과 맞지 않는다

`compose.bluegreen.yaml`의 두 색은 모두 `build: context: .`를 쓴다. 즉 각 색이 **그 시점 EC2 작업 디렉터리의 소스로 각자 빌드**한다. blue를 띄운 뒤 소스를 갱신하고 green을 띄우면 두 색은 서로 다른 빌드가 되고, "직전 색으로 롤백한다"가 정확히 무엇으로 돌아가는 것인지 아무도 특정할 수 없다. 롤백 대상은 **이름으로 지목할 수 있어야** 한다.

여기에 `t4g.small`(2GB)이라는 제약이 겹친다. `compose.bluegreen.yaml`이 이미 `-Xmx384m`으로 힙을 눌러 둔 것은 app 2벌 + nginx 2벌이 함께 뜨기 때문인데, 그 위에서 Gradle 빌드까지 돌린다.

### "자동 배포 금지"는 배포 위험 판단이 아니었다

자동 배포를 뺀 문서는 네 곳이지만, **그중 어디에도 "배포를 자동화하면 위험하다"는 판단은 없다.**

| 문서 | 적힌 것 | 실제 |
|---|---|---|
| ADR-0005 | (010 spec과 ADR-0013이 "자동 배포·자동 머지 금지"의 근거로 **인용**) | **이 문서 본문에는 "배포"도 "머지"도 나오지 않는다** (2026-08-12 확인, `grep -n "머지\|배포" docs/adr/0005-*.md`). 다룬 것은 API 키 없이 에이전트를 서버에서 돌릴 수 없다는 것이다 — **인용이 원문보다 넓었다** |
| ADR-0013 §범위 밖 | "자동 배포·자동 머지" | 이슈 트리거 **에이전트 하네스**의 범위 선언. 한 줄에 둘이 묶여 있다. 자동 머지 금지는 같은 문서 §승인·머지에서 **실제로 결정했다** |
| 010 spec §범위 제외 | "자동 배포·배포 파이프라인 (수동 배포로 시작)" | 1차 MVP를 최소 구성으로 띄우기 위한 범위 축소 |
| `deploy/README.md` | "배포 자동화(CI) — 수동 배포로 시작한다" | 위 spec을 옮겨 적은 것 |

**이 ADR은 그 한 줄을 둘로 나눈다.** 자동 머지 금지는 유지한다 — 사람이 코드를 보고 머지 버튼을 누르는 게이트는 그대로다. 바뀌는 것은 **그 버튼 이후**다: 지금까지는 머지 후에도 사람이 배포 절차를 다시 수행했고, 앞으로는 하지 않는다.

## 결정

**`dev`에 머지되면 GitHub Actions가 이미지 빌드부터 ALB 전환까지 수행한다. 사람의 개입 지점은 PR 머지 버튼 하나다.**

```
사람: PR 머지 (dev)
  │
  ▼  push: dev
[GitHub Actions — ubuntu-24.04-arm]
  ① ./gradlew bootJar
  ② 이미지 빌드 → ECR push (태그 = 커밋 SHA)
  ③ OIDC로 AWS IAM 역할 임시 자격 증명 획득
  │
  ▼  SSM Send Command (SSH 인바운드 없음)
[EC2 t4g.small]
  ④ 라이브 색 판별 → 유휴 색을 새 이미지로 기동
  ⑤ 컨테이너 헬스체크 통과 대기
  │
  ▼  ALB API
  ⑥ 유휴 색 타깃 그룹 healthy 확인 → 리스너 전환
  ⑦ 이전 색은 내리지 않고 남긴다 (다음 배포까지 롤백 경로)
                     │
                     └─ 실패 시: 전환하지 않고 새 색을 내린다 (§결정 6)
```

### 1. 트리거는 `dev` push다

`dev`가 이 팀의 통합 브랜치이자 모든 기능 PR의 대상이다(`docs/conventions/git.md`). `main`을 트리거로 삼으면 배포할 때마다 `dev → main` PR을 사람이 하나 더 만들어야 하고, 그것은 "머지 이후는 사람이 손대지 않는다"는 이 결정의 목적과 정반대다.

**대가를 명시한다 — `dev`에 들어간 것은 즉시 공개 URL에 뜬다.** 미완성 기능을 숨길 자리가 없다. 이 대가를 받아들이는 조건은 둘이다.

- CI(`.github/workflows/ci.yml`)가 `dev` 대상 PR에서 `./gradlew build`를 이미 게이트로 걸고 있다. 빌드·테스트가 깨진 코드는 머지 전에 걸린다.
- **노출 시점을 통제해야 하는 기능은 머지 시점으로 통제한다.** 배포 파이프라인에 승인 단계를 넣어 해결하지 않는다 — 그러면 사람이 눌러야 할 버튼이 다시 둘이 된다.

이에 맞춰 `main`의 역할을 다시 적는다. **`main`은 배포 소스가 아니라 시연·심사 시점의 스냅샷이다.** 배포되는 것은 항상 `dev`다 (`docs/conventions/git.md` 갱신).

### 2. AWS 자격 증명은 GitHub OIDC로 받는다 — 저장하지 않는다

러너는 장기 액세스 키 대신 **OIDC 토큰을 AWS IAM 역할로 교환**해 임시 자격 증명을 받는다. `conventions.md` 시크릿 규칙("실제 값은 환경변수 또는 AWS Secret에만")의 연장이다 — **저장하지 않는 크리덴셜이 가장 안전하다.**

신뢰 정책은 리포지터리가 아니라 **브랜치까지 못박는다.**

```
"token.actions.githubusercontent.com:sub":
  "repo:finplay-team/finplay-backend:ref:refs/heads/dev"
```

레포까지만 제한하면 **어떤 브랜치의 워크플로우든** 이 역할을 가져갈 수 있다. 이 레포는 공개(public)이므로 포크 PR에서 워크플로우 파일을 바꾼 코드가 돌 여지를 남기지 않는다 — 배포 워크플로우는 `pull_request` 트리거를 쓰지 않고 `push: dev`만 구독한다.

**그래도 남는 사실은 적어 둔다: 이 레포에 push 권한이 있는 사람은 사실상 배포 권한을 갖는다.** `dev` 브랜치 보호 규칙(PR 필수·승인 1명)이 이 권한의 실질적인 경계다.

### 3. EC2 명령 실행은 SSM Send Command다 — SSH를 열지 않는다

ADR-0020 §5는 "네트워크 경계는 보안 그룹 참조로 정의한다"고 결정했다. **GitHub Actions 러너의 IP는 고정이 아니므로 그 규칙과 SSH가 양립하지 않는다** — SSH로 배포하려면 22번을 넓은 대역으로 열거나 GitHub의 IP 목록을 계속 따라다녀야 한다.

SSM은 방향이 반대다. EC2의 SSM Agent가 **아웃바운드로** AWS에 붙어 명령을 받아 가므로 인바운드 규칙이 하나도 필요 없다. 실행 기록도 SSM 콘솔에 남는다.

전제: EC2에 SSM Agent가 떠 있어야 하고(Amazon Linux·Ubuntu 최신 AMI는 기본 포함), 인스턴스 프로파일에 `AmazonSSMManagedInstanceCore`가 붙어야 한다. **이 인스턴스 프로파일에는 이미 S3 접근 정책이 붙어 있다**(ADR-0020 §3, 이슈 #330) — 정책을 추가하는 것이지 역할을 새로 만드는 것이 아니다.

### 4. 이미지는 러너에서 빌드해 ECR에 올리고, EC2는 pull만 한다

- **태그는 커밋 SHA다.** `latest`를 쓰지 않는다 — 같은 이름이 시점마다 다른 것을 가리키면 "직전 색으로 롤백"이 무엇으로 돌아가는지 다시 불명확해진다. 롤백 대상은 이름으로 지목할 수 있어야 한다(§맥락).
- **blue와 green이 같은 이미지를 쓴다는 것이 보장된다.** EC2에서 각자 빌드하던 구조에서는 보장되지 않던 것이다.
- **러너는 `ubuntu-24.04-arm`을 쓴다.** EC2가 `t4g.small`, 즉 Graviton(arm64)이다. x86 러너에서 만든 이미지는 그 위에서 돌지 않는다(또는 QEMU 에뮬레이션으로 느리게 돈다). 이 레포는 공개이므로 GitHub의 Linux arm64 러너를 추가 비용 없이 쓸 수 있다 — **다만 실제 사용 가능 여부는 첫 파이프라인 실행에서 확인한다**(후속 이슈 체크 항목).
- **Gradle 빌드는 이미지 안이 아니라 러너에서 한다.** 현재 `Dockerfile`은 빌드 단계에서 `./gradlew bootJar`를 돌리는 멀티스테이지 구조인데, 그러면 러너의 Gradle 캐시를 쓸 수 없어 매 배포가 의존성 다운로드부터 시작한다. CD 경로는 러너가 `bootJar`를 만들고 **jar만 담는 런타임 전용 Dockerfile**을 쓴다. 현재 `Dockerfile`은 수동 배포·로컬 경로를 위해 그대로 둔다(후속 이슈에서 분리).

### 5. 전환은 파이프라인이 상태를 읽어서 정한다 — 사람이 색을 지정하지 않는다

어느 색이 라이브인지는 **ALB 리스너의 현재 기본 작업**에서 읽는다. 사람이 "이번엔 green" 하고 입력하는 방식은 쓰지 않는다 — 그 입력이 틀리면 라이브 색을 재기동하게 되고, 그것이 §맥락에서 지목한 가장 나쁜 실패다. **상태의 정본은 한 곳(ALB)이고, 파이프라인은 그것을 읽기만 한다.**

### 6. 헬스체크가 실패하면 전환하지 않는다 — 그것이 이 파이프라인의 롤백이다

| 실패 시점 | 동작 | 사용자 영향 |
|---|---|---|
| 유휴 색 컨테이너가 healthy가 되지 않음 | 전환하지 않고 새 색 컨테이너를 내린다. 워크플로우 실패 | **없다** — 라이브 색을 건드린 적이 없다 |
| 전환 후 새 색 타깃이 unhealthy | ALB 리스너를 이전 색으로 되돌린다. 워크플로우 실패 | 전환~복귀 사이 구간만 |

**"자동 롤백"의 뜻을 좁혀서 못박는다 — 직전 색으로 되돌리는 것이지, 임의의 과거 버전으로 가는 것이 아니다.** 그 이상은 사람이 이전 SHA 태그로 파이프라인을 재실행하는 수동 경로다(`deploy/cd-runbook.md`).

이것은 010 spec이 범위 제외로 두었던 "롤백 자동화"를 **부분적으로만** 들여온다. 두 단계 전 버전으로 돌아가는 자동 경로는 여전히 없다.

### 7. 롤백은 앱만 되돌린다 — 스키마는 되돌리지 않는다

Flyway 마이그레이션은 앱 기동 시 적용되고 앞으로만 간다(ADR-0004). 즉 **이전 색으로 롤백해도 DB 스키마는 새 버전 그대로**다. 구버전 앱이 신버전 스키마 위에서 돌아야 한다.

따라서 이 ADR은 ADR-0004에 조건을 하나 더한다.

- **한 배포에서 파괴적 변경(컬럼·테이블 삭제, 이름 변경, 타입 축소, NOT NULL 승격)을 하지 않는다.** 두 배포로 나눈다 — ① 새 컬럼 추가 + 양쪽 쓰기, ② (롤백 필요가 사라진 뒤) 옛 컬럼 제거.
- 이 제약은 **롤백 가능성을 유지하기 위한 비용**이다. 지키지 않으면 §결정 6의 롤백 경로가 "앱은 돌아가지만 데이터는 깨진다"가 된다.

### 8. 프론트(별도 레포)의 `dist/`도 같은 파이프라인을 탄다

프론트는 별도 레포(`finplay-team/finplay-frontend`)이고, 지금은 사람이 `npm run build`의 `dist/`를 EC2에 복사한다. 이것을 남겨 두면 "완전 자동 배포"가 백엔드에만 해당하게 된다.

- 프론트 레포의 워크플로우가 `dist/`를 빌드해 **S3 아티팩트 버킷에 커밋 SHA 키로 업로드**한 뒤, `repository_dispatch`로 이 레포의 배포 워크플로우를 호출한다.
- 배포 파이프라인은 유휴 색을 기동할 때 **그 색의 정적 디렉터리**(`FRONTEND_DIST_BLUE_PATH`·`FRONTEND_DIST_GREEN_PATH`)에 해당 아티팩트를 푼다. 즉 **배포 단위는 "백엔드 이미지 + 프론트 dist" 한 쌍**이고, 정적 파일도 색상 전환을 함께 탄다.
- 프론트만 바뀐 경우에도 색 전환을 한다. `deploy/README.md`의 "정적 파일은 재기동 없이 교체 가능"이라는 수동 경로는 라이브 색의 파일을 제자리에서 바꾸는 방식인데, 그러면 **롤백 시 되돌아갈 이전 프론트가 남지 않는다.** 색을 나누는 이유와 어긋나므로 자동 경로에서는 쓰지 않는다.
- 트리거가 두 레포로 늘어나므로 **배포 워크플로우에 `concurrency` 그룹을 걸어 직렬화한다.** 두 배포가 동시에 유휴 색을 잡으면 서로의 스택을 덮어쓴다.
- 프론트 레포 쪽 워크플로우 작성은 **그 레포의 별도 이슈**다. 이 ADR은 계약(S3 키 규칙 + `repository_dispatch` 페이로드)만 정한다.

### 9. 이 ADR이 결정하지 않는 것

- **자동 머지.** 머지 버튼은 계속 사람이 누른다 (ADR-0005·0013 유지).
- **배포 후 스모크 자동 실행.** 자동 게이트는 헬스체크(`/actuator/health` + ALB 타깃 상태)까지다. `scripts/smoke.ps1`은 010 spec대로 사람이 실행한다 — 스모크는 로그인 계정을 쓰므로 파이프라인에 계정 크리덴셜을 넣게 되고, 그 대가를 지금 치를 이유가 없다. 헬스체크로 못 잡는 회귀는 CI의 테스트가 잡는다.
- **스테이징 환경.** 지금 환경은 하나다. 블루-그린의 유휴 색은 스테이징이 아니다(전환 직전 몇 분만 존재한다).
- **오토스케일링·다중 EC2.** ADR-0020 §6의 범위 밖 판단을 그대로 유지한다. 이 파이프라인은 EC2 **한 대** 안의 두 색을 전제한다.
- **배포 알림 채널.** 지금은 GitHub Actions 실패 표시가 알림이다. 별도 채널(Slack 등)은 필요해지면 정한다.

## 결과

**좋은 점**

- 사람이 기억해야 하는 배포 절차가 없어진다. §맥락의 다섯 단계는 파이프라인 안에 있고, 특히 **"어느 색이 라이브인가"를 사람이 판단하지 않는다.**
- 롤백 대상이 커밋 SHA 태그로 **이름을 갖는다.** 어떤 코드가 배포됐는지가 ECR 태그와 워크플로우 로그로 남는다.
- 배포에 필요한 장기 크리덴셜이 **0개**다. SSH 키도, AWS 액세스 키도 GitHub에 저장하지 않는다. EC2에 22번 인바운드도 열지 않는다.
- 프론트·백엔드가 한 쌍으로 전환되므로, 프론트가 기대하는 API가 아직 안 뜬 중간 상태가 생기지 않는다.
- `t4g.small`에서 Gradle 빌드가 사라진다 — 앱 2벌이 쓰는 메모리 여유가 늘어난다.

**받아들이는 대가**

- **`dev`가 곧 공개 URL이다.** 미완성 기능이 머지되는 즉시 노출된다. 노출 통제 수단은 머지 시점 하나뿐이다(§결정 1).
- **파괴적 마이그레이션을 한 배포에 담을 수 없다**(§결정 7). 컬럼 하나 지우는 데 두 배포가 필요해진다.
- **AWS 콘솔 설정이 또 늘고, IaC가 없으므로 문서가 유일한 정본이다.** ADR-0020 §결과가 이미 지적한 문제가 커진다 — OIDC 공급자·IAM 역할 2종·ECR 리포지터리·SSM 권한·아티팩트 버킷이 추가된다. `deploy/cd-runbook.md`가 그 체크리스트다.
- **ECR·S3 아티팩트 저장 비용이 는다.** 이미지 태그가 SHA라 쌓이므로 수명 주기 정책(예: 최근 10개 유지)이 필요하다.
- **파이프라인이 실패하면 배포가 막힌다.** 지금까지는 사람이 SSH로 들어가면 언제든 배포할 수 있었다. 그 수동 경로는 폴백으로 문서에 남기지만(`deploy/README.md`), 파이프라인과 수동 경로가 갈라지면 상태를 두 곳에서 관리하게 된다.
- **레포 push 권한 ≈ 배포 권한**이다(§결정 2).

## 대안과 기각 사유

**(a) 수동 배포를 유지하고 절차서만 다듬는다**

가장 싸다. 그러나 §맥락에서 본 대로 블루-그린의 다섯 단계는 **상태 의존적**이라, 절차서를 아무리 정확히 써도 "지금 어느 색이 라이브인지"를 사람이 매번 조회해 판단해야 한다. 배포 빈도가 늘수록 틀릴 확률이 누적되고, 틀렸을 때의 대가가 사용자 요청 실패다. 기각.

**(b) SSH 키를 GitHub Secret에 넣고 `ssh`로 명령을 실행한다**

설정이 가장 단순하고 예제도 많다. 그러나 ① 장기 개인키가 GitHub에 남고, ② EC2에 22번 인바운드가 필요한데 러너 IP가 고정이 아니라 사실상 넓은 대역을 열게 된다 — **ADR-0020 §5(보안 그룹 참조로 경계를 정의한다)를 정면으로 되돌린다.** 기각.

**(c) EC2가 레지스트리를 폴링해 새 이미지를 당겨 간다 (watchtower 류)**

GitHub이 AWS에 접근할 필요가 없어 권한 설계가 가장 단순하다. 그러나 폴링은 **"띄운다"만 할 수 있고 "헬스체크 통과 후 전환하고, 실패하면 되돌린다"를 못 한다.** 블루-그린의 핵심이 전환 제어인데 그 제어권이 파이프라인에 없다. 배포 시점도 폴링 주기만큼 불확정이다. 기각.

**(d) AWS CodeDeploy / CodePipeline을 쓴다**

블루-그린을 관리형으로 얻는다. 그러나 CodeDeploy의 EC2 블루-그린은 **인스턴스를 새로 띄워 교체하는 ASG 기반 모델**이라, "EC2 한 대 안에서 두 색을 포트로 나눠 돌린다"는 ADR-0020의 현재 구조와 맞지 않는다. 그 모델을 쓰려면 인스턴스를 늘려야 하고, 그것은 ADR-0020 §6이 명시적으로 뒤로 미룬 결정이다. 팀이 익혀야 할 콘솔도 하나 더 는다. **다중 인스턴스로 가는 시점에 재검토한다.** 기각(현 시점).

**(e) `main` 머지를 트리거로 한다**

`main`을 "배포된 것"의 정본으로 유지할 수 있어 이력이 깔끔하다. 그러나 배포마다 `dev → main` PR을 사람이 만들고 머지해야 하므로 **사람 개입 지점이 둘**이 된다. 이 결정의 목적("머지 이후는 손대지 않는다")과 어긋난다. 대신 `main`의 역할을 시연·심사 스냅샷으로 다시 정의했다(§결정 1). 기각.

**(f) EC2에서 계속 이미지를 빌드하고, 파이프라인은 명령만 보낸다**

ECR 비용이 들지 않고 변경이 적다. 그러나 §맥락의 두 문제(두 색이 서로 다른 빌드가 될 수 있음, `t4g.small`에서 Gradle이 앱 2벌과 메모리를 다툼)가 그대로 남는다. **배포된 것이 무엇인지 이름으로 지목할 수 없으면 롤백이 성립하지 않는다.** 기각.

## 후속

전부 **별도 이슈**다. 이 ADR은 방향만 결정한다.

- `.github/workflows/deploy.yml` 작성 — 위 ①~⑦ 단계, `concurrency` 그룹, 실패 시 롤백.
- `compose.bluegreen.yaml`을 `build:`에서 ECR `image:` 참조로 전환 + `.env.example`에 이미지 태그 변수 추가.
- 런타임 전용 Dockerfile 분리(§결정 4). 현재 `Dockerfile`은 수동 경로용으로 유지.
- AWS 콘솔 설정 — OIDC 공급자, 배포용 IAM 역할(신뢰 정책을 `refs/heads/dev`로 한정), ECR 리포지터리 + 수명 주기 정책, 인스턴스 프로파일에 SSM 정책 추가, 프론트 아티팩트 S3 버킷. 절차는 `deploy/cd-runbook.md`.
- ALB·타깃 그룹 2개·ACM 인증서 발급 — ADR-0020 §후속이 이미 남긴 항목이며 **이 파이프라인의 선행 조건**이다.
- 프론트 레포(`finplay-team/finplay-frontend`)의 빌드·업로드·`repository_dispatch` 워크플로우.
- graceful shutdown(`server.shutdown: graceful` + `stop_grace_period`) — 이슈 #332가 별도 PR로 분리한 항목. 전환 순간 진행 중이던 요청을 끊지 않으려면 필요하다.
- 첫 실행 후 실측으로 확인할 것 — `ubuntu-24.04-arm` 러너 가용성, 전환 총 소요 시간, 전환 순간 SSE(`/api/stocks/stream`) 연결이 어떻게 끊기고 재연결되는지.
- 배포 지표(머지 → 배포 완료 시간)를 `docs/harness-roadmap.md`의 지표 3종에 추가할지 판단한다 — 그 문서의 지표는 에이전트 하네스 기준이라 축이 다르다.

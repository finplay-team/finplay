# ADR-0022: 프론트는 S3에서 독립 배포하고, 백엔드는 CORS로 연다

- 상태: 승인됨
- 날짜: 2026-08-12
- 관계: 이슈 #352. 프론트 정적 파일의 **서빙 주체와 배포 경로**에 대한 정본. 배포 아키텍처의 나머지(RDS·ElastiCache·S3 분리, 블루-그린, ALB + ACM)는 [ADR-0020](0020-managed-service-deployment.md)이, 배포 실행 방식은 [ADR-0021](0021-continuous-deployment.md)이 계속 정본이며 이 ADR은 그 둘을 통째로 대체하지 않는다. **대체하는 것은 셋이다** — ① 이슈 #108의 "A안: nginx 동일 오리진" 결정 전체, ② **ADR-0020 §결정 도입부의 배포 구성 다이어그램**(`## 결정` 바로 아래, §1 앞)이 "EC2 (nginx + app)"으로 그려 둔 것 중 **nginx가 정적 파일을 서빙한다는 부분만** — §결정 1~5 본문은 이 역할을 결정한 적이 없어 그대로 유효하다(PR #353 리뷰에서 지적된 인용 정밀도 정정, 2026-08-12), ③ ADR-0021 §결정 8("프론트 `dist/`도 같은 파이프라인을 탄다") 전체. ADR-0021의 나머지 결정(§1~7, §9)은 그대로 유효하다.

## 맥락

### 프론트 배포가 백엔드 인프라에 묶여 있다

현재 프론트 빌드 산출물은 **EC2 로컬 디스크**(`frontend-dist-blue/`·`frontend-dist-green/`)에 있고, EC2 안 nginx 컨테이너가 정적 파일 서빙과 `/api` 프록시를 함께 담당한다(`deploy/nginx-blue.conf`·`nginx-green.conf`). 그 결과 **화면 문구 한 줄을 고치는 데도 EC2에 접속해 파일을 복사해야 한다.**

이것은 ADR-0020이 세운 방향과 어긋난다. 그 ADR의 핵심은 "인스턴스를 언제든 버릴 수 있게 상태를 밖으로 뺀다"였고, 실제로 DB·캐시·업로드 이미지를 전부 인스턴스 밖으로 옮겼다. 그런데 **프론트 정적 파일만 인스턴스 안에 남았다.** 업로드 이미지를 S3로 옮긴 것과 같은 논리가 정적 파일에도 그대로 적용된다.

### 이슈 #108이 A안을 고른 근거 4개 중 하나는 이미 소멸했다

이슈 #108(2026-07-30)은 "A안: nginx 동일 오리진"과 "B안: 프론트 분리 + CORS" 중 A안을 골랐다. 근거 중 1번은 *"B안은 백엔드 HTTPS를 강제하는데 당시 인증서가 없었다"*였는데, **ADR-0020이 ALB + ACM을 도입하면서 이 근거는 사라졌다.** 백엔드는 이미 HTTPS다.

반면 근거 3번 — *"SSE + CORS preflight를 회피한다"* — 는 **아직 유효하고, 이 결정이 감수하는 실제 위험이다.** 이 ADR은 그 위험을 없앴다고 주장하지 않는다. 대신 §결정 3의 단계 구분으로 그것을 **가장 먼저, 가장 적은 변수 위에서 확인하도록** 순서를 설계한다.

### 착수 전 코드로 확인한 사실 (2026-08-12)

결정의 전제가 되므로 여기 남긴다. 이슈 본문의 기술적 전제를 코드로 확인하지 않고 문서에 옮겨 적어 배포가 깨졌던 사례(`ai/agent-mistakes.md` 2026-07-31)가 있어, 이번에는 확인한 것만 적는다.

| 확인 | 결과 | 결정에 미치는 영향 |
|---|---|---|
| 프론트의 API 주소 지정 방식 | `VITE_*` 환경변수 0개, 모든 호출이 상대경로 `/api`. 하드코딩은 3군데(`apiClient.ts`, `useStockStream.ts`) | 프론트 레포에 베이스 URL 도입이 **선행 조건**이다. 다만 3군데뿐이라 비용은 작다 |
| 쿠키 전송 여부 | `credentials:` 옵션 사용처 0. 토큰은 localStorage + `Authorization: Bearer` | `allowCredentials=false`로 확정한다 (§결정 2) |
| SSE 구현 방식 | `EventSource`가 아니라 `fetch` + `Authorization` 헤더(`useStockStream.ts:2`) | `Authorization`은 CORS 안전목록 헤더가 아니므로 **preflight가 반드시 발생한다.** 이슈 #108의 우려는 가정이 아니라 확정된 조건이다 |
| 프론트의 OAuth 로그인 | 착수 시점엔 `authorize` 호출부 0(UI 없음)이었으나, **작업 도중 프론트 `main`에 병합됐다**(finplay-frontend#12, `SocialLoginButtons.tsx`) | §결정 4가 막던 위험이 **이미 실재한다.** `oauth_state` 쿠키(`SameSite=Lax`)가 크로스 오리진 콜백 fetch에 실리지 않아 A 단계(S3 단독)에서는 로그인이 400 `VALIDATION_ERROR`로 막힌다. 프론트가 그 실패를 크래시 없이 안내 문구로 처리하도록 되어 있어(`OAuthCallback.tsx`) 사용자에게 보이는 형태는 "로그인 안 됨" 수준이지 오류 화면이 아니다. §결정 4는 여전히 유효한 해법이며, B 단계(같은 사이트 도메인)까지는 **로그인 버튼이 화면에 보이되 동작하지 않는 것을 알려진 한계로 받아들인다** |
| `server.forward-headers-strategy` | `application.yml`에 **없다** | nginx가 `X-Forwarded-Proto https`를 강제 주입해 왔다(`nginx-blue.conf`). nginx를 빼면 이 설정이 없는 채로 ALB 헤더를 해석하지 못한다 (§결정 6) |
| ADR-0021 §결정 8의 구현 | `.github/workflows/`에 `agent.yml`·`ci.yml`뿐 — 해당 파이프라인은 **아직 존재하지 않는다** | 그 결정을 대체해도 **삭제할 코드가 없다.** 문서 변경만으로 끝난다 |

## 결정

**프론트 정적 파일은 S3에 두고 독립적으로 배포한다. EC2에는 백엔드만 남기고, 오리진이 갈라지는 대가로 백엔드에 CORS를 도입한다.**

```
[브라우저]
   ├─ 프론트 오리진 ──────────→ S3  (정적 파일. EC2와 무관하게 배포된다)
   └─ https://finplay.site ──→ ALB ─→ EC2 (백엔드 앱만. nginx 없음)
                                        │
                          ┌─────────────┼─────────────┐
                        RDS        ElastiCache        S3
                                                 (업로드 이미지)
```

### 1. 프론트 정적 파일은 S3에 두고, EC2에서 nginx를 제거한다

`compose.bluegreen.yaml`의 `nginx-blue`·`nginx-green`, `compose.deploy.yaml`의 `nginx` 서비스를 없애고 `deploy/nginx-blue.conf`·`nginx-green.conf`·`nginx.conf`를 삭제한다. 앱 컨테이너가 호스트 포트(blue 8081 / green 8082)를 직접 열고 ALB 타깃 그룹이 그 포트를 가리킨다.

**단일 스택(`compose.deploy.yaml`)도 함께 정리한다.** 블루-그린에서만 nginx를 빼면 저장소에 **서로 모순되는 두 배포 스택**이 남아, 다음 사람이 어느 쪽이 정본인지 판별할 수 없다.

### 2. 백엔드는 CORS로 열되, 허용 오리진은 환경변수로 주입한다

`SecurityConfig`에 `CorsConfigurationSource`를 추가한다.

- **허용 오리진을 코드에 하드코딩하지 않는다.** 로컬·배포가 다르고, 무엇보다 §결정 3의 A→B 전환을 **코드 배포 없이** 가능하게 만드는 것이 이 선택의 핵심이다. 전환기에는 두 오리진을 함께 허용하고, 안정화 후 옛 것을 뺀다.
- **허용 헤더에 `Authorization`을 반드시 포함한다.** SSE가 이 헤더를 싣는다.
- 허용 메서드는 `GET, POST, PUT, PATCH, DELETE, OPTIONS`.
- **`allowCredentials`는 `false`다.** 프론트가 쿠키를 전송하지 않는다는 것을 확인했다(§맥락 표). `true`로 두면 `allowedOrigins`에 `*`를 쓸 수 없게 되는 제약만 얻고 얻는 것이 없다.
- **preflight(OPTIONS)가 `JwtAuthenticationFilter`에 막히지 않아야 한다.** CORS 처리가 인증 필터보다 먼저 돌아야 하며, 이것은 설정이 아니라 **테스트로 확인할 대상**이다.

### 3. 단계적으로 간다 — S3 단독으로 먼저 검증하고, CloudFront는 나중에 얹는다

| 단계 | 프론트 오리진 | 목적 |
|---|---|---|
| **A** | S3 정적 웹 호스팅 기본 주소 (HTTP) | CORS·preflight·SSE가 실제로 동작하는지 **최소 변수**로 확인 |
| **B** | `https://www.finplay.site` (CloudFront) | HTTPS·커스텀 도메인·CDN |

**A를 먼저 두는 이유는 진단 가능성이다.** 이 작업에서 유일하게 불확실한 것은 이슈 #108이 지목한 "SSE가 CORS를 넘어 흐르는가"이고, A는 용의자가 CORS 설정 하나뿐이다. CloudFront부터 얹으면 캐시 정책·오리진 설정·SPA 폴백이 용의자에 추가되어, 실패했을 때 원인을 가르는 비용이 커진다.

**A는 임시 상태가 아니라 검증 게이트다.** A에서 SSE push가 확인되지 않으면 B로 넘어가지 않는다. 그리고 A 단계 내내 기존 nginx 서빙이 살아 있으므로(§결정 7의 순서) 실패에 시간 압박이 없다.

**B로 갈 때 백엔드 코드는 바뀌지 않는다.** 서버 `.env`의 허용 오리진 한 줄과 AWS 콘솔 작업뿐이다.

### 4. API 도메인은 `https://finplay.site`로 유지하고, 프론트를 `www`에 둔다

B 단계에서 프론트를 `www.finplay.site`에 두고 API는 apex(`finplay.site`)에 그대로 남긴다. **API를 `api.finplay.site`로 옮기지 않는다.**

- API 주소가 고정되면 `KAKAO_REDIRECT_URI`·`NAVER_REDIRECT_URI`와 각 개발자센터 콘솔 설정, ALB의 ACM 인증서를 **하나도 건드리지 않는다.**
- `www.finplay.site`와 `finplay.site`는 **같은 등록가능 도메인이라 same-site다.** 프론트의 카카오·네이버 로그인 UI(finplay-frontend#12, §맥락 표 갱신 참고)가 붙이려는 `oauth_state` 쿠키(`SameSite=Lax`, `Secure`, `path=/api/auth/oauth/{provider}/callback`)가 이 조건에서 그대로 동작한다. 프론트가 S3 기본 주소나 CloudFront 기본 도메인에 있으면 cross-site가 되어 이 쿠키가 차단된다.
- **이 로그인 UI는 이미 프론트에 존재하므로 "붙이지 않는다"는 선택지가 없다.** A 단계(S3 단독)에서는 로그인 버튼이 눌리지만 `oauth_state` 쿠키가 콜백 요청에 실리지 않아 백엔드가 400 `VALIDATION_ERROR`로 거부한다 — 프론트가 이 실패를 크래시 없이 안내 문구로 처리하도록 이미 되어 있어(`OAuthCallback.tsx`), 사용자에게는 "로그인이 안 된다"로 보이는 알려진 한계로 남긴다. **B로 넘어가야 실제로 동작한다.**

### 5. API를 CloudFront에 태우지 않는다

B 단계에서도 CloudFront는 S3 정적 파일만 서빙하고, `/api`는 ALB로 직통한다. SSE(`/api/stocks/stream`, `/api/cryptos/stream`)를 CDN 뒤에 두면 캐싱 정책과 오리진 응답 타임아웃이라는 **새 실패 지점**이 생긴다. 동일 오리진을 되찾아 CORS를 없애는 대가로 그 위험을 사는 것은, 이 ADR이 CORS를 감당하기로 한 결정과 모순된다.

### 6. `server.forward-headers-strategy`를 명시한다

nginx가 `X-Forwarded-Proto https`를 강제로 넣어 주던 자리가 비므로, ALB가 넣는 `X-Forwarded-*`를 Spring이 직접 해석하게 한다. 없으면 앱이 요청을 `http`로 인식해 **OAuth 리다이렉트 URL 생성과 Secure 쿠키 발급이 틀어질 수 있다.**

이 설정은 nginx가 살아 있는 동안에도 무해하다(nginx도 같은 헤더를 넣는다). 따라서 **nginx 제거보다 먼저 넣는다** — 순서를 뒤집으면 "nginx는 없는데 헤더 해석은 안 되는" 구간이 잠시 생긴다.

### 7. 되돌리기 쉬운 순서로 적용한다

1. **백엔드: ADR + CORS + forward-headers** — nginx를 유지한 채 배포한다. CORS 응답 헤더는 요청에 `Origin`이 있을 때만 나가고 현재는 동일 오리진이라 붙지 않으므로, **이 배포는 기존 서비스에 무영향이다.**
2. **프론트: 베이스 URL 도입 + S3 게시 + 실측 검증** — 기존 사이트가 그대로 살아 있는 상태에서 별도 주소로 검증한다. 실패해도 롤백할 것이 없다.
3. **nginx 제거 + ALB 타깃 전환** — 검증이 끝난 뒤에만 수행하는, 유일하게 되돌리기 어려운 단계.

이 순서는 임의가 아니다. 이 저장소는 **"검증 없이 푸시한 수정이 다음 리뷰에서 다시 차단되는" 패턴을 3라운드 연속 겪은 적이 있다**(`ai/agent-mistakes.md` 2026-08-03, PR #132). 되돌리기 어려운 변경을 검증 뒤로 미루는 것이 그 재발을 막는 구조적 방법이다.

### 8. 프론트와 백엔드는 더 이상 한 쌍으로 전환되지 않는다 — **API 하위호환을 지킨다**

ADR-0021 §결정 8은 배포 단위를 "백엔드 이미지 + 프론트 dist 한 쌍"으로 묶고 정적 파일도 색상 전환을 함께 타게 했다. **이 ADR은 그 묶음을 푼다.** 프론트는 S3에 올라간 순간 모든 사용자에게 즉시 보이며, 어느 색이 라이브인지와 무관하다.

그 대가로 **"신버전 프론트 + 구버전 API" 조합이 배포 중에 실재하게 된다.** 따라서 다음을 규칙으로 못박는다.

- **API 변경은 하위호환으로 한다.** 필드 추가는 자유롭고, 필드 제거·의미 변경·필수 파라미터 추가는 프론트가 먼저 대응한 뒤에만 배포한다.
- 하위호환이 불가능한 변경이 필요하면 **엔드포인트를 새로 추가하고 구 엔드포인트를 남긴 뒤, 프론트 전환 후 제거**하는 2단계로 나눈다.
- 이 규칙은 색상 전환이 지켜 주던 것을 사람이 지켜야 하는 것으로 바꾼 것이다. **이것이 프론트 독립 배포의 실질 비용이다.**

### 9. 이 ADR이 결정하지 않는 것

- **EC2 2대 분리.** 현재 EC2는 **1대**이며 그 안에서 blue(8081)·green(8082) 컨테이너로 색을 나눈다. 따라서 **인스턴스 장애 시 두 색이 동시에 죽어 무중단이 성립하지 않는다.** 이것은 비용을 이유로 받아들인 알려진 한계이며, 이 ADR은 그 상태를 바꾸지 않는다. (ADR-0020 본문은 "같은 EC2"라고 쓰면서 같은 문서의 그림은 EC2 2대로 그려 놓아 불일치가 있었다 — 실제 구성은 1대다.)
- **프론트 레포의 배포 워크플로우 자동화.** 지금은 사람이 `aws s3 sync`를 실행한다. 자동화는 프론트 레포의 별도 이슈다.
- **CloudFront 캐시 무효화 자동화.** B 단계 이후 프론트 배포마다 무효화가 필요하다는 사실은 §결과에 적지만, 그 실행을 어디서 자동화할지는 정하지 않는다.
- **`compose.deploy.yaml`(단일 스택)을 계속 유지할지.** 블루-그린이 실제 배포 경로가 된 이상 단일 스택의 존재 이유가 약해졌으나, 이 ADR은 nginx만 걷어내고 폐기 여부는 판단하지 않는다.

## 결과

**좋은 점**

- **프론트 배포가 EC2에서 완전히 분리된다.** 백엔드 인프라에 접속하지 않고, 백엔드를 재기동하지 않고, 어느 색이 라이브인지 알 필요 없이 프론트를 배포할 수 있다. 이 작업의 목적이 이것이다.
- **ADR-0020의 "상태를 인스턴스 밖으로" 원칙이 정적 파일까지 확장돼 일관해진다.** DB·캐시·업로드 이미지는 이미 밖에 있었고 정적 파일만 남아 있었다.
- **배포 스택이 단순해진다.** 컨테이너가 색당 2개에서 1개로 줄고, nginx 설정 파일 3개와 `FRONTEND_DIST*_PATH` 환경변수 3개가 사라진다. blue·green이 각자의 정적 디렉터리를 봐야 했던 이유도 함께 사라진다.
- **A→B 전환에 코드 배포가 필요 없다.** 허용 오리진이 환경변수이므로 CloudFront 도입은 인프라 작업만으로 끝난다.
- OAuth 콘솔·ALB 인증서를 건드리지 않으므로 **이 작업으로 로그인이 깨질 경로가 없다**(§결정 4).

**받아들이는 대가**

- **CORS preflight가 모든 인증 요청에 붙는다.** 프론트가 `Authorization` 헤더를 쓰므로 안전목록을 벗어나며, 특히 SSE 연결마다 OPTIONS 왕복이 선행한다. 이슈 #108이 피하려 했던 바로 그 비용이고, 이 ADR은 그것을 없앴다고 말하지 않는다 — 감수하고 실측으로 확인한다.
- **A 단계 동안 프론트가 HTTPS가 아니다.** S3 정적 웹 호스팅 엔드포인트는 HTTPS를 지원하지 않는다. 주소창에 "안전하지 않음"이 표시되며, 이 구간에서는 프론트에 OAuth 로그인을 붙일 수 없다(§결정 4).
- **프론트·백엔드의 원자적 전환이 사라진다.** §결정 8의 하위호환 규칙을 사람이 지켜야 하며, 어기면 배포 중 사용자에게 깨진 화면이 보인다. 색상 전환이 자동으로 막아 주던 것이다.
- **B 단계 이후 프론트 배포에 캐시 무효화가 추가된다.** `aws s3 sync`만 하고 무효화를 빠뜨리면 새 파일을 올려도 사용자에게 옛 화면이 계속 보인다. 오류가 나지 않고 조용히 틀리는 종류의 실패다.
- **ALB 유휴 타임아웃이 SSE 연결을 직접 지배하게 된다.** nginx의 `proxy_read_timeout 3600s`가 사라지므로, ALB 기본값(60초)에서 연결이 끊기면 ALB 속성으로 조정해야 한다.
- **AWS 콘솔 설정이 문서에 없으면 복원할 수 없는 상태가 하나 더 늘어난다.** 버킷 정책·정적 호스팅 설정·CloudFront 배포는 코드가 아니라 콘솔에 있다(IaC 미도입). ADR-0020 §결과가 적은 것과 같은 부류다.

## 대안과 기각 사유

**(a) nginx 동일 오리진을 유지한다 (= 이슈 #108 A안 존치)**

CORS·preflight를 도입하지 않아도 되고 SSE 위험이 없다. 그러나 **프론트 배포가 백엔드 인프라에 묶인 상태가 그대로 남는다** — 이 작업이 해결하려는 문제 자체가 남는다. A안의 근거 하나(인증서 부재)는 이미 소멸했고, 남은 근거(preflight 회피)는 §결정 3의 단계 구분으로 위험을 관리 가능한 크기로 줄일 수 있다. 기각.

**(b) CloudFront에 `/api` 비헤이비어를 추가해 단일 도메인으로 묶는다**

프론트를 S3로 옮기면서도 동일 오리진을 유지할 수 있어 CORS가 아예 불필요해진다. 실제로 A안의 장점과 S3 분리의 장점을 동시에 갖는 유일한 안이다. 그러나 **SSE를 CDN 뒤로 넣게 된다**(§결정 5) — 캐싱 정책과 오리진 타임아웃이 새 실패 지점이 되고, 그 실패는 "가끔 스트림이 끊긴다" 형태라 진단이 어렵다. CORS는 실패하면 콘솔에 명확한 오류가 찍히는 반면 이쪽은 조용히 틀린다. **진단 가능한 위험을 조용한 위험으로 바꾸는 거래**라 기각.

**(c) API를 `api.finplay.site`로 옮기고 프론트에 apex를 준다**

주소 체계가 가장 깔끔하고 프론트가 대표 주소를 갖는다. 그러나 **OAuth 콘솔 2곳의 리다이렉트 URI, EC2 `.env`의 두 값, ALB 인증서를 전부 재작업**해야 하고, 그중 하나라도 어긋나면 로그인이 깨진다. 이 작업의 목적(프론트 분리)에 아무것도 더하지 않으면서 실패 지점만 늘린다. `www`를 프론트에 주면 same-site 이점(§결정 4)은 그대로 얻으면서 이 비용이 0이 된다. 기각.

**(d) 처음부터 CloudFront + 커스텀 도메인으로 간다 (B 단계 직행)**

중간 상태 없이 최종형에 도달하고 HTTP 구간이 없다. 그러나 첫 검증에서 SSE가 안 흐를 때 **용의자가 CORS·CDN 캐싱·오리진 설정·SPA 폴백으로 늘어난다.** 이 저장소에는 "조준 밖 영역이 비어 리뷰 라운드가 3회로 늘었다"(2026-08-03)와 "필터 실행 통과를 전체 통과 근거로 삼아 실패를 늦게 발견했다"(2026-08-04) 같은 기록이 있고, 둘 다 **검증 범위를 좁게 잡아 원인 규명이 늦어진** 사례다. 단계를 나누는 비용(A 구간의 임시 HTTP 주소)이 그 위험보다 싸다. 기각.

**(e) S3 대신 Vercel·Netlify 등 프론트 전용 호스팅을 쓴다**

빌드·배포·HTTPS·CDN이 한 번에 해결되고 무료 티어로 충분하다. 그러나 이 팀은 이미 S3를 쓰고 있고(업로드 이미지, ADR-0020 §결정 3), AWS 계정 하나로 인프라를 통일해 두면 권한·비용·장애 지점이 한곳에 모인다. 외부 서비스를 하나 더 들이는 것은 **운영 대상을 늘리는 방향**이라 ADR-0020의 판단 기준(§대안 c의 "버릴 수 없는 인스턴스를 하나 더 만들지 않는다")과 어긋난다. 기각.

## 후속

- **A 단계에서 SSE push를 브라우저로 실측한다.** 이슈 #108이 남긴 유일한 유효 근거에 대한 반증이며, 통과하지 못하면 이 ADR의 §결정 3에 따라 B로 진행하지 않는다. 결과는 `ai/specs/010-deployment/spec.md`의 검증 절에 기록한다.
- **B 단계(CloudFront + `www.finplay.site`)는 별도 작업이다.** 이 ADR은 방향과 도메인 배치를 정할 뿐 절차를 정의하지 않는다.
- **프론트 레포의 베이스 URL 도입은 그 레포의 별도 작업이다.** 이 저장소의 CORS 배포가 선행 조건이다.
- **ADR-0021 §결정 8이 정의한 프론트 아티팩트 계약(S3 키 규칙 + `repository_dispatch`)은 폐기된다.** 해당 워크플로우가 아직 구현되지 않아 지금은 문서 정리로 끝나지만, CD 파이프라인을 구현할 때 이 ADR을 먼저 읽어야 한다.
- **EC2 1대의 무중단 한계**(§결정 9)는 실사용자 트래픽이 붙는 시점에 재검토한다. ADR-0020 §6이 오토스케일링·ASG를 범위 밖으로 둔 것과 같은 이유로 지금 결정하지 않는다.
- **ALB 유휴 타임아웃의 실제 값과 SSE 유지 여부**를 A 단계에서 관측하고, 조정이 필요하면 `deploy/README.md`에 값과 근거를 남긴다.

# ADR-0027: "머지된 마이그레이션 수정 금지"의 기준은 git 머지가 아니라 DB 적용이다

- 상태: 승인됨
- 날짜: 2026-08-20
- 관계: 이슈 #448. [ADR-0004](0004-flyway-migrations.md)를 **대체하지 않는다** — §결정의 "이미 머지된 마이그레이션 파일은 절대 수정하지 않는다"가 어디까지를 가리키는지 정하고, 그 안에 예외 하나를 만든다. 근거 사례는 PR #446(V42 머지) · PR #447(V42 → V45 리네임)이고, 이 사고의 다른 면(번호 역전 자체를 어떻게 막을 것인가)은 이슈 #449에서 따로 다룬다.

## 맥락

ADR-0004는 `이미 머지된 마이그레이션 파일은 절대 수정하지 않는다`라고만 적는다. **"머지"가 git 머지인지 DB 적용인지 적혀 있지 않다.** 평소에는 둘이 거의 같은 시점이라 구분할 일이 없었다 — `dev`에 머지되면 곧바로 배포되고(ADR-0021), 배포되면 Flyway가 적용한다.

PR #447이 그 둘이 갈라지는 첫 사례였다. 사실 관계는 이렇다.

- `V42__add_shared_trade_id_to_community_posts.sql`은 커밋 `27bdbfcd`(PR #446)로 **git 기준으로는 `dev`에 머지된 상태**였다.
- 그러나 **어떤 환경의 `flyway_schema_history`에도 기록된 적이 없었다.** 먼저 머지된 PR #439가 V43·V44를 올려 운영 DB가 V44까지 진행된 뒤였고, Flyway가 `validate` 단계에서 `Detected resolved migration not applied to database: 42`로 멈춰 `migrate`가 아예 실행되지 않았기 때문이다.

이 상태에서 "수정 금지"를 글자 그대로 읽으면 **막다른 길**이 된다. V42 파일을 그대로 두면 운영 DB는 계속 validate에서 죽고, 그 위에 새 마이그레이션을 얹어도 상황은 그대로다. `out-of-order=true`는 순서 검증을 영구히 약화시키므로(한 번 켜면 이후 모든 배포에 적용된다) 이 한 건을 풀자고 쓸 수단이 아니다. **즉 파일 리네임 외에 안전한 경로가 사실상 없다.**

PR #447 리뷰어도 같은 판단을 했지만, 규칙 문언에 근거가 없어 "해석 공백을 좁게 활용해 통과한 형태"로 분류하고 권장 사항으로 남겼다. 명문화하지 않으면 다음에 같은 상황에서 같은 논쟁을 다시 한다.

## 결정

1. **ADR-0004의 "이미 머지된"은 "어느 환경에서든 `flyway_schema_history`에 기록된"을 뜻한다.** git 머지 여부는 판정 기준이 아니다. 이 규칙이 원래 막으려는 것은 *이미 적용된 이력*의 체크섬·순서가 파일과 어긋나는 상태이지, 파일이 어느 브랜치에 있느냐가 아니다.
2. **git에는 머지됐으나 어떤 환경의 `flyway_schema_history`에도 기록된 적이 없는 마이그레이션은 리네임하거나 삭제할 수 있다.** 단 아래 §판정 절차를 밟고, 확인한 근거를 그 PR 본문에 남긴다.
3. **한 번이라도 적용된 마이그레이션은 종전대로 수정 금지다** — 내용·버전 번호·파일명 전부. 고칠 것이 있으면 새 번호 파일을 추가한다 (ADR-0004 §결정 유지).
4. **이 예외는 복구 수단이지 정상 경로가 아니다.** 애초에 번호를 선점당하지 않는 것이 우선이며(`docs/git-conventions.md`의 "머지 직전 번호 재확인"), 예외를 쓴 PR은 리뷰에서 판정 근거를 확인받는다. 근거가 본문에 없으면 리뷰에서 차단한다.

## 판정 절차 — "적용된 적 없음"을 무엇으로 확인하나

확인해야 할 환경은 **운영(`prod`), 팀원 로컬(`local`), 테스트(Testcontainers)** 셋이다. 이 중 결정적인 것은 운영 하나다.

1. **운영 DB 조회가 정본이다.** 운영 MySQL에서
   ```sql
   SELECT version, script, success FROM flyway_schema_history ORDER BY installed_rank;
   ```
   를 실행해 해당 버전이 **행으로 존재하지 않음**을 확인한다. 접근 경로는 SSM Send Command다(ADR-0021 §결정 3 — EC2에 SSH를 열지 않는다). 이것 하나만으로 판정이 선다.
2. **운영 DB에 붙을 수 없을 때의 차선 — 배포 로그.** 그 마이그레이션을 담은 커밋 이후의 Deploy 워크플로가 **전부 실패**했고, 실패 원인이 `Detected resolved migration not applied to database: N`이면, Flyway 자신이 "N은 파일로는 해석됐지만 DB에 적용되지 않았다"고 판정한 것이다. 이 메시지는 validate 단계에서 나오므로 그 배포에서 `migrate`가 실행되지 않았다는 뜻이기도 하다.
3. **2를 쓸 때는 성공 배포 이력 부재를 함께 확인한다.** 해당 커밋 이후 Deploy 워크플로가 한 번이라도 성공했다면 그 실행에서 적용됐을 수 있다 — Actions 실행 이력에서 성공 건이 없음을 확인한다. **2와 3은 함께여야 1을 대신한다.**
4. **로컬·테스트는 걸림돌이 아니다.** Testcontainers는 실행마다 새 DB라 이력이 남지 않는다. 팀원 로컬 DB에는 이미 적용돼 있을 수 있는데, 리네임 후 그 로컬은 validate 실패로 기동이 막힌다 — **해결책은 로컬 DB 재생성**(`docker compose down -v` 후 재기동)이며, 리네임 PR은 이 안내를 본문에 적는다. 로컬은 언제든 버릴 수 있는 상태이므로 예외 적용을 막는 근거가 되지 않는다.
5. **1을 확인하지 못하고 2+3도 성립하지 않으면 예외를 쓰지 않는다.** 그때는 파일을 그대로 두고 새 번호로 앞으로 고친다.

환경이 늘어나면(스테이징 등) 1번을 환경마다 반복한다 — "어느 환경에서든"이 기준이기 때문이다.

## 결과

- 배포가 막힌 상태에서 **규칙 위반 없이 밟을 수 있는 복구 경로**가 생긴다. 다음에 같은 상황이 오면 해석 논쟁 대신 §판정 절차를 따르면 된다.
- 대가는 **판정 비용**이다. "적용된 적 없음"은 운영 DB 조회를 요구하고, 그건 아무나 즉시 할 수 있는 일이 아니다. 그래도 잘못 판정해 이미 적용된 마이그레이션을 리네임했을 때의 대가(운영 DB가 영구히 validate 실패, 수동 `flyway_schema_history` 조작 외에 복구 불가)가 훨씬 크므로 이 비용은 감수한다.
- 이 ADR은 **번호 역전이 일어난 뒤의 처리**만 정한다. 번호 역전 자체를 어떻게 막을 것인가는 이슈 #449의 몫이고, 그쪽이 해결되면 이 예외를 쓸 일이 줄어드는 것이 정상이다.

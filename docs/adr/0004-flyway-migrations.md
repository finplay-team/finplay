# ADR-0004: DB 스키마는 Flyway 마이그레이션으로만 변경한다

- 상태: 승인됨 — 결정은 그대로이고, [ADR-0021](0021-continuous-deployment.md) §결정 7이 **제약을 하나 추가**했으며 (2026-08-12), [ADR-0027](0027-unapplied-migration-rename-exception.md)이 **"수정 금지"의 적용 범위를 정하고 예외 하나를 만들었다** (2026-08-20).
- 날짜: 2026-07-22

> **추가 제약 (ADR-0021 §결정 7).** 자동 배포의 롤백은 **앱만 되돌리고 스키마는 되돌리지 않는다** — 구버전 앱이 신버전 스키마 위에서 돌아야 한다.
> 그래서 **파괴적 변경(컬럼·테이블 삭제, 이름 변경, 타입 축소, NOT NULL 승격)을 한 배포에 담지 않는다.** 두 배포로 나눈다 —
> ① 추가 + 양쪽 쓰기, ② 롤백 필요가 사라진 뒤 제거. 지키지 않으면 롤백 경로가 "앱은 돌아가지만 데이터가 깨진다"가 된다.

> **적용 범위 (ADR-0027).** 아래 §결정의 "이미 머지된"은 **git 머지가 아니라 `flyway_schema_history`에 기록된 것**을 뜻한다.
> git에는 머지됐으나 **어떤 환경에서도 적용된 적 없는** 마이그레이션은 리네임·삭제할 수 있다 — 판정 절차와 근거는 ADR-0027을 따른다.

## 맥락

`ddl-auto=update`로 하이버네이트가 스키마를 자동 변경하면 팀원마다 DB 상태가 달라지고, 운영 반영 시 어떤 DDL이 실행될지 예측할 수 없다. 팀 프로젝트에서 스키마 이력은 코드처럼 버전 관리되어야 한다.

## 결정

- 스키마 변경은 `src/main/resources/db/migration/V{N}__{설명}.sql` 파일로만 한다.
- `spring.jpa.hibernate.ddl-auto=validate` — 하이버네이트는 엔티티와 스키마가 일치하는지 검증만 한다. 불일치 시 기동 실패가 정상 동작이다 (마이그레이션 누락을 조기에 발견).
- 이미 머지된 마이그레이션 파일은 절대 수정하지 않는다. 고칠 게 있으면 새 버전 파일을 추가한다. (여기서 "머지된"의 기준과 유일한 예외는 [ADR-0027](0027-unapplied-migration-rename-exception.md)에 있다.)
- 로컬/테스트(Testcontainers)/운영 모두 같은 마이그레이션을 실행한다.

## 결과

- 엔티티를 바꾸면 마이그레이션 파일도 같은 PR에 포함해야 한다 (안 하면 validate가 잡아낸다).
- 스키마 이력이 git에 남아 롤백 지점과 변경 사유 추적이 가능하다.

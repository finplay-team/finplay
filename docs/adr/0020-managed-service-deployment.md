# ADR-0020: 배포는 EC2 + 관리형 서비스(RDS·ElastiCache·S3) 위에서 블루-그린으로 한다

- 상태: 승인됨
- 날짜: 2026-08-11
- 관계: 이슈 #326. `docs/specs/010-deployment`의 배포 아키텍처 정본. ADR-0014(코인 감시 Redis 락)·ADR-0015(조회 캐시 Redis 락)·ADR-0018(코인 카드 SSE push)이 공통 전제로 인용해 온 **"다중 인스턴스 전환이 예정돼 있다"의 실체를 이 ADR이 정의한다** — 세 ADR은 그대로 유효하며 이 ADR이 그 전제를 사후 승인한다. `docs/specs/022-community-enhancement/plan.md`의 "이미지를 로컬 파일시스템에 저장한다"는 단일 인스턴스 전제 위에 있었고, 이 ADR이 그 전제를 없앤다 — 상세는 §맥락.

## 맥락

`docs/specs/010-deployment/spec.md`가 정의한 현재 배포 구조는 **EC2 한 대에 `compose.deploy.yaml`로 nginx·app·mysql·redis 네 컨테이너를 함께 올리는 것**이다. 같은 spec의 범위 제외 절이 "무중단 배포·롤백 자동화·오토스케일링"을 명시적으로 뺐다. 1차 MVP를 띄우기 위한 최소 구성으로는 타당했지만, 지금 세 방향에서 한계가 동시에 드러났다.

### 상태 저장소가 EC2 인스턴스와 생명주기를 공유한다

`compose.deploy.yaml`의 `mysql`·`redis`는 named volume에 데이터를 두는데, 그 볼륨은 EC2 인스턴스의 EBS 위에 있다. **인스턴스를 종료하면 원장이 함께 사라진다.** 이것은 가정이 아니라 이 팀이 이미 겪은 사건이다 — 비용 절감을 위해 EC2를 종료했다가 그 위의 DB 데이터를 잃고 복구에 시간을 썼다.

블루-그린은 이 문제를 더 키운다. 블루-그린의 전제는 "인스턴스를 언제든 새로 만들고 버릴 수 있다"인데, 인스턴스에 원장이 붙어 있으면 그 전제 자체가 성립하지 않는다. **인스턴스를 버릴 수 있게 만들려면 상태를 인스턴스 밖으로 먼저 빼야 한다.**

### 다중 인스턴스 전제가 세 ADR에 걸쳐 있는데 그 전환을 결정한 문서가 없다

ADR-0014는 `@Scheduled` 겹침 방지가 다중 인스턴스에서 사라진다는 이유로 Redis 분산 락을 도입했고, ADR-0015는 "인스턴스 내 방어(`sync = true`)로는 부족하다"를 이유로 같은 락 구조를 조회 캐시에 적용했으며, ADR-0018은 인스턴스 로컬 `SseEmitterRegistry`를 넘는 팬아웃이 필요하다는 이유로 Redis pub/sub을 얹었다. 셋 다 근거 문장이 **"다중 인스턴스 전환이 예정돼 있다"** 하나다.

그런데 그 전환이 구체적으로 무엇인지 — 어떤 서비스 조합으로, 어떤 배포 방식으로 가는지 — 를 결정한 ADR은 지금까지 없었다. 세 ADR이 인용하는 전제가 어느 문서에도 정의돼 있지 않은 상태다. 이 ADR이 그 빈자리를 채운다.

동시에 그 전제는 **Redis가 인스턴스 밖 공유 자원이라는 것**을 이미 요구하고 있었다. EC2 안 컨테이너로 뜬 Redis는 그 인스턴스에서만 보이므로, 세 ADR의 설계는 현재 구조에서는 애초에 작동할 수 없다 — 락도 pub/sub도 인스턴스마다 별개의 Redis를 보게 된다. **세 ADR은 이 ADR이 실행되기 전까지 설계로만 옳고 배포로는 옳지 않았다.**

### 로컬 파일시스템 저장이 다중 인스턴스에서 깨진다

`docs/specs/022-community-enhancement/plan.md`의 `LocalFileStorageService` 항목은 이 문제를 미리 적어 뒀다 — "로컬 파일시스템은 인스턴스 간에 공유되지 않는다. 이 구현은 단일 인스턴스 배포를 전제하며, 다중 인스턴스 배포로 전환하려면 `FileStorageService` 구현체를 오브젝트 스토리지로 먼저 교체해야 한다"(PR #269 리뷰). `S3FileStorageService`는 "실제로 필요해지는 시점(운영 배포 논의)에 추가한다"로 미뤄져 있었다. **지금이 그 시점이다.**

`FileStorageService` 인터페이스가 이미 있으므로 이 교체는 구현체 하나를 추가하는 일이다 — 설계를 다시 하는 일이 아니다.

## 결정

**배포는 EC2 위에 애플리케이션만 두고, 상태를 갖는 것은 전부 관리형 서비스로 분리한다. 그 위에서 블루-그린으로 무중단 배포한다.**

```
                     ┌─ ALB (ACM 인증서, HTTPS) ─┐
                     │                            │
              [Target Group: blue]        [Target Group: green]
                     │                            │
              EC2 (nginx + app)            EC2 (nginx + app)
                     └───────────┬────────────────┘
                                 │  (상태는 인스턴스 밖에만 있다)
                  ┌──────────────┼──────────────┐
                RDS          ElastiCache        S3
             (MySQL)          (Redis)      (업로드 이미지)
```

### 1. DB는 RDS로 분리한다

`finplay-db` — MySQL 8.4, `db.t4g.micro`, **Single-AZ**, private 서브넷 2개(2 AZ에 걸친 서브넷 그룹), 전용 보안 그룹 `finplay-rds-sg`.

Single-AZ를 고른 것은 이 결정의 목적이 **고가용성이 아니라 생명주기 분리**이기 때문이다. EC2를 버려도 원장이 남는다는 요구는 Single-AZ로 이미 충족된다. Multi-AZ 스탠바이는 비용을 두 배로 만들면서 이 요구에 아무것도 더하지 않는다 — 필요해지는 시점(실사용자 트래픽)에 무중단으로 켤 수 있으므로 지금 결정하지 않는다.

### 2. 캐시는 ElastiCache로 분리하고, 클라이언트는 TLS로 붙는다

`finplay-cache` — Redis OSS 7.1, `cache.t3.micro`, **복제본 1 + 다중 AZ + 자동 장애 조치**, private 서브넷, 전용 보안 그룹 `finplay-elasticache-sg`.

**여기는 RDS와 달리 복제본을 둔다.** 판단 근거가 다르기 때문이다 — Redis는 이 저장소에서 fail-open(장애 시 DB로 폴백)만 하는 것이 아니다. `PriceStore`는 시세의 유일한 저장소이고, ADR-0014의 감시 락과 ADR-0015의 조회 캐시 락은 fail-closed(락을 못 잡으면 그 틱을 건너뛴다)다. 즉 **Redis가 죽으면 폴백되는 것이 아니라 기능이 멈춘다.** RDS의 Single-AZ 논리(“가용성은 나중에”)를 여기에 그대로 복사하면 단일 노드 장애가 곧 서비스 정지가 된다.

**클라이언트는 `SPRING_DATA_REDIS_SSL_ENABLED=true`로 붙는다.** ElastiCache의 전송 중 암호화를 켜면 서버가 TLS 핸드셰이크를 요구하는데, Lettuce 기본 설정은 평문으로 접속하므로 **TCP는 연결되고 Redis 핸드셰이크만 타임아웃된다**(2026-08-11 실측: `RedisCommandTimeoutException: Connection initialization timed out after 2 second(s)`). DNS·보안그룹·포트가 전부 정상이라 네트워크 문제로 오진하기 쉬운 증상이므로 이 값을 배포 필수 환경변수로 못박는다.

### 3. 업로드 파일은 S3로 옮긴다

`FileStorageService`의 새 구현체 `S3FileStorageService`를 추가하고 배포 프로필에서 `LocalFileStorageService` 대신 쓴다. 인터페이스(`store`/`load`/`delete`)는 바꾸지 않는다 — 022 plan이 이 교체를 예상하고 설계한 경계를 그대로 쓴다.

이로써 `compose.deploy.yaml`의 `app` 서비스에 이미지 볼륨이 없어 재배포마다 업로드 파일이 유실되던 문제도 함께 사라진다. **볼륨 마운트를 추가해 고치지 않는다** — 볼륨을 붙이면 그 파일이 다시 인스턴스에 묶여 이 ADR의 목적을 되돌린다.

### 4. 배포는 블루-그린으로 한다

같은 EC2에서 blue(8081)·green(8082) 두 스택을 번갈아 띄우고 ALB의 두 타깃 그룹으로 전환한다. 새 스택이 헬스체크를 통과한 뒤에만 트래픽을 옮기고, 이전 스택은 롤백 경로로 잠시 남긴다.

**ALB는 무중단만을 위한 것이 아니다.** ACM 인증서를 ALB에 붙이면 HTTPS가 해결되고, 그것이 지금 막혀 있는 **카카오·네이버 OAuth 로그인을 여는 유일한 경로**다 — `OAuthStateCookieFactory`가 `prod`에서 `OAUTH_STATE_COOKIE_SECURE=false`를 fail-fast로 거부하고(2026-07-31 실측, `docs/agent-mistakes.md`), 브라우저는 `http://`에서 `Secure` 쿠키를 저장하지 않는다. 즉 HTTPS 없이는 OAuth가 원리적으로 불가능하다. 무중단 배포와 OAuth 활성화가 같은 하나의 인프라(ALB + ACM)로 동시에 풀린다.

### 5. 네트워크 경계는 보안 그룹 참조로 정의한다

RDS·ElastiCache는 **public 서브넷에 두지 않는다.** 각 전용 보안 그룹의 인바운드 소스는 CIDR이 아니라 **EC2의 보안 그룹 ID**로 지정한다. 블루·그린 인스턴스가 몇 대로 늘어나도 같은 보안 그룹만 달면 접근 규칙을 다시 만들 필요가 없다 — 이 참조 방식이 "인스턴스는 갈아 끼우는 것"이라는 전제와 맞는 유일한 형태다.

기본 VPC 보안 그룹(`default`)을 재사용하지 않는다. 실제로 RDS 생성 시 `default`가 자동 선택돼 EC2에서 3306 접속이 실패한 일이 있었다(2026-08-11) — 콘솔 기본값이 이 규칙과 반대 방향이므로 생성 후 반드시 확인한다.

### 6. 이 ADR이 결정하지 않는 것

- **오토스케일링·ASG**: 블루-그린은 인스턴스를 버릴 수 있게 만들지만 자동으로 늘리지는 않는다. 상시 다중 인스턴스 운영은 별도 결정이다.
- **스케줄러 인스턴스 분리**: 다중 인스턴스가 되면 `@Scheduled` 배치를 전용 인스턴스로 뺄지, ADR-0014의 Redis 락에 계속 의존할지 판단이 필요하다. 지금은 락에 의존하는 현 구조를 유지한다.
- **RDS 백업·복구 정책의 상세**: 자동 백업 보존 기간·시점 복구 운용은 실사용자 트래픽 이전에 별도로 정한다.

## 결과

**좋은 점**

- **EC2를 버려도 원장·캐시·업로드 파일이 남는다.** 이 팀이 실제로 겪은 데이터 유실이 같은 원인으로 재발할 수 없는 구조가 된다.
- ADR-0014·0015·0018이 전제로만 갖고 있던 "다중 인스턴스"가 **배포에서도 성립하게 된다.** 세 ADR의 Redis 락·pub/sub은 공유 Redis가 있어야 작동하는데, 그 공유 Redis가 이제 실재한다.
- ALB + ACM으로 **HTTPS가 붙어 카카오·네이버 OAuth 로그인이 열린다** — 무중단 배포의 부산물이 아니라 이 결정의 명시적 목표 중 하나다.
- 백업·패치·페일오버가 관리형 서비스로 넘어가 팀이 운영해야 할 것이 줄어든다. mysql 컨테이너의 `MYSQL_ROOT_PASSWORD` 같은 배포 전용 시크릿이 하나 사라진다.
- Redis 복제본 + 자동 장애 조치로 `PriceStore`·감시 락처럼 폴백이 없는 경로가 단일 노드 장애에 정지하지 않는다.

**받아들이는 대가**

- **비용이 늘어난다.** EC2 한 대 안에 있던 mysql·redis가 각각 과금되는 서비스가 된다(`db.t4g.micro` + `cache.t3.micro` × 2노드). 프리 플랜 크레딧 소진 속도가 빨라지므로 예산 알림을 유지한다.
- **로컬 개발과 배포의 구성이 갈라진다.** 로컬은 여전히 `compose.yaml`의 컨테이너 mysql·redis를 쓰고(`spring-boot-docker-compose`), 배포만 관리형 서비스다. TLS 설정처럼 **배포에서만 필요한 값**이 생기며, 이 차이는 로컬에서 재현되지 않는다.
- **AWS 콘솔 설정이 문서에 없으면 복원할 수 없는 상태가 된다.** 서브넷 그룹·보안 그룹·암호화 옵션은 코드가 아니라 콘솔에 있다(IaC를 도입하지 않았다). 이 ADR과 010 spec의 기술이 사실상 유일한 정본이다.
- **ElastiCache의 전송 중 암호화 여부는 생성 후 변경할 수 없다.** 클러스터를 다시 만들지 않는 한 클라이언트가 TLS로 맞추는 것 외의 선택지가 없다.
- `docs/specs/022-community-enhancement/plan.md`의 로컬 저장 결정을 뒤집으므로, `S3FileStorageService` 구현과 기존 업로드 파일 이관이 **별도 작업으로 반드시 뒤따라야 한다.** 그 전까지 재배포 시 업로드 이미지 유실은 남아 있다.

## 대안과 기각 사유

**(a) EC2 안 컨테이너를 유지하고 볼륨 스냅샷 백업만 추가한다**

가장 싸고 변경이 적다. 그러나 백업은 **유실 후 복구**를 줄일 뿐 유실 자체를 막지 못하고, 블루-그린의 "인스턴스를 버릴 수 있다"는 전제를 여전히 세울 수 없다. 인스턴스 교체마다 DB를 복원하는 절차가 배포 경로에 들어가면 그것은 무중단 배포가 아니다. 기각.

**(b) DB만 RDS로 빼고 Redis는 EC2 컨테이너로 남긴다**

비용이 덜 늘어난다. 그러나 ADR-0014·0015·0018이 요구하는 것은 **인스턴스 간 공유 Redis**다 — 인스턴스마다 별개 Redis를 보면 분산 락은 락이 아니고 pub/sub 팬아웃은 자기 자신에게만 간다. 세 ADR을 전부 무력화하면서 그 사실이 로그에 드러나지도 않는다(락은 항상 성공하고 push는 조용히 일부만 간다). 기각.

**(c) ElastiCache 대신 별도 EC2에 Redis를 직접 띄운다**

관리형 서비스 비용을 피하면서 공유 Redis 요구는 만족한다. 그러나 앱 EC2가 아닌 또 하나의 EC2를 사람이 운영하게 된다(패치·모니터링·페일오버 수동). 인스턴스를 버릴 수 있게 만들려는 결정에서 **버릴 수 없는 인스턴스를 하나 더 만드는 것**은 방향이 반대다. 기각.

**(d) 블루-그린 없이 재배포 다운타임을 감수한다**

`docker compose up -d --build`로 40초 안팎 멈추는 것을 그대로 받아들이는 안이다. 그러나 상태 분리(1~3번)를 하고 나면 블루-그린에 추가로 필요한 것은 ALB와 포트가 다른 compose 파일 하나뿐이라 한계 비용이 작다. 무엇보다 **ALB는 HTTPS(ACM) 때문에 어차피 필요하다** — OAuth를 열려면 ALB를 세워야 하고, 세우고 나면 타깃 그룹을 하나 더 만드는 것이 블루-그린의 전부다. 기각.

**(e) S3 대신 EFS를 여러 인스턴스에 마운트한다**

`LocalFileStorageService`의 `Path` 기반 코드를 그대로 두고 마운트만 바꾸면 되므로 구현이 가장 적다. 그러나 `FileStorageService` 인터페이스가 이미 추상화를 제공하므로 구현체 교체 비용이 애초에 크지 않고, EFS는 정적 파일 서빙에 S3보다 비싸며 CDN 연결 경로도 자연스럽지 않다. 기각.

## 후속

- `S3FileStorageService` 구현과 기존 로컬 업로드 파일의 S3 이관은 **별도 이슈**로 분리한다. 이 ADR은 방향만 결정하며, 그 작업 전까지 `docs/specs/022-community-enhancement/plan.md`의 로컬 저장 전제가 코드에 남아 있다.
- ALB·타깃 그룹·ACM 인증서 발급과 `compose.bluegreen.yaml` 작성은 **별도 이슈**다. 이 ADR은 그 구성을 요구할 뿐 절차를 정의하지 않는다.
- RDS Single-AZ는 실사용자 트래픽이 붙는 시점에 Multi-AZ 전환을 재검토한다 — 무중단으로 켤 수 있으므로 지금 결정하지 않는다.
- 다중 인스턴스를 실제로 상시 운영하게 되면 ADR-0014의 `watch-lock-ttl-seconds`, ADR-0015의 `lock-ttl-millis`·`wait-millis` 기본값을 실측으로 조정한다 — 세 ADR 모두 "다중 인스턴스 배포 후 실측해 조정한다"를 미해결로 남겨 뒀다.
- ElastiCache 페일오버 순간의 락·pub/sub 유실 가능성은 ADR-0018 §후속이 남긴 재검토 대상이다. 복제본을 둔 지금이 그 조건에 해당하므로, 실제 페일오버를 한 번 관측할 기회가 생기면 그때 확인한다.

# Spec: 요약·브리핑 조회 캐시 (이슈 #245)

## 개요

종목 뉴스 요약과 개장 전 브리핑은 **전 회원이 같은 값을 본다.** 요약은 `(종목, 거래일, 범위)`마다 한 벌, 브리핑은 시장마다 한 벌인데 지금은 조회할 때마다 DB로 간다. 회원이 1,000명이면 같은 행을 1,000번 읽는다. 조회 경로에 LLM 호출은 0건이라 느리지는 않지만(전부 배치 안에 있다), 내용이 하루 한두 번만 바뀌고 모두가 같은 값을 보므로 캐시 조건으로는 이보다 좋을 수 없다.

**캐시를 얹는 순간 지금은 없는 문제가 생긴다.** 현재 구조에는 만료라는 개념 자체가 없어 쏠림이 성립하지 않지만, TTL이 붙으면 만료 찰나에 들어온 요청이 전부 원본으로 내려간다. 이 spec은 캐시 도입과 그 방어를 함께 다룬다.

## 설계는 ADR-0015에서 이미 확정됐다

**`docs/adr/0015-feedback-query-cache.md`(상태: 승인됨)가 이 기능의 설계 정본이다.** 이 spec은 그 8개 결정을 요구사항·완료 조건 형태로 옮긴 것이며, 여기서 설계를 다시 정하지 않는다. ADR과 어긋나는 구현이 필요해지면 구현하지 말고 새 ADR을 제안한다(CLAUDE.md 규칙 2).

| ADR-0015 결정 | 이 spec에서의 위치 |
|---|---|
| 1. 캐시 대상은 **시각 비의존 조각**만 — 캐시 5종 | 요구사항 CACHE-001, 비즈니스 규칙 §1 |
| 2. TTL은 고정 상수가 아니라 **다음 갱신 시점까지 남은 시간**을 매 저장마다 계산 | 요구사항 CACHE-002 |
| 3. **음성 결과 미캐시** + 코인 배치가 실제 갱신에 성공했을 때만 무효화 | 요구사항 CACHE-003 |
| 4. 쏠림 방어는 **Redis 분산 락**, `CryptoWatchLock`에서 `RedisLock` 추출, 실패 시 대기 후 타임아웃이면 **DB 직행(fail-open)** | 요구사항 CACHE-004 |
| 5. **Spring 캐시 추상화를 도입하지 않는다** — `FeedbackQueryCache` 한 클래스가 전담 | 요구사항 CACHE-005 |
| 6. **Redis 장애는 전부 삼켜 캐시 미스로 취급** | 요구사항 CACHE-006 |
| 7. 키는 `feedback:query-cache:...`, 락은 `feedback:query-cache:lock:...` | 비즈니스 규칙 §5 |
| 8. **스키마 변경 없음**(Flyway 마이그레이션 없음) | 범위 제외 |

## 왜 응답 전체를 캐시하지 않는가 (이 spec의 핵심 판단)

"전 회원이 같은 값을 본다"가 **응답 전체에는 성립하지 않는다.** 일부가 `now`의 함수다.

| 경로 | `items` | 요약·브리핑 텍스트 |
|---|---|---|
| 주식 요약 (`InstrumentNewsQueryService`) | **시각 의존** — 상한이 `now`라 09:00~15:30 동안 매 순간 넓어진다. 이 상한이 §C-5 노출 게이트 그 자체다 | 비의존 |
| 주식 브리핑 (`MarketBriefingService`) | **비의존** — 구간이 `[D-1 15:30, D 09:00]` 고정이다(FEED-009) | 비의존 |
| 코인 요약·브리핑 | **시각 의존** — `[now-24h, now]` 롤링(FEED-008) | 비의존 |

**시각 의존 목록을 캐시하면 계약이 바뀐다.** 주식 요약 `items`를 캐시하면 노출 게이트가 늦게 열리고, 코인은 "`items`의 24시간 창은 조회 시각 기준"(FEED-008)이 깨진다. 그래서 캐시 대상은 시각 비의존 조각 5개뿐이다.

## PRD 대조

- 이 기능은 **PRD의 새 요구사항이 아니라** 이미 **완료**인 FEED-008(종목 뉴스 요약)·FEED-009(개장 전 브리핑)의 **조회 성능 개선**이다. 두 경로의 응답 계약은 한 글자도 바뀌지 않는다(ADR-0015 §결과).
- 따라서 **`docs/prd.md` §3 "구현 현황" 표를 갱신하지 않는다** — CLAUDE.md 규칙 10의 "갱신 비대상: 제공하는 기능이 그대로인 변경"에 해당한다. `docs/specs/012-ai-feedback/plan.md`의 8개 분할 진행 상태 표에도 넣지 않는다(이슈 #245 본문 명시 — 그 분할에 없는 별도 이슈다).
- PRD에 대응 ID가 없으므로 이 spec 로컬 식별자 **`CACHE-001~006`**(PRD 미등재)을 쓴다. 023-watchlist가 `WATCH-001`을 쓴 것과 같은 방식이다.
- **PRD §10의 "빗썸 레이트리밋 Decision Gate"(관측 전에 임의의 캐시 계층이나 TTL 숫자를 넣지 않는다)는 이 이슈의 대상이 아니다** — 그 게이트는 코인 차트의 외부 빗썸 REST 호출(MKT-008·MKT-010)을 다룬다. 다만 그 게이트가 경계한 "임의의 TTL 숫자"는 여기서도 피한다 — ADR-0015 §2가 도메인 경계 TTL을 고른 이유가 정확히 그것이다.
- **개선을 실측 없이 주장하지 않는다(C-005).** 완료 조건은 응답 속도가 아니라 **원본 호출 횟수**로 쓴다.

## 사용자 시나리오

- 회원은 종목 뉴스 요약을 조회한다. 여러 회원이 같은 종목·같은 거래일·같은 범위를 조회하면 서버는 요약 텍스트를 **DB에서 한 번만 읽는다.** (CACHE-001)
- 회원은 개장 전 브리핑을 조회한다. 같은 거래일이면 서버는 브리핑 텍스트와 `items`를 **DB에서 한 번만 읽는다.** (CACHE-001)
- 회원이 장 마감 전(15:30 이전)과 이후에 같은 종목을 조회하면 **서로 다른 요약**을 본다 — 캐시가 범위 전환에서 갈린다. (CACHE-002)
- 코인 배치가 매시 05분에 요약·브리핑을 새로 만들면, 그 직후 조회한 회원은 **새 값**을 본다. 옛 값이 남지 않는다. (CACHE-003)
- 만료 순간에 회원 여러 명이 동시에 같은 조회를 해도 서버는 **원본을 한 번만** 읽는다. (CACHE-004)
- Redis가 죽어도 회원의 조회는 **평소처럼 200으로 성공한다.** 느려질 뿐 실패하지 않는다. (CACHE-006)

## 요구사항

### CACHE-001 — 시각 비의존 조각 5종을 캐시한다

- [ ] 아래 5개 항목이 캐시되고, 캐시 적중 시 해당 원본 DB 조회가 일어나지 않는다.

| 캐시 항목 | 키 축 | 값 |
|---|---|---|
| 주식 요약 텍스트 | `(instrumentId, originTradeDate, scope)` | 요약 문자열 |
| 코인 요약 텍스트 | `(instrumentId)` | 요약 문자열 |
| 주식 브리핑 텍스트 | `(originTradeDate)` | 브리핑 문자열 |
| 주식 브리핑 `items` | `(originTradeDate, 목록 절단 상한)` | `BriefingNewsItem` 목록 |
| 코인 브리핑 텍스트 | (단일 키) | 브리핑 문자열 |

- [ ] **캐시된 목록의 길이가 설정과 어긋나지 않는다.** 목록 절단 상한을 바꾸면 그다음 조회부터 새 길이가 나온다 — 옛 길이 목록이 만료까지 남지 않는다. 절단 상한이 키 축에 들어가는 이유이며, 예외도 로그도 없이 화면 목록 길이만 틀리는 종류의 결함을 막는다.
- [ ] **주식 요약 `items`와 코인 `items`는 캐시하지 않는다.** 매 요청 DB로 간다 — 그 구간 질의가 §C-5 노출 게이트의 구현이라 캐시하면 게이트가 늦게 열린다.
- [ ] 두 조회 API의 **응답 계약이 바뀌지 않는다.** 상태값(`NOT_YET`/`EMPTY`/`UNAVAILABLE`/`READY`) 판정 순서와 결과가 캐시 적중·미적중에 관계없이 같다.

### CACHE-002 — 만료는 도메인 경계 TTL이다

- [ ] TTL은 고정 상수가 아니라 **"다음 갱신 시점까지 남은 시간"**을 매 저장마다 계산한다. 임의의 숫자(예: 60초)를 고르지 않는다.
- [ ] 주식은 다음 범위 전환·다음 배치, 코인은 **다음 정시 05분**(`feedback.batch.crypto-cron`)이 경계다.
- [ ] 주식 요약은 `scope`가 키에 있으므로 **장 마감 전후 범위 전환에서 캐시가 자동으로 갈린다** — 같은 종목·같은 거래일인데 15:30 전후 내용이 다르다.
- [ ] **지터를 넣지 않는다.** 경계를 넘겨 캐시하면 옛 값이 노출되기 때문이며, 대신 CACHE-004의 방어를 필수로 둔다.

### CACHE-003 — 음성 결과 미캐시 + 코인 배치 무효화

- [ ] **`READY`만 캐시한다.** 행이 없거나(`EMPTY`) 서술이 없는(`UNAVAILABLE`) 결과는 캐시하지 않는다 — 배치가 아직 안 돈 시각의 "없음"을 캐시하면 배치가 만든 뒤에도 옛 상태가 남는다.
- [ ] **주식은 무효화가 필요 없다.** 생성 경로가 이미 있는 행을 건너뛰므로 한 번 생긴 값은 그날 안 바뀐다.
- [ ] **코인은 배치가 실제 갱신에 성공했을 때만 해당 키를 무효화한다.** 갱신을 건너뛴 경우(새 기사 없음·창 안 기사 0건)는 무효화하지 않는다.
- [ ] 코인 배치가 새 요약·브리핑을 만든 직후 조회하면 **새 값**이 나온다.

### CACHE-004 — 쏠림 방어는 Redis 분산 락이고 fail-open이다

- [ ] 캐시 미스 시 분산 락을 시도하고, 획득한 요청만 원본을 읽어 캐시를 채운다.
- [ ] 락 획득에 실패한 요청은 **폴링하며 대기**하다가 캐시가 채워지면 그 값을 쓴다.
- [ ] **대기가 타임아웃이면 원본(DB)으로 직행한다(fail-open).** 락을 못 얻었다고 조회를 실패시키지 않는다 — 이슈 #244가 "얻지 못하면 이번 틱을 건너뛴다"였던 것과 갈리는 지점이며, 배치와 조회의 성격 차이에서 온다.
- [ ] 락 메커니즘은 `CryptoWatchLock`에서 **`RedisLock`으로 추출**하고 양쪽이 그 위에 얹힌다. `CryptoWatchLock`을 그대로 재사용하지 않는다(키 접두사와 TTL 45초가 코인 감시 전용이다).
- [ ] **#244(ADR-0014)의 코인 감시 동작이 그대로 유지된다** — 기존 테스트가 한 건도 수정 없이 통과한다.

### CACHE-005 — Spring 캐시 추상화를 도입하지 않는다

- [ ] `@EnableCaching`·`@Cacheable`·`spring-boot-starter-cache`를 **쓰지 않는다.**
- [ ] 캐시 키 조립·TTL 계산·직렬화·락 게이트는 **`FeedbackQueryCache` 한 클래스**가 전부 갖고, 조회 서비스 두 곳은 `getOrLoad(키, 로더)` 형태로만 쓴다.

### CACHE-006 — Redis 장애에도 조회가 실패하지 않는다

- [ ] 캐시 조회·저장·락·무효화의 모든 Redis 접촉이 실패해도 **캐시 미스와 같게 취급해 원본으로 내려간다.**
- [ ] Redis가 완전히 죽은 상태에서 요약 조회·브리핑 조회가 **200과 정상 응답 본문**을 낸다.
- [ ] **캐시 계층을 재배포 없이 끌 수 있다(운영 킬 스위치).** 이 저장소의 첫 조회 경로 캐시이고 사용자가 기다리는 읽기 앞단에 새 계층이 들어가는데, 되돌아갈 폴백(DB 직행)은 이미 검증된 기존 경로다. 끈 상태에서도 두 조회의 응답이 지금과 동일하다. (완료 조건의 "캐시를 끈 대조군"을 운영 코드 경로 그대로 재현할 수 있는 것은 이 스위치의 부수 효과다.)

## 비즈니스 규칙

1. **캐시는 `now`의 함수가 아닌 값만 담는다.** 어떤 캐시 값도 조회 시각에 따라 달라지면 안 된다 — 달라지는 값을 담는 순간 §C-5 노출 게이트(주식)나 FEED-008의 24시간 창(코인) 계약이 깨진다.
2. **캐시는 부가물이지 정본이 아니다.** 정본은 항상 MySQL이며, 캐시가 없거나 Redis가 죽으면 원본으로 간다. 캐시가 없어서 장애가 되는 경로를 만들지 않는다.
3. **음성 상태(값 없음)는 캐시하지 않는다.** "아직 없다"를 캐시하면 배치가 만든 뒤에도 화면이 옛 상태를 본다.
4. **조회 경로는 아무것도 쓰지 않는다**(기존 규칙 유지, FEED-008·FEED-009). 캐시 저장은 DB 쓰기가 아니므로 이 규칙과 충돌하지 않으나, GET이 LLM을 호출하거나 MySQL에 쓰는 일은 여전히 없다.
5. **키 네임스페이스는 `feedback:query-cache:`, 락은 `feedback:query-cache:lock:`이다.** `price:crypto:`·`candle:crypto:`·`ranking:`·`feedback:crypto-watch:lock:` 어느 것과도 겹치지 않는다.
6. **주문·체결·계좌·잔액·보유·손익 원장은 이 작업으로 변하지 않는다.** 이 spec은 읽기 경로만 건드린다.

## 범위 제외

이슈 #245 본문의 제외 범위를 그대로 옮긴다.

- **변동 원인 카드 조회와 매도 직후 피드백 조회.** 카드는 노출 게이트가 회원의 조회 시각에 걸려 캐시 키가 복잡하고, 매도 회고는 회원 개인 데이터라 공유 대상이 아니다. 필요하면 별도 이슈이며, 그때 **회원별 키가 성립하는지부터** 판단한다.
- **코인 감시 겹침 방어.** 이슈 #244에서 완료됐다(ADR-0014, PR #254). 이 spec은 그 결과물에서 `RedisLock`을 추출해 재사용할 뿐 감시 로직 자체를 바꾸지 않는다.
- **캐시 적중률 모니터링 도구 연동.** 지금은 로그·테스트로 충분하다.
- **DB 인덱스나 쿼리 튜닝.** 지금 조회는 인덱스로 덮여 있고 이 이슈의 관심사가 아니다.
- **스키마 변경.** Redis만 쓴다 — Flyway 마이그레이션을 추가하지 않는다(ADR-0015 §8).
- **`docs/api-routes.md`·`docs/api-contracts.md` 수정.** controller 변경이 없고 조회 계약이 바뀌지 않는다(ADR-0015 §결과). 마무리 단계에서 동기화 모드가 다시 판단한다.
- **`docs/prd.md` §3 구현 현황 표, `docs/specs/012-ai-feedback/plan.md` 8개 분할 진행 상태 표.** 위 "PRD 대조" 참고.

## 완료 조건

원본 호출 횟수는 전부 **대조군과 함께** 확인한다 — 방어를 껐을 때 몇 번 불리는지 먼저 보이고, 켰을 때 몇 번인지 보인다. 방어를 켠 결과만 있으면 "캐시 덕인지 락 덕인지" 구분되지 않는다(PR #254 리뷰에서 실제로 받은 지적이다).

- [ ] **캐시 적중으로 원본 조회가 줄어든다** — 같은 요청을 여러 번 보내 원본 조회 횟수를 센다. 캐시 없이 N번 조회하면 원본 N회, 캐시가 있으면 1회다.
- [ ] **만료 쏠림이 막힌다** — 캐시가 빈 상태에서 동시 요청 N건을 보내면 원본 조회가 1회다. 방어를 끈 대조군에서는 같은 조건이 **N회로 재현된다.** 동시 요청은 `CyclicBarrier`로 스레드 겹침을 강제한다 — 순차 실행이면 아무것도 증명하지 못한다.
- [ ] **락을 못 얻은 요청이 타임아웃되면 DB로 직행한다(fail-open)** — 응답이 실패하지 않는다.
- [ ] **내용이 바뀌면 캐시도 바뀐다** — 코인 배치가 새로 만든 직후 조회하면 새 값이 나온다. 갱신을 건너뛴 배치 실행은 무효화하지 않는다.
- [ ] **주식의 범위 전환(장 마감 전후)에서 캐시가 올바르게 갈린다** — 같은 종목·같은 거래일인데 15:30 전후 요약이 다르다.
- [ ] **코인은 매시 갱신 주기와 어긋나지 않는다** — TTL이 다음 정시 05분을 넘지 않는다.
- [ ] **음성 결과가 캐시되지 않는다** — 요약 행이 없는 상태에서 조회한 뒤 배치가 행을 만들면, 그다음 조회가 새 값을 본다.
- [ ] **Redis가 죽어도 요약 조회·브리핑 조회가 200이다.**
- [ ] **기존 테스트가 전부 그대로 통과한다** — 특히 #244의 코인 감시 테스트가 수정 없이 통과한다.
- [ ] **조회 전후로 주문·체결·계좌·잔액·보유·손익 원장이 변하지 않는다.**
- [ ] `./gradlew build` 통과 (테스트 + 포맷 + 커버리지).

## 개요

인증 사용자가 본인 소유의 체결 1건에 투자일기 1건을 작성한다. 매수 체결에는 매수 회고를(JOUR-001, 구현 완료), 매도 체결에는 매도 회고를(JOUR-003, 구현 완료) 작성하고, 각각 본문을 수정할 수 있으며(JOUR-002·JOUR-004, 구현 완료), 본인이 쓴 회고를 한 목록으로 훑어볼 수 있다(JOUR-006, 구현 완료). 투자일기는 체결 이후의 기록이며 주문·체결·계좌·잔액·보유·FIFO lot·실현손익 원장을 변경하지 않는다. 이번 착수 범위는 **회고 1건을 단건으로 읽는 읽기 엔드포인트 2개**(JOUR-005 — 매수 회고용·매도 회고용)이며, AI 복기와 구조화 필드는 포함하지 않는다.

## 사용자 시나리오

- 사용자는 매수 체결 후 해당 체결에 투자일기 본문을 한 번 작성한다.
- 사용자는 매도 체결 후 해당 체결에 매도 회고 본문을 한 번 작성한다.
- 사용자는 자신이 쓴 매수 회고의 본문을 나중에 다시 고칠 수 있고, 횟수 제한 없이 여러 번 고칠 수 있다. **그 매수 체결의 일부 또는 전부를 이미 매도했더라도 마찬가지다.**
- 사용자는 아직 매수 회고를 쓰지 않은 매수 체결에 대해서는 수정할 것이 없다는 응답을 받는다.
- 사용자는 다른 사용자의 매수 회고를 수정할 수 없다.
- 사용자는 자신이 쓴 매도 회고의 본문을 나중에 다시 고칠 수 있고, 횟수 제한 없이 여러 번 고칠 수 있다.
- 사용자는 아직 매도 회고를 쓰지 않은 매도 체결에 대해서는 수정할 것이 없다는 응답을 받는다.
- 사용자는 다른 사용자의 매도 회고를 수정할 수 없다.
- 사용자는 매수 체결에는 매도 회고를, 매도 체결에는 매수 회고를 작성할 수 없다.
- 사용자는 다른 사용자의 체결에는 투자일기를 작성할 수 없다.
- 사용자는 같은 체결에 같은 종류의 투자일기를 다시 작성할 수 없다.
- 사용자는 같은 종목을 매수·매도했더라도 매수 회고와 매도 회고를 각각 별개로 작성한다.
- 사용자는 투자일기를 작성하지 않아도 매매·보유·커뮤니티 기능을 계속 사용할 수 있다.
- 사용자는 자신이 쓴 매수 회고와 매도 회고를 **한 목록에서 최신순으로** 훑어볼 수 있고, 목록의 각 항목이 매수 회고인지 매도 회고인지 구분할 수 있다.
- 사용자는 주식과 코인을 나눠서(`market`) 투자일기 목록을 본다. 거래내역·주문 목록과 같은 조회 방식이다.
- 사용자는 목록을 스크롤해 다음 페이지를 이어 받고, 페이지 경계에서 같은 회고를 두 번 보거나 빠뜨리지 않는다.
- 사용자는 다른 사용자의 투자일기를 목록에서 볼 수 없다.
- 아직 회고를 하나도 쓰지 않은 사용자는 오류가 아니라 빈 목록을 받는다.
- 사용자는 목록에서 고른 회고 1건의 전체 내용을 단건으로 열어 본다. 목록 항목이 매수 회고면 매수 상세 경로로, 매도 회고면 매도 상세 경로로 연다.
- 사용자는 수정 화면을 열기 전에 지금 저장돼 있는 본문을 단건 조회로 그대로 읽어온다.
- 사용자는 아직 회고를 쓰지 않은 체결의 상세를 열면 "없다"는 응답을 받는다.
- 사용자는 다른 사용자의 투자일기를 단건으로도 열 수 없다.

## 요구사항

### JOUR-001 매수 투자일기 작성 (1차 착수, 구현 완료)

- [x] `POST /api/trades/{buyTradeId}/journal`로 투자일기를 작성한다.
- [x] `buyTradeId`가 존재하는 매수 체결이며 인증 사용자 소유인지 검증한다.
- [x] 매수 체결 1건당 투자일기 1건만 존재한다 (`UNIQUE(buy_trade_id)`).
- [x] 이미 투자일기가 존재하면 409 `DUPLICATE_RESOURCE`로 거부한다.
- [x] 본문은 공백이 아닌 텍스트여야 하며, 목표가·손절가·예상보유기간 같은 별도 필드는 이번 계약에 포함하지 않는다.
- [x] 성공 시 투자일기 ID, 매수 체결 ID, 본문, 작성시각을 반환한다.

### JOUR-003 매도 투자일기 작성 (2차 착수, 구현 완료)

- [x] `POST /api/trades/{sellTradeId}/sell-journal`로 매도 회고를 작성한다.
- [x] `sellTradeId`가 존재하는 매도 체결이며 인증 사용자 소유인지 검증한다.
- [x] 매도 체결 1건당 매도 회고 1건만 존재한다 (`UNIQUE(sell_trade_id)`).
- [x] 이미 매도 회고가 존재하면 409 `DUPLICATE_RESOURCE`로 거부한다.
- [x] 본문은 공백이 아닌 텍스트여야 하며, 목표가·손절가·예상보유기간 같은 별도 필드는 이번 계약에 포함하지 않는다 (JOUR-001과 동일).
- [x] 성공 시 투자일기 ID, 매도 체결 ID, 본문, 작성시각을 반환한다.

### JOUR-004 매도 투자일기 수정 (3차 착수, 구현 완료)

- [x] `PATCH /api/trades/{sellTradeId}/sell-journal`로 이미 작성한 매도 회고의 본문을 수정한다.
- [x] `sellTradeId`가 존재하는 매도 체결이며 인증 사용자 소유인지 검증한다 (JOUR-003과 같은 404·403·400 매핑).
- [x] 해당 매도 체결에 매도 회고가 아직 없으면 404 `NOT_FOUND`로 거부한다. 수정 요청으로 새 회고를 만들지 않는다(upsert 금지).
- [x] 수정 가능한 필드는 본문(`content`) 하나뿐이다. 본문은 작성과 같은 검증(공백 아닌 텍스트, 같은 길이 상한)을 받는다.
- [x] **매도 회고에는 수정 잠금 조건을 두지 않는다** — 아래 §비즈니스 규칙의 "매도 회고 수정 잠금 없음" 항목이 근거이며, 이 판단은 PR 본문에도 남긴다.
- [x] 수정 시각을 기록하고, 성공 시 투자일기 ID, 매도 체결 ID, 본문, 작성시각, 수정시각을 반환한다.
- [x] 수정 성공·실패는 매수 회고(JOUR-001) 계약과 데이터에 영향을 주지 않는다.

### JOUR-002 매수 투자일기 수정 (4차 착수, 구현 완료)

- [x] `PATCH /api/trades/{buyTradeId}/journal`로 이미 작성한 매수 회고의 본문을 수정한다.
- [x] `buyTradeId`가 존재하는 매수 체결이며 인증 사용자 소유인지 검증한다 (JOUR-001과 같은 404·403·400 매핑).
- [x] 해당 매수 체결에 매수 회고가 아직 없으면 404 `NOT_FOUND`로 거부한다. 수정 요청으로 새 회고를 만들지 않는다(upsert 금지).
- [x] 수정 가능한 필드는 본문(`content`) 하나뿐이다. 본문은 작성과 같은 검증(공백 아닌 텍스트, 같은 길이 상한)을 받는다.
- [x] **매수 회고에도 수정 잠금 조건을 두지 않는다** — 해당 매수 lot에 매도 배분(`trade_allocations`)이 있든 없든, 전량 매도됐든 항상 수정할 수 있다. 근거는 아래 §비즈니스 규칙의 "매수 회고 수정 잠금 없음"이며, 이 판단은 PR 본문에도 남긴다.
- [x] 수정 시각을 기록하고, 성공 시 투자일기 ID, 매수 체결 ID, 본문, 작성시각, 수정시각을 반환한다.
- [x] 수정 성공·실패는 매도 회고(JOUR-003·004) 계약과 데이터에 영향을 주지 않는다.

### JOUR-006 투자일기 목록 조회 (5차 착수, 구현 완료, 이슈 #203)

- [x] `GET /api/journal?market=&cursor=&limit=`로 인증 사용자 본인의 투자일기 목록을 조회한다.
- [x] 매수 회고(`buy_trade_journals`)와 매도 회고(`sell_trade_journals`)를 **한 목록에 섞어** 반환한다. 두 종류를 따로 조회하는 엔드포인트를 만들지 않는다.
- [x] `market`은 **필수** 파라미터다. `STOCK`|`CRYPTO` 리터럴만 허용하며, 두 시장을 합친 통합 조회는 이번 범위에 없다 (PORT-002 `GET /api/trades`·PORT-003 `GET /api/orders`와 동일).
- [x] **커서 기반 페이지네이션**을 쓰고 최신순으로 정렬한다. `cursor`·`limit`은 선택이며 `limit` 기본 20, 1~100 범위를 벗어나면 클램핑 없이 400 `VALIDATION_ERROR`로 거부한다 (형제 API와 동일 규칙).
- [x] **정렬 기준은 `createdAt`(회고를 처음 쓴 시점) 내림차순**이며, 동시각 동점은 체결 ID 내림차순으로 끊는다. `updatedAt` 기준으로 정렬하지 않는다 — 방금 수정한 오래된 회고가 목록 맨 위로 튀어 "최신순"의 의미가 흔들린다.
- [x] 각 항목은 회고 종류(`journalType`: `BUY`|`SELL`)와 **원래 체결 ID**(`buyTradeId` 또는 `sellTradeId` 중 해당하는 쪽)로 식별한다. **통합 `journalId`를 노출하지 않는다** — JOUR-005의 식별자 체계를 선점하지 않기 위해서다.
- [x] **항목 필드는 `journalType`·`buyTradeId`·`sellTradeId`·`content`·`createdAt`·`updatedAt` 6개 고정**이다. 매수 항목은 `sellTradeId`가, 매도 항목은 `buyTradeId`가 `null`이다. 종목·가격·수량·실현손익 등 체결 정보는 넣지 않는다(`GET /api/trades`가 정본). wrapper는 형제 API와 같은 `content`·`nextCursor`·`hasNext` 3필드다.
- [x] 다른 사용자의 투자일기는 목록에 섞이지 않는다. 조회 대상은 요청 파라미터가 아니라 Access Token의 인증 사용자로 결정한다.
- [x] 투자일기가 하나도 없으면 오류가 아니라 빈 목록(`content: []`, `nextCursor: null`, `hasNext: false`)을 반환한다.
- [x] 조회는 **읽기 전용**이다. 주문·체결·계좌·잔액·보유·FIFO lot·실현손익 원장은 물론 투자일기 자체도 변경하지 않는다.

### JOUR-005 투자일기 상세 조회 (6차 착수, 완료, 이슈 #217)

- [x] `GET /api/journal/buy/{buyTradeId}`로 본인이 쓴 **매수 회고 1건**을 조회한다.
- [x] `GET /api/journal/sell/{sellTradeId}`로 본인이 쓴 **매도 회고 1건**을 조회한다.
- [x] **경로를 타입별로 분리한다.** 단일 경로 `GET /api/journal/{journalId}`를 만들지 않는다 — 두 회고 테이블이 각자 독립된 PK 시퀀스를 쓰기 때문에 숫자 하나만으로는 어느 테이블인지 정해지지 않는다. 근거는 아래 §비즈니스 규칙 "상세 조회는 타입별 경로로 분리한다"다.
- [x] 경로 변수는 회고 자체의 PK가 아니라 **그 회고가 달린 체결 ID**(`buyTradeId`/`sellTradeId`)다 — 작성·수정 계약 4개와 목록 항목이 이미 쓰고 있는 식별자를 그대로 쓴다.
- [x] 본인이 작성한 투자일기만 조회할 수 있다. 체결이 존재하지 않으면 404 `NOT_FOUND`, 타인 소유 체결이면 403 `FORBIDDEN`으로 거부한다 (JOUR-001·003과 동일한 매핑).
- [x] 체결은 있으나 그 체결에 회고가 아직 없으면 404 `NOT_FOUND`다 (수정 계약 JOUR-002·004와 동일).
- [x] 경로와 체결 구분이 어긋나면(매수 경로에 매도 체결 ID, 매도 경로에 매수 체결 ID) 400 `VALIDATION_ERROR`다. 검증 순서는 `체결 존재(404) → 소유(403) → 체결 구분(400) → 회고 존재(404)`로 **수정 계약과 같다**.
- [x] 응답 필드는 `journalId`·`buyTradeId`(매도는 `sellTradeId`)·`content`·`createdAt`·`updatedAt` **5개 고정**이다 — 같은 회고의 수정 응답(`BuyJournalUpdateResponse`·`SellJournalUpdateResponse`)과 필드 구성이 1:1로 같다. 종목·가격·수량·실현손익 등 체결 정보는 넣지 않는다(`GET /api/trades`가 정본).
- [x] 조회는 **읽기 전용**이다. 투자일기의 `updatedAt`은 조회로 바뀌지 않고, 원장도 읽기만 한다.
- [x] **스키마를 바꾸지 않는다** — 기존 두 테이블과 기존 리포지토리 조회 메서드(`findByBuyTradeId`·`findBySellTradeId`)를 그대로 쓴다. 신규 Flyway 마이그레이션이 없다.

## 비즈니스 규칙

- 본인의 체결에만 작성할 수 있다. 없는 체결은 404, 타인 체결은 403으로 거부한다.
- **체결 구분과 회고 종류가 맞아야 한다.** 매수 회고는 매수가 아닌 체결에, 매도 회고는 매도가 아닌 체결에 대해 400으로 거부한다.
- **검증 순서는 `존재(404) → 소유(403) → 체결 구분(400) → 중복(409)`으로 고정한다.** 타인 체결이면 그 체결의 매수·매도 속성을 오류로 흘리기 전에 403이 먼저다. 매수·매도 회고가 같은 순서를 쓴다.
- 투자일기 저장과 소유권·중복 검증은 한 트랜잭션에서 처리한다.
- 투자일기 작성 성공·실패는 주문·체결·계좌·잔액·보유·FIFO lot·실현손익을 변경하지 않는다.
- 동시 중복 작성은 애플리케이션 검증과 유니크 제약(`UNIQUE(buy_trade_id)`·`UNIQUE(sell_trade_id)`)으로 한 건만 성공시킨다.
- 투자일기는 원장(`trades`)을 **읽기만** 한다. 투자일기 쪽에서 체결·계좌·보유를 갱신하는 경로를 만들지 않는다.
- 매수 회고와 매도 회고는 서로의 존재를 검증 조건으로 삼지 않는다. 매수 회고 없이 매도 회고만 쓸 수 있고, 그 반대도 가능하다.

### 매도 회고 수정 (JOUR-004)

- **수정 검증 순서는 `체결 존재(404) → 소유(403) → 매도 여부(400) → 회고 존재(404)`로 고정한다.** 작성(JOUR-003)의 앞 3단계와 같고, 마지막 단계만 "중복이면 거부(409)"에서 "없으면 거부(404)"로 뒤집힌다. 타인 체결이면 그 체결에 회고가 있는지를 흘리기 전에 403이 먼저다.
- **수정은 본문 교체다.** 매도 체결 ID·작성시각·투자일기 ID는 바뀌지 않으며, 요청으로 지정할 수도 없다.
- **이미 배포된 작성 계약(`POST .../sell-journal`)의 응답 필드를 바꾸지 않는다.** 수정시각은 수정 응답에만 새로 등장한다 — 작성 응답에 필드를 더하면 JOUR-003을 쓰는 프론트엔드에 불필요한 변경이 번진다. 작성 직후 회고의 수정시각을 어떤 값으로 둘지(작성시각과 동일 / 비어 있음)는 `plan.md`가 컬럼 정의와 함께 정한다.
- **수정 횟수에 제한을 두지 않고, 수정 이력을 보관하지 않는다.** 마지막 본문 1건만 남는다 — PRD가 이력·버전 요구사항을 두지 않았고, 이력 테이블은 상세·목록(JOUR-005·006) 계약이 정해진 뒤에야 노출 방식을 정할 수 있다.
- **매도 회고 수정 잠금 없음 (JOUR-004 착수 결정, 2026-08-04).** PRD JOUR-004는 "후속 매도 배분에 의한 잠금 대상이 아니다. 그 외 잠금 조건이 필요한지는 착수 시 확정한다"고 남겼다. 이번 착수에서 **잠금 조건을 두지 않는 것으로 확정한다.** 근거는 셋이다.
  1. **잠금의 목적이 없다.** 매수 회고 잠금(JOUR-002)의 취지는 "매도 배분이 일어난 뒤 매수 시점의 판단을 사후 수정하지 못하게" 하는 것이었다(`005-order-sell/spec.md`. **그 매수 회고 잠금 자체도 2026-08-04 이슈 #197에서 철회됐다** — 아래 §매수 회고 수정 절 참고. 이 문단은 JOUR-004 착수 시점의 기록이다). 매도 회고는 매도 체결이 확정된 **뒤**의 기록이고, 그 매도 체결의 FIFO 배분·실현손익은 체결 시점에 이미 확정돼 이후 원장 이벤트로 바뀌지 않는다. 회고의 전제를 뒤집을 후속 사건 자체가 없다.
  2. **잠금 후보가 모두 아직 없는 기능에 걸려 있다.** 생각할 수 있는 조건(작성 후 N일 경과, AI 피드백 생성 후 잠금, 커뮤니티·랭킹 공개 후 잠금)은 각각 spec 012(AI 피드백)·JOUR-005·006(조회)·커뮤니티 공개 범위가 정해져야 판단할 수 있다. 지금 근거 없이 조건을 넣으면 실제 요구가 생기기 전에 계약이 굳는다.
  3. **되돌리기 비용이 비대칭이다.** "잠금 없음 → 잠금 추가"는 새 오류 코드·조건을 더하는 확장이지만, "잠금 있음 → 잠금 해제"는 이미 거부됐던 요청이 성공하게 되는 완화라 프론트엔드가 이미 대응한 오류 경로를 다시 걷어내야 한다.
  - **후속 조건**: 나중에 매도 회고를 입력으로 쓰는 AI 피드백(spec 012)이 붙으면, 잠금을 도입할지 피드백을 재생성할지는 **그 spec에서** 결정한다. 이번 계약은 그 결정을 앞당기지 않는다.
- 수정 성공·실패도 작성과 동일하게 주문·체결·계좌·잔액·보유·FIFO lot·실현손익 원장을 변경하지 않는다. 투자일기는 원장을 **읽기만** 한다.
- 수정 조회·검증·저장은 한 트랜잭션에서 처리한다. 같은 회고에 동시 수정이 들어오면 마지막 커밋이 남으며(last-write-wins), 별도 낙관적 락을 도입하지 않는다 — 본인만 수정할 수 있어 동시 편집자가 한 사람이다.

### 매수 회고 수정 (JOUR-002)

> 매도 회고 수정(JOUR-004)과 **같은 규칙**이 매수 체결 기준으로 그대로 적용된다. 아래는 그 대응 관계와, 매수 회고에만 있었던 잠금 게이트의 처리다.

- **수정 검증 순서는 `체결 존재(404) → 소유(403) → 매수 여부(400) → 회고 존재(404)`로 고정한다.** 작성(JOUR-001)의 앞 3단계와 같고, 마지막 단계만 "중복이면 거부(409)"에서 "없으면 거부(404)"로 뒤집힌다. 타인 체결이면 그 체결에 회고가 있는지를 흘리기 전에 403이 먼저다. JOUR-004와 대칭이며 3단계 조건만 `side == BUY`다.
- **수정은 본문 교체다.** 매수 체결 ID·작성시각·투자일기 ID는 바뀌지 않으며, 요청으로 지정할 수도 없다.
- **이미 배포된 작성 계약(`POST .../journal`)의 응답 필드를 바꾸지 않는다.** 수정시각은 수정 응답에만 새로 등장한다 — JOUR-004에서 `SellJournalResponse`(4필드)를 그대로 두고 `SellJournalUpdateResponse`(5필드)를 분리한 것과 같은 처리를 매수 회고에도 적용한다.
- **수정 횟수에 제한을 두지 않고, 수정 이력을 보관하지 않는다.** 마지막 본문 1건만 남는다 — PRD가 이력·버전 요구사항을 두지 않았고, 이력 테이블은 상세·목록(JOUR-005·006) 계약이 정해진 뒤에야 노출 방식을 정할 수 있다.
- **매수 회고 수정 잠금 없음 (JOUR-002 착수 결정, 2026-08-04, 이슈 #197).** `005-order-sell/spec.md`는 "첫 매도 배분이 발생한 매수 lot은 투자일기 수정이 잠긴다"고 규정했고 PRD는 그 판정 시점·조건·오류 코드(`JOURNAL_LOCKED` 예정)를 Decision Gate로 남겨 두었다. 이번 착수에서 **잠금을 두지 않는 것으로 확정하며, 이 결정이 위 두 문서의 잠금 규정을 대체한다**(PRD JOUR-002·`005-order-sell/spec.md` §비즈니스 규칙 모두 이 결정으로 갱신했다). 근거는 셋이다.
  1. **잠금이 보호할 소비자가 없다.** 투자일기 본문을 실제로 읽어 무언가에 쓰는 기능이 현재 하나도 없다. 랭킹(RANK-001)은 `accounts.realized_pnl` 원장 기준이라 투자일기와 무관하고, AI 피드백·주간/월간 리포트(spec 012)는 미구현이다. 소비자가 없는 상태에서 보호 장치부터 만드는 건 가상의 미래 요구사항을 위한 설계다.
  2. **"첫 매도 배분"은 틀린 트리거였다.** 사후 왜곡(hindsight bias)은 매도 여부와 무관하게 발생한다 — 팔지 않고 계속 보유만 해도 주가 변동을 보면서 회고를 사후에 다시 쓸 수 있다. `trade_allocations` 기반 잠금은 실제 위협과 상관없는 대리 신호에 걸려 있었다.
  3. **되돌리기 비용이 비대칭이다.** "잠금 없음 → 잠금 추가"는 새 오류 코드·조건을 더하는 확장이지만, "잠금 있음 → 잠금 해제"는 이미 거부됐던 요청이 성공하게 되는 완화라 프론트엔드가 이미 대응한 오류 경로를 다시 걷어내야 한다. JOUR-004가 같은 근거로 잠금 없이 확정됐고, 두 회고의 수정 계약이 대칭이 된다.
  - **"영구히 없음"이 아니라 "지금은 없음"이다.** 이 서비스는 교육용 모의투자이고 투자일기로 얻는 외부적 이득(랭킹 반영 등)이 없어 사용자가 자기 데이터를 훼손할 유인이 약하다. 향후 AI 피드백·리포트가 투자일기 본문을 실제로 읽어 분석하게 되면 **그 기능의 스펙에서** "피드백·리포트 생성 시점 기준으로 직전/직후 수정을 제한한다" 같은 규칙을 정의한다. 잠금 트리거는 매도 이벤트가 아니라 **피드백 생성 이벤트**에 묶는 것이 설계 방향이며, 이번 범위에서는 구현하지 않고 방향만 남긴다.
- 수정 성공·실패도 작성과 동일하게 주문·체결·계좌·잔액·보유·FIFO lot·실현손익 원장을 변경하지 않는다. 특히 **`holding_lots`·`trade_allocations`를 읽지도 않는다** — 잠금이 없으므로 배분 데이터를 판정에 쓸 이유가 없다.
- 수정 조회·검증·저장은 한 트랜잭션에서 처리한다. 동시 수정은 last-write-wins이며 낙관적 락을 두지 않는다(JOUR-004와 동일 — 본인만 수정할 수 있어 동시 편집자가 한 사람이다).

### 투자일기 목록 조회 (JOUR-006)

- **JOUR-005 식별자 게이트를 선점하지 않는다 (JOUR-006 착수 결정, 2026-08-04, 이슈 #203).** 목록 항목은 `journalType`(`BUY`|`SELL`)과 그 회고가 달린 **체결 ID** 한 개(`buyTradeId` 또는 `sellTradeId`, 해당하지 않는 쪽은 `null`)로만 식별한다. 근거는 둘이다.
  1. **통합 `journalId`는 아직 정의되지 않은 값이다.** `buy_trade_journals.id`와 `sell_trade_journals.id`는 서로 다른 시퀀스라 값이 겹친다. 어느 한쪽 PK를 `journalId`라는 이름으로 노출하면, JOUR-005가 나중에 "두 테이블을 합친 새 식별자 체계"를 택할 때 **같은 이름이 다른 값을 가리키게 되는 breaking change**가 된다.
  2. **체결 ID는 이미 확정된 식별자다.** 매수·매도 회고 작성·수정 계약 4개가 모두 `/api/trades/{tradeId}/...` 경로를 쓰고 응답에 `buyTradeId`·`sellTradeId`를 담고 있다. 목록이 같은 값을 그대로 쓰면 프론트엔드는 목록 → 수정 화면을 이미 있는 계약만으로 연결할 수 있고, JOUR-005가 어떤 URL을 택하든 이 항목 필드는 그대로 유효하다.
  - **후속 조건**: JOUR-005 착수 시 상세 조회 URL이 정해지면, 목록 항목에 그 리소스를 가리키는 식별자를 **추가**할 수 있다. 이번 계약의 필드는 제거하지 않는다(추가는 확장, 제거·의미 변경은 breaking).
- **정렬 키는 `(createdAt, 체결 ID)` 내림차순이고, 커서 문자열은 `{createdAt}_{tradeId}` 형식이다.** 형제 API(`GET /api/trades`·`GET /api/orders`)의 `{ISO_LOCAL_DATE_TIME}_{id}` 형식과 같고, 파싱 실패는 같은 400 `VALIDATION_ERROR`다. **동점 tie-break에 회고 PK를 쓰지 않고 체결 ID를 쓰는 이유**는 두 테이블을 합친 목록에서 회고 PK는 값이 겹쳐 순서가 유일하게 정해지지 않기 때문이다. 반면 체결 ID는 `trades` 한 테이블에서 채번되고, 한 체결에는 그 체결 구분에 맞는 회고가 최대 1건뿐이라(`UNIQUE(buy_trade_id)`·`UNIQUE(sell_trade_id)`, 매수 체결에는 매도 회고를 쓸 수 없음) 합친 목록에서도 유일하다 — 커서가 가리키는 위치가 항상 한 곳이라 페이지 경계에서 중복·누락이 없다.
- **`market` 필터와 소유권 검증은 같은 조건 하나로 처리한다.** 계좌는 `(user, market)` 단위이므로, 회고 → 체결(`trades.account_id`)이 **인증 사용자의 해당 시장 계좌**인 회고만 조회하면 시장 필터와 타인 데이터 차단이 동시에 걸린다. 이슈 #203의 설계 메모가 제안한 `trade_id → trades.instrument_id → instruments.market` 경로는 쓰지 않는다 — 조인이 한 단계 더 길고 소유권 검증을 별도로 얹어야 하는데, 형제 API(`GET /api/trades`·`GET /api/orders`)가 이미 계좌 스코프 방식(`AccountService.getAccountFor`)으로 통일돼 있다. 두 경로의 결과는 같다(체결의 계좌 시장과 종목 시장은 주문 시점에 일치가 보장된다).
- **해당 시장 계좌가 없으면 404 `NOT_FOUND`다.** 회고가 0건인 것과 계좌 자체가 없는 것은 다른 상황이며, 전자는 200 빈 목록이다. 이는 `GET /api/trades`·`GET /api/orders`의 기존 동작(`AccountService.getAccountFor`)과 같다.
- **목록 응답에는 종목·가격·수량·실현손익 등 체결 정보를 넣지 않는다.** 작성·수정 계약이 이미 정한 원칙(`GET /api/trades`가 체결 정보의 정본)을 목록에도 그대로 적용한다. 목록 항목이 체결 ID를 담고 있으므로 프론트엔드는 필요 시 체결 내역과 맞출 수 있다.
- **조회는 `@Transactional(readOnly = true)`이며 어떤 테이블도 쓰지 않는다.** 투자일기의 `updatedAt`은 조회로 바뀌지 않는다.
- **회고가 없는 체결은 목록에 나오지 않는다.** 목록의 단위는 체결이 아니라 회고다 — 회고를 쓰지 않은 체결까지 "빈 회고"로 채워 보여주지 않는다(그 목록은 `GET /api/trades`가 담당한다).

> **plan.md에서 확정한 설계 항목 (JOUR-006, 완료)**: ① 두 테이블을 합치는 방식(각 테이블에서 `limit + 1`건씩 가져와 애플리케이션 계층에서 병합 vs. 네이티브 `UNION ALL`) ② 새 컨트롤러 배치(기존 `JournalController`는 `@RequestMapping("/api/trades")`라 `GET /api/journal`을 담을 수 없다) ③ 응답 DTO 이름과 wrapper 구조(형제 API의 `content`·`nextCursor`·`hasNext` 3필드 형태를 따른다).

### 투자일기 상세 조회 (JOUR-005)

- **상세 조회는 타입별 경로로 분리한다 (JOUR-005 착수 결정, 2026-08-05, 이슈 #217).** `GET /api/journal/buy/{buyTradeId}`와 `GET /api/journal/sell/{sellTradeId}` 두 엔드포인트를 만들고, PRD가 초안으로 적어 둔 단일 경로 `GET /api/journal/{journalId}`는 만들지 않는다. **이 결정이 JOUR-005의 식별자 체계 Decision Gate를 해제하며, PRD JOUR-005의 URL 서술을 대체한다.** 근거는 셋이다.
  1. **숫자 하나로는 어느 테이블인지 정해지지 않는다.** `buy_trade_journals.id`와 `sell_trade_journals.id`는 서로 다른 AUTO_INCREMENT 시퀀스라 값이 겹친다(둘 다 `1`이 존재할 수 있다). 단일 경로를 유지하려면 두 테이블을 합치거나 ID에 타입을 실어야 하는데, 아래 두 대안이 모두 더 비싸다.
  2. **테이블 통합은 이미 머지된 구현 4개를 되돌려야 한다.** JOUR-001~004(PR #181·#189·#192·#201)가 `buy_trade_id`·`sell_trade_id` 전용 컬럼과 각 테이블의 유니크 제약 위에 서 있고, 엔티티·리포지토리·DTO·마이그레이션 6개가 그 구조를 전제한다. 상세 조회 하나를 위해 스키마와 네 계약을 다시 여는 비용이 얻는 것보다 크다.
  3. **접두사 문자열 ID(`"buy:42"`)는 이 프로젝트의 유일한 예외가 된다.** 지금까지 모든 리소스 ID가 숫자(`Long`)이고 경로 변수도 전부 숫자 파싱(파싱 실패 시 400)이다. 문자열 ID를 도입하면 이 한 엔드포인트만 파싱·검증 규칙이 달라진다.
  - **경로 분리는 목록(JOUR-006)과도 자연스럽게 맞물린다.** 목록 항목이 이미 `journalType`(`BUY`|`SELL`) + 해당 체결 ID를 내려주므로(§"JOUR-005 식별자 게이트를 선점하지 않는다"), 클라이언트는 목록에서 받은 타입만 보고 어느 경로로 갈지 알 수 있다. 목록 응답 계약은 이 결정으로 **바뀌지 않는다** — 통합 `journalId`는 앞으로도 노출하지 않으며, 지금 그 필드를 추가할 이유도 사라졌다.
- **경로 변수는 체결 ID이고, 회고 PK는 경로에 노출하지 않는다.** 작성·수정 계약 4개가 모두 `/api/trades/{tradeId}/...`로 체결 ID를 쓰고 목록 항목도 체결 ID를 담는다. 상세만 회고 PK를 경로에 쓰면 클라이언트가 같은 리소스를 두 가지 키로 다뤄야 한다. `journalId`는 **응답 본문에만** 남는다(작성·수정 응답이 이미 그 값을 돌려주고 있어 필드를 빼면 오히려 계약이 좁아진다).
- **검증 순서는 수정 계약(JOUR-002·004)과 같다** — `체결 존재(404) → 소유(403) → 체결 구분(400) → 회고 존재(404)`. 타인 체결이면 그 체결의 매수·매도 속성과 회고 존재 여부를 흘리기 전에 403이 먼저다. 이 엔드포인트에 **409는 없다**(새 행을 만들지 않는다).
- **경로와 체결 구분이 어긋나면 404가 아니라 400이다.** "매수 경로에 매도 체결 ID"는 리소스가 없는 게 아니라 **클라이언트가 경로를 잘못 고른 것**이며, 작성·수정 네 계약이 이미 같은 상황을 400 `VALIDATION_ERROR`로 처리하고 있다. 상세만 404로 다르게 응답하면 같은 실수가 엔드포인트마다 다른 코드로 돌아온다.
- **응답은 수정 응답과 같은 5필드다.** 프론트엔드가 수정 화면에서 쓰던 타입을 상세 조회에 그대로 재사용할 수 있고, "조회로 읽은 값 → 수정 요청 → 수정 응답"이 같은 모양으로 순환한다. `journalType`을 응답에 넣지 않는 이유는 경로가 이미 타입을 확정하기 때문이다 — 필요해지면 나중에 **추가**할 수 있다(추가는 확장, 제거·의미 변경이 breaking이다).
- **조회는 `@Transactional(readOnly = true)`이며 어떤 테이블도 쓰지 않는다.** 스키마 변경도 없다 — 리포지토리의 기존 `findByBuyTradeId`·`findBySellTradeId`(JOUR-002·004가 수정용으로 추가한 것)를 그대로 재사용한다.
- **회고가 없는 체결에 "빈 회고"를 만들어 반환하지 않는다.** 상세 조회는 읽기이며, 없는 것은 404다(목록이 회고 없는 체결을 항목으로 만들지 않는 것과 같은 원칙).

> **plan.md에서 확정할 설계 항목 (JOUR-005)** (여기서 규칙으로 못 박지 않는다): ① 새 컨트롤러를 만들지 기존 `JournalListController`(`@RequestMapping("/api/journal")`)에 메서드를 더할지 ② 응답 DTO를 새로 만들지 기존 `~UpdateResponse`를 재사용할지 ③ 서비스 메서드 이름과 매수·매도 두 유스케이스의 중복 처리 방식.

## 범위 제외

이번 착수(JOUR-005)에서 하지 않는 것이다. 괄호 안은 다루는 PRD 요구사항이다.

- **수정 잠금 로직 전체** — `JOURNAL_LOCKED` 오류 코드, `trade_allocations`·`holding_lots` 기반 잠금 판정, 수정 횟수·기간 제한을 만들지 않는다. 위 §비즈니스 규칙 "매수 회고 수정 잠금 없음"이 근거이며, **투자일기 본문을 읽는 소비 기능(spec 012)이 생기기 전까지 그리고 그 스펙의 별도 결정 전까지는 이후에도 만들지 않는다.**
- **단일 경로 상세 조회**(`GET /api/journal/{journalId}`) — 위 §비즈니스 규칙 "상세 조회는 타입별 경로로 분리한다"로 배제했다. 통합 식별자·접두사 문자열 ID도 만들지 않는다.
- **목록 항목에 상세 링크·식별자 추가** — 경로 분리로 클라이언트가 `journalType` + 체결 ID만으로 상세 URL을 조립할 수 있으므로, JOUR-006 목록 응답에 새 필드를 더하지 않는다(목록 계약 무변경).
- **목록 조회의 통합(전 시장) 축·기간/종목/회고종류 필터·정렬 옵션·키워드 검색** — 이번 목록은 `market` 축과 최신순 정렬 하나뿐이다. PRD JOUR-006이 요구하지 않았고, 형제 API도 같은 형태다.
- **매수·매도 회고 테이블 통합(스키마 변경)** — 상세 조회도 기존 두 테이블을 읽기만 한다. 신규 마이그레이션이 없다. **경로 분리 결정으로 통합의 유일한 동기(단일 `journalId`)가 사라졌으므로 이 spec에서는 더 이상 검토 대상이 아니다.**
- 투자일기 삭제 (PRD에 요구사항 없음).
- 목표가·손절가·근거·예상보유기간 같은 구조화 필드.
- 매수·매도 회고 **삭제**와 수정 이력·버전 보관(마지막 본문 1건만 남는다).
- 매수 회고 응답에 매도 배분·실현손익 등 후속 원장 정보를 포함하는 것 (`GET /api/trades`가 이미 제공한다).
- **매수·매도 회고 경로의 공통 추상화 리팩터링** — 여섯 유스케이스가 다 모여 중복이 뚜렷해졌지만, 이번 PR의 diff는 추가 위주로 둔다. 이미 머지·배포된 다섯 계약의 동작을 건드리지 않는 것이 상세 조회 하나를 여는 것보다 우선이다. 추상화가 필요하다면 **기능 변경이 없는 별도 리팩터링 PR**로 다룬다.
- 투자일기 기반 AI 피드백·가격 알림·주간 회고 (spec 012 범위).

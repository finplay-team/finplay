# Spec: 코인 시세 신선도 보강과 체결 가용성 확대

> GitHub 이슈 #369. 팀 확정 방향: **A(REST 폴링 백업)와 B(체결 경로의 STALE 허용)를 함께 적용한다**(yxejxnn 확정, 2026-08-13) — 재논의하지 않는다.
> 선행 근거: `docs/specs/032-price-quote-stale-split/spec.md`(표시/체결 stale 판정 분리), `docs/specs/003-market-data/spec.md` MKT-003·MKT-004, 이슈 #107(폴러 최초 도입), 이슈 #355.
> 요구사항 ID는 이 spec 전용 네임스페이스 `PRICE-REST-*`를 쓴다 — `PRICE-STALE-*`(032)와 같은 패턴으로, PRD 본문에 요구사항 절을 새로 추가하지 않고 이 spec이 정본이다. PRD §3 "구현 현황"에는 완료 시 행을 추가한다(CLAUDE.md 규칙 10).


## 개요

코인 현재가의 신선도는 지금 **마지막 체결 틱의 수신시각 하나**로만 판정하고(`PriceStore.isStale`, 10초 초과 시 stale), 그 시각을 갱신하는 유일한 경로가 빗썸 웹소켓의 체결 메시지다. **실제 체결이 없으면 연결이 정상이어도 시계가 늙는다.**

그 결과 체결이 뜸한 종목은 10초마다 `STALE`로 떨어지고, spec 032가 화면 표시는 살려놨지만 **주문은 여전히 409 `PRICE_UNAVAILABLE`로 거부된다.** 2026-08-13 운영 화면 실측에서 12개 코인 중 8개가 동시에 지연이었고, 잠시 뒤에는 BTC를 제외한 전 종목이 지연이었다 — 저유동성 알트만의 엣지 케이스가 아니라 **BTC를 뺀 사실상 전 종목이 상시로 매매 불가에 놓이는 문제**다.

이 spec은 두 방향을 함께 적용한다.

- **A — 지연이 생기는 빈도 자체를 없앤다.** 3초 주기 REST 폴링이 "이 가격이 지금도 최신"임을 계속 재확인해 신선도 시계를 리셋한다. 웹소켓을 대체하지 않고 병행한다.
- **B — 그래도 남는 지연에서 매매가 막히지 않게 한다.** 연결이 살아있고 가격을 받은 적이 있으면, 그 가격이 10초를 넘겼어도 마지막 가격으로 체결을 허용한다.

**둘의 관계**: A가 위험 노출 빈도를 줄이고, B가 남은 구간의 사용성을 보장한다. A만 하면 웹소켓·REST가 동시에 조용한 순간에 여전히 막히고, B만 하면 오래된 가격으로 체결되는 일이 일상적으로 발생한다. **함께 적용해야 "지연도 드물고, 지연이 나도 매매는 된다"가 성립한다.**

## 왜 032의 결정을 뒤집는가

032는 표시와 체결을 나누면서 체결을 fail-closed로 유지했고, 그 근거로 *"화면에 가격이 보이니 체결도 될 것이라고 오해하지 않도록"*을 들었다. 그 판단을 지금 뒤집는 이유는 다음과 같다.

- **비용과 편익의 저울이 실측으로 뒤집혔다.** 032 작성 시점에는 stale이 저유동성 소수 종목의 간헐적 현상이라고 전제했다. 2026-08-13 실측은 BTC를 제외한 사실상 전 종목이 상시 stale임을 보여준다. "드문 위험을 막는 대가"가 아니라 **"일상적으로 서비스의 핵심 기능이 동작하지 않는 대가"**였다.
- **이 서비스가 지키려는 것은 실제 자산이 아니다.** FinPlay는 가상 자산 기반 교육형 모의투자다(PRD). 실거래소의 시세 중단·거래정지 관행은 실제 손실을 막기 위한 것이고, 여기서 stale 체결이 만드는 위험은 **랭킹 공정성 훼손**이라는 서비스 내부 문제다. 매매 자체가 안 되는 것과 견줄 무게가 아니다.
- **A가 그 위험을 구조적으로 줄인다.** B를 단독 채택하면 "오래된 가격 체결"이 일상이 되지만, A와 함께 적용하면 stale 자체가 정상 운영 중엔 거의 발생하지 않는다. B가 실제로 발동하는 것은 웹소켓과 REST가 **둘 다** 조용한 예외 구간이다.
- **표시와 체결이 어긋나는 상태가 오히려 오해를 만든다.** 032의 원래 우려("가격이 보이면 체결도 될 것이라 오해")는, 실제로는 **가격이 보이는데 주문만 거부되는 현재 상태**로 나타났다. 화면과 체결의 판정을 일치시키는 것이 사용자 모델에 더 가깝다.

MKT-004의 "10초 초과 시 주문 거부" 규칙은 이 spec으로 **실질적으로 좁아진다** — 아래 §비즈니스 규칙과 완료 조건에서 문서 갱신 대상으로 다룬다.

## 사용자 시나리오

- 회원이 체결이 뜸한 코인(웹소켓 연결 정상)의 시장가 매수·매도를 주문하면 409 `PRICE_UNAVAILABLE` 없이 정상 체결된다.
- 회원이 코인 목록·상세 화면을 보면 정상 운영 중에는 "지연" 표시가 뜨지 않는다 — REST 폴링이 신선도를 유지하기 때문이다.
- 드물게 웹소켓·REST가 모두 조용해 "지연"이 표시되더라도, 회원은 그 종목을 **여전히 매매할 수 있다** — 마지막으로 받은 실제 가격으로 체결된다.
- 회원이 활발히 거래되는 코인(BTC 등)을 볼 때는 이번 변경 전과 동일하게 **웹소켓 체결이 도착하는 즉시** 가격이 갱신된다 — REST 폴링이 실시간 반영을 3초 주기로 늦추지 않는다.
- 빗썸 웹소켓 연결이 끊기거나 해당 종목의 시세를 한 번도 받지 못했으면, 회원은 여전히 화면에서 가격을 볼 수 없고 주문도 거부된다 — 보여줄 값 자체가 없는 경우는 이번 완화 대상이 아니다.
- 운영자는 REST 폴링이 실패·타임아웃·비정상 응답을 만나도 그 회차만 건너뛰고 스케줄러가 계속 도는 것을 확인한다.

## 요구사항

### PRICE-REST-001 관측 시각과 체결 시각의 분리 (A)

- [x] `PriceStore`는 심볼별로 **마지막 체결 시각**과 **마지막 관측 시각**을 서로 다른 값으로 보관한다. 전자는 "이 가격이 언제 체결됐는가"(거래소가 준 시각), 후자는 "이 가격이 지금도 최신이라고 마지막으로 확인한 때"(웹소켓 틱 수신 또는 REST 폴링 성공)다.
- [x] stale 판정(`isStale`)의 기준은 **관측 시각**으로 바뀐다 — 10초 임계값 자체는 그대로 둔다.
- [x] API 응답의 `sourceTime`이 뜻하는 값은 **체결 시각 그대로 유지**된다 — 화면에 "몇 시 기준 가격인가"로 표시되는 값의 의미를 바꾸지 않는다.

### PRICE-REST-002 REST 폴링의 운영 확장 (A)

- [x] `BithumbRestTickerPoller`가 운영 환경에서도 동작한다. 3초 주기로 빗썸 공개 ticker REST를 1회 호출해 **전 코인 심볼의 현재가를 한 번에** 받아온다.
- [x] 폴링이 성공한 심볼은 관측 시각이 갱신된다. 응답 가격이 저장된 가격과 다르면 가격도 함께 갱신된다.
- [x] 폴링 실패·타임아웃·비정상 상태코드·파싱 불가는 **그 회차만 건너뛰고** 로그만 남긴다 — 예외를 스케줄러 밖으로 던지지 않으며, 임의값·보간값으로 대체하지 않는다(현행 동작 유지).
- [x] 폴링이 연속 실패해 관측 시각이 10초를 넘기면 기존과 동일하게 `STALE`로 떨어진다 — 폴러가 죽은 것을 신선함으로 위장하지 않는다.

### PRICE-REST-003 웹소켓 실시간성 보존 (A)

- [x] 웹소켓으로 도착한 체결 틱은 REST 폴링이 켜진 뒤에도 **버려지지 않고 즉시 반영된다.** REST가 방금 관측 시각을 갱신했다는 이유로 그보다 이른 체결 시각을 가진 실제 틱이 무시되어서는 안 된다.
- [x] 동일 심볼의 **과거 체결 틱이 최신 체결을 덮어쓰지 않는다**(MKT-003 무변경).

### PRICE-REST-004 체결 경로의 STALE 허용 (B)

- [x] 빗썸 연결상태가 `CONNECTED`이고 해당 심볼의 최신 가격을 한 번이라도 받은 적이 있으면, 관측 시각이 10초를 넘겼더라도(`STALE`) **시장가·지정가 주문이 그 마지막 가격으로 체결된다** — `PRICE_UNAVAILABLE`을 던지지 않는다.
- [x] 체결에 쓰는 가격은 **실제로 수신된 마지막 가격 그대로**다 — 임의값·보간값으로 대체하지 않는다.
- [x] 코인의 체결 판정과 표시 판정은 **같은 규칙**을 쓴다. 032가 나눠놓은 두 경로는 이 spec에서 판정 규칙이 일치하게 되며, 규칙을 두 벌로 유지하지 않는다.
- [x] `PriceQueryServiceTest.getOrderExecutionPriceStillThrowsPriceUnavailableWhenCryptoTickIsStale`은 이 요구사항과 충돌하므로 새 동작을 고정하는 테스트로 이름과 단정을 반전시킨다.

### PRICE-REST-005 여전히 거부되는 경우 (fail-closed 잔여선)

- [x] 빗썸 연결상태가 `DISCONNECTED`이면 REST 관측 시각이 신선하더라도 표시·체결 모두 기존과 동일하게 `UNAVAILABLE` / 409다.
- [x] 해당 심볼의 시세를 한 번도 받은 적이 없으면(최신가 자체가 없음) 기존과 동일하게 `UNAVAILABLE` / 409다.
- [x] 위 두 경우는 "가격이 오래된 것"이 아니라 **"보여줄 가격 자체가 없는 것"**이므로 이번 완화 대상이 아니다. 이 구분은 032가 세운 것이며 이 spec도 그대로 승계한다.

### PRICE-REST-006 스케줄러 용량

- [x] 운영 프로필에 `@Scheduled` 작업이 하나 늘어나는 것을 `spring.task.scheduling.pool.size`에 반영한다. 이 값을 검증하는 기존 테스트(`NewsCollectionIntegrationTest.schedulingPoolIsLargeEnoughForEveryScheduledTask`)가 통과해야 한다.
- [x] 스케줄 개수를 단정하는 주석이 `application.yml`과 `application-crypto-real.yml` 두 곳에 있으므로 **둘을 함께 갱신한다**(현재 16 vs 13으로 이미 어긋나 있다).

## 비즈니스 규칙

- **"가격이 언제 체결됐는가"와 "그 가격이 지금도 유효한가"는 서로 다른 질문이다.** 전자는 거래소가 준 사실이고 후자는 우리가 확인한 사실이다. 어느 소비자든 둘을 하나의 값으로 뭉뚱그리지 않는다.
- **"가격이 오래된 것"과 "가격이 아예 없는 것"은 서로 다른 상태다.** 전자는 이번 spec에서 매매를 허용하고, 후자는 계속 거부한다. 이 둘을 하나의 `boolean`으로 뭉뚱그리지 않는다(032가 세운 구분을 승계).
- 표시·체결에 쓰는 가격은 여전히 **실제로 수신된 마지막 체결가**다 — 임의값·보간값·호가 기준가로 대체하지 않는다.
- REST 폴링 주기는 stale 임계값보다 **반드시 짧아야 한다.** 길면 폴링이 정상 동작해도 그 사이에 stale이 발생한다.
- **주문 거부 조건은 "연결이 끊겼거나 시세를 한 번도 받은 적이 없을 때"뿐이다** — 10초 초과 자체는 주문 거부 사유가 아니다(MKT-004, `docs/specs/003-market-data/spec.md`·`docs/prd.md`에서 이 내용으로 갱신 완료).
- 코인 시세 정본은 여전히 Redis 최신 틱이다 — 새 MySQL 테이블을 만들지 않는다.

## 남은 알려진 공백

A+B를 모두 적용해도 **웹소켓이 완전히 끊긴 구간에서는 매매가 막힌다.** REST가 신선한 가격을 계속 확보하고 있어도 `PriceStore.isPriceAvailable`이 연결상태를 먼저 검사하기 때문이다(PRICE-REST-005).

이 spec은 그 동작을 유지한다. 연결상태 게이트를 여는 것은 "빗썸 실시간 연결이 끊긴 상태에서도 주문을 받는다"는 뜻이라, 신선도 완화와는 무게가 다른 결정이고 연결상태의 소유권 구조 자체를 바꿔야 한다. 필요해지면 별도 이슈로 연다. 그때 함께 볼 항목: 웹소켓 재연결 백오프 상한(현재 최대 60초), ping/pong 미처리로 인한 재연결 빈도.

## 범위 제외

- **웹소켓 끊김 시 REST 페일오버 승격** — 위 §남은 알려진 공백 참조.
- **웹소켓 호가(orderbook) 채널 추가 구독** — 이슈 #369에서 REST 방향으로 확정했다. 후속 옵션으로만 남긴다.
- **`STALE_THRESHOLD` 10초 임계값 자체의 변경** — 이 spec은 판정 재료를 늘리고 체결 허용 범위를 넓힐 뿐 숫자는 그대로 둔다.
- **`PriceStatus.STALE` 값 자체의 제거** — 폴러까지 실패하는 구간에서 화면에 "지연"을 알리는 용도로 여전히 필요하다. 체결만 허용될 뿐 표시는 계속 구분한다.
- **웹소켓 ping/pong 하트비트 도입·재연결 백오프 조정** — 별개 원인이며 별도 이슈로 분리한다.
- **stale 가격으로 체결된 거래에 별도 표식(주문 이력·투자일기 등)을 남기는 것** — B의 발동 자체가 A로 인해 드물어지므로 이번 범위에서는 하지 않는다. 실제로 빈번하다고 확인되면 별도 이슈로 연다.
- **`HoldingValuationService`(평가손익)의 stale 취급** — 032가 엄격 유지로 확정했다(PRICE-STALE-005). 이 spec은 **체결 경로만** 완화하며 평가손익은 건드리지 않는다. 다만 A로 인해 stale 자체가 거의 발생하지 않으므로 실질적으로 함께 정상화된다.
- **주식 가격 경로 전체** — 이번 spec은 코인에만 해당한다.
- **빗썸 REST 레이트리밋 정책의 전면 재검토** — 이번 호출량(3초 주기 · 전 심볼 1회 묶음)이 저촉되지 않는지만 확인한다.

# Spec: PR 생성 전 정지 지점 이슈 알림

## 개요
이슈 트리거 하네스(ADR-0013)의 `implement-and-open-pr` job은 PR을 연 뒤의 모든 정지 지점에 이력 코멘트를 남기도록 정비돼 있다(ADR-0016, PR #293). 그런데 이력 코멘트 스텝은 전부 `steps.pr.outputs.number != ''`를 요구하므로, **PR이 만들어지기 전에 흐름이 죽으면 아무 데도 알림이 가지 않는다.** 2026-08-10 실행(이슈 #276 처리)에서 실제로 발생했다 — 구현 에이전트가 100턴·$7.25를 쓰고도 브랜치·PR을 만들지 못했고, 이슈에는 지금도 아무 응답이 없다(GitHub 이슈 #311, `docs/agent-mistakes.md` 2026-08-10 행).

`github.event.issue.number`는 이 job의 트리거 시점(`issue_comment`)부터 항상 존재하므로, PR이 없어도 게시 대상은 확보돼 있다. 이 spec은 PR 생성 전 구간에 이력 코멘트를 추가해 이 사각지대를 없앤다.

## 사용자 시나리오
- 팀원이 이슈 코멘트로 `@claude N안으로 구현해줘`를 남겼는데, 구현 에이전트 호출이 정상 종료되지 않으면(실패·취소·타임아웃) 이슈에 그 사실과 실행 로그 링크가 담긴 코멘트가 남는다.
- 구현은 끝났지만 러너의 검증 빌드가 실패하면, 이슈에 빌드 실패 사실과 실행 로그 링크가 담긴 코멘트가 남는다.
- 구현·빌드는 끝났지만 PR 번호 조회가 실패하면(PR을 못 찾음), 이슈에 그 사실과 실행 로그 링크가 담긴 코멘트가 남는다.
- 팀원은 Actions 탭을 직접 열어보지 않아도 이슈 코멘트 이력만 보고 어느 단계에서 왜 멈췄는지 알 수 있다.
- 정상 흐름(구현 → 빌드 → PR 오픈 → 이후 ADR-0016 정비 구간)에서는 이 변경으로 인한 추가 코멘트가 붙지 않는다.

## 요구사항
- [ ] 구현 에이전트 호출(`claude-code-action`)이 정상 종료되지 않으면(`outcome != success` — 실패·취소·타임아웃·이전 스텝 실패로 인한 스킵 포함) 이슈에 이력 코멘트가 남는다.
- [ ] 구현 에이전트 호출은 정상 종료됐지만 러너의 빌드 검증(`id: build`)이 정상 종료되지 않으면 이슈에 이력 코멘트가 남는다.
- [ ] 빌드 검증은 정상 종료됐지만 PR 번호 조회(`id: pr`)가 정상 종료되지 않으면(빈 `NUMBER`로 인한 명시적 `exit 1` 포함) 이슈에 이력 코멘트가 남는다.
- [ ] 위 세 코멘트는 실패 사유(해당 스텝의 실제 `outcome` 값)와 Actions 실행 링크(`${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}`)를 포함한다.
- [ ] 위 세 정지 지점은 상호 배타적이다 — 하나의 실행에서 정확히 한 곳만 해당 조건에 걸리고, 코멘트도 정확히 1개만 게시된다.
- [ ] 정상 흐름(구현 → 빌드 → PR 오픈까지 모두 성공)에서는 이 세 코멘트 중 어느 것도 게시되지 않는다 — 기존 PR 기반 이력 코멘트 동작(ADR-0016)은 그대로 유지된다.
- [ ] 기존 `steps.pr.outputs.number != ''` 게이트를 쓰는 PR 이후 구간의 이력 코멘트 스텝들은 변경하지 않는다.

## 비즈니스 규칙
- PR이 존재하지 않는 시점의 이력 코멘트는 항상 이슈(`github.event.issue.number`)에 게시된다. PR이 존재하는 시점(PR 오픈 이후)의 이력 코멘트는 기존 그대로 PR에 게시된다 — "PR 유무로 게시 위치를 가른다"는 원칙을 이 job 전체에 일관되게 적용한다(이슈 #311 "결정이 필요한 지점" 1번, 완료 조건 "정상 흐름에서 중복 코멘트가 늘지 않는다"가 이 선택을 강제한다).
- 새로 추가하는 세 이력 코멘트 스텝은 판정·승인이 아니므로 ADR-0016이 이미 세운 원칙대로 `always()`를 쓰고, 대상 판정은 `outcome == 'failure'`가 아니라 `outcome != 'success'`로 통일한다(취소된 스텝의 `outcome`은 `cancelled`이지 `failure`가 아니므로 `!= 'success'`라야 타임아웃 경로도 잡힌다).
- 코멘트 본문은 "실패했습니다"로 단정하지 않고 실제 `outcome` 값을 함께 찍는다(ADR-0016과 동일한 원칙) — 취소(타임아웃)와 실패를 코멘트만 보고 구분할 수 있어야 한다.
- 기존 `steps.pr.outputs.number != ''` 게이트는 그대로 유지하고, PR이 없는 정지 지점 전용 스텝을 별도로 추가한다 — 게시 대상(이슈 vs PR)을 고르는 공통 스텝으로 합치지 않는다. ADR-0016이 세운 "정지 지점마다 스텝 하나" 구조를 유지해 회귀 위험을 낮춘다(이슈 #311 "결정이 필요한 지점" 3번).

## 범위 제외
- `verify-actor` job 자체가 실패하는 경우(예: 협업자 확인 GitHub API 호출 실패)의 알림 — 이 job은 `implement-and-open-pr`보다 앞서 실행되며, 실패하면 `implement-and-open-pr`가 아예 시작되지 않는다. 이슈 본문과 이번 작업 지시 모두 "PR 생성 전"의 범위를 `implement-and-open-pr` job 내부 3개 정지 지점으로 명시했고, `verify-actor`는 별도 job이라 이번 spec의 대상이 아니다.
- `propose-directions` job(라벨 트리거, 방향 제시 단계)의 실패 알림 — 별도 job이며 이 이슈의 범위(PR 오픈 흐름)가 아니다.
- ADR-0016이 이미 다루는 PR 오픈 이후 구간(자체 리뷰·자동 수정 라운드·최종 판정·조건부 승인)의 이력 코멘트 로직 변경 — 이번 spec은 그 앞 구간만 다룬다.
- Gradle 프로세스 충돌로 검증 빌드가 깨지는 문제 — PR #310에서 이미 처리했다.
- 구현 에이전트가 턴 상한에 걸리는 문제(이슈 #276 실행의 `num_turns: 100`) — 별도 판단이 필요하며 이번 spec의 대상이 아니다. (참고: 턴 상한에 걸려도 `outcome`은 대개 `failure`나 `cancelled`가 아니라 `success`로 끝나는 경우가 있을 수 있어, 이 spec의 조건만으로는 모든 "결과물 없이 끝난 성공"까지 잡지 못할 수 있다. 이는 확인되지 않은 가능성이며 이번 spec의 완료 조건은 어디까지나 "`outcome != success`"이다.)
- 사람의 최종 승인·머지 자동화(ADR-0005 유지).

## 완료 조건
- [ ] 세 정지 지점(구현 호출 실패·빌드 실패·PR 조회 실패) 각각에서 이슈에 사유(실제 `outcome` 값)와 Actions 실행 링크가 담긴 코멘트가 정확히 1개 남는 것을, 도달 가능한 outcome 조합을 전수 검토해(표 또는 스크립트) 확인한다.
- [ ] 정상 흐름(구현 → 빌드 → PR 오픈)에서 이 변경으로 인한 추가 코멘트가 없는 것을 같은 전수 검토로 확인한다.
- [ ] `docs/adr/0016-review-gate-auto-fix-round.md`의 이력 코멘트 스텝 열거가 PR 생성 전 구간의 3개 스텝을 포함하도록 갱신된다(기존 결정을 뒤집지 않고 적용 범위만 넓히는 갱신 — 새 ADR 번호를 만들지 않는다).
- [ ] `.github/workflows/agent.yml`이 `python -c "import yaml; yaml.safe_load(...)"`로 문법 검증을 통과하고, 새로 추가한 각 `run:` 블록이 `bash -n`으로 문법 검증을 통과한다.
- [ ] 테스트 이슈 1건으로 실제 검증한다(머지 후 가능 — `issue_comment` 트리거는 항상 `dev` 기준 워크플로우 버전으로 실행되므로 PR 머지 전에는 실제 하네스 실행으로 검증할 수 없다).

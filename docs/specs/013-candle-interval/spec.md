# Spec: 캔들 조회 기간 확장 — 일봉/주봉/월봉 (1d · 1w · 1M)

> 단계: **2차 MVP (팀 회의 표현: 1차 고도화)**. 이슈 #143.
>
> PRD 근거: **MKT-009**(`docs/prd.md`). 선행 근거: MKT-002(주식 과거 분봉 재생·`stock_candles`), MKT-008(코인 빗썸 공개 캔들 REST 중계), C-005(외부 연동은 Fake로 자동 테스트하고 실제 호출은 외부 스모크로 구분 보고), C-006(과거 데이터는 공공데이터).
>
> 선행 spec: `003-market-data`. **이 spec은 003의 1차 계약(`interval=1m`만 허용)을 대체한다** — 003 spec.md·plan.md의 해당 문장은 지우지 않고 "1차 고도화(이슈 #143, 013)에서 확장됨" 이력 표시만 남겼다.
>
> **왜 003을 고치지 않고 새 폴더인가**: 003은 1차 MVP 범위로 이미 전 항목이 완료(`tasks.md` 전부 `[x]`)된 spec이고, 그 "제외 범위"·"1차는 1m만" 문장들은 **당시 계약을 기록한 이력**이다. PRD도 MKT-009를 명시적으로 2차 MVP로 분리했다. 완료된 1차 spec을 사후 편집해 2차 요구사항을 섞으면 무엇이 1차 계약이었는지 추적할 수 없어진다. 011·012도 같은 이유로 후속 폴더를 썼다.

## 개요

캔들 API `GET /api/instruments/{instrumentId}/candles`의 `interval` 허용값을 `1m` 하나에서 **`1m | 1d | 1w | 1M`**(1분봉·일봉·주봉·월봉)로 확장한다.

- **주식**: 정본인 1분봉(`stock_candles`)을 거래일·주·월 단위로 **집계**해 제공한다. 새 저장 테이블도, 새 Flyway 마이그레이션도 만들지 않는다.
- **코인**: 빗썸 공개 캔들 REST의 일·주·월봉 엔드포인트(`/v1/candles/days`·`/weeks`·`/months`)에 **위임**한다. 1분봉(MKT-008)과 똑같이 저장 없이 요청 시점에 조회해 중계한다.

응답 DTO(`CandleResponse`)의 필드 구조는 그대로다. 소비자는 `interval`만 바꿔 같은 형태의 배열을 받는다.

## 사용자 시나리오

- 회원은 주식 종목 차트에서 `interval=1d`를 요청해 거래일 단위 OHLCV 봉을 볼 수 있다.
- 회원은 주식 종목 차트에서 `interval=1w`·`1M`을 요청해 주·월 단위로 묶인 봉을 볼 수 있다.
- 회원은 코인 종목 차트에서 `interval=1d`·`1w`·`1M`을 요청해 빗썸이 제공하는 일·주·월봉을 볼 수 있다.
- 회원은 기존과 동일하게 `interval=1m`으로 1분봉을 볼 수 있다 — 응답 값·정렬·미마감 봉 규칙이 이전과 완전히 같다.
- 회원이 지원하지 않는 `interval`(`1D`·`1W`·`5m`·빈 값 등)을 보내면 400 `VALIDATION_ERROR`로 즉시 거부된다.

## 요구사항

### 공통 계약

- [ ] `interval` 허용값은 `1m`(1분봉)·`1d`(일봉)·`1w`(주봉)·`1M`(월봉) 네 개다.
- [ ] **`interval`은 대소문자를 구분한다** — `1M`은 월봉, `1m`은 분봉이다. `1D`·`1W`·`1MO`·`1min`·`1d ` 같은 변형은 전부 400 `VALIDATION_ERROR`다. 서버는 대소문자를 정규화하지 않는다.
- [ ] 응답은 기존 `CandleResponse`(`sourceTime`·`open`·`high`·`low`·`close`·`volume`) 그대로다. `interval` 확장을 이유로 필드를 추가·제거하지 않는다.
- [ ] 모든 `interval`의 응답은 **시각 오름차순**이다.
- [ ] 한 번의 요청이 반환하는 봉 개수 상한은 **200개**다(모든 `interval`·모든 시장 공통, 빗썸 상한과 동일). 요청 범위가 상한을 넘으면 `to` 기준 **최신 200개**를 반환한다. 상한은 계약으로 명시하며 조용히 잘라내지 않는다.
- [ ] `sourceTime`은 **KST 기준 그 봉이 덮는 구간의 시작 시각**이다.
- [ ] 오류 계약은 기존과 같다 — 없는 `instrumentId`는 404 `NOT_FOUND`, `from > to`는 400 `VALIDATION_ERROR`, 코인 외부 조회 실패는 502 `MARKET_DATA_PROVIDER_ERROR`, 인증 실패는 401 `UNAUTHORIZED`.
- [ ] `interval` 검증은 종목 조회보다 **먼저** 수행한다(기존 순서 유지) — 잘못된 `interval`은 존재하지 않는 종목이어도 400이다.

### 주식 — `stock_candles` 집계 (1d · 1w · 1M)

- [ ] 원천은 `stock_candles`의 1분봉뿐이다. 집계 결과를 저장하지 않는다(테이블·컬럼·마이그레이션 추가 금지).
- [ ] **버킷 경계(확정)**
  - `1d` = `stock_candles.trading_date` 하나 = 한국 거래일 하나. 09:00~15:30 구간 전체를 하나의 봉으로 묶는다.
  - `1w` = 그 `trading_date`가 속한 주. **주의 시작은 월요일**(ISO-8601, KST). 주말·공휴일은 거래일이 없으므로 자연히 빠진다.
  - `1M` = 그 `trading_date`가 속한 **달력 월**(KST). 월의 시작은 1일이다.
- [ ] **타임존(확정)**: 주식의 모든 시각은 KST 기준이며 `LocalDate`·`LocalTime`으로 다룬다. UTC 변환을 하지 않는다. 주·월 경계 판정도 KST 달력으로 한다.
- [ ] **`sourceTime`(확정)**: 버킷 시작일의 `00:00:00`이다.
  - `1d` → `{trading_date}T00:00:00`
  - `1w` → `{그 주 월요일}T00:00:00`
  - `1M` → `{그 달 1일}T00:00:00`
  - 월요일·1일이 실제 거래일이 아니어도 **라벨로만** 쓴다. 그 날에 거래가 있었다는 뜻이 아니다.
- [ ] **OHLCV 산출(확정)**
  - `open` = 버킷 안에서 `(trading_date, candle_time)`이 가장 이른 분봉의 `open`
  - `high` = 버킷 안 분봉 `high`의 최대값
  - `low` = 버킷 안 분봉 `low`의 최소값
  - `close` = 버킷 안에서 `(trading_date, candle_time)`이 가장 늦은 분봉의 `close`
  - `volume` = 버킷 안 분봉 `volume`의 합
  - 시가·종가를 "그 날 09:00 봉"·"그 날 15:29 봉"처럼 고정 시각으로 가정하지 않는다 — 실제 존재하는 분봉 중 최소·최대 시각을 쓴다.
- [ ] **공개 상한(reveal bound) — 미공개 데이터 유출 금지(확정)**
  - 집계 대상은 **이미 공개된 분봉뿐**이다. 공개 상한은 오늘(서비스 일자)의 `stock_replay_sessions`에서 정한다.
  - 오늘 `READY` 재생세션이 **없으면** 어떤 `interval`이든 200 `[]`를 반환한다(1분봉과 동일한 계약, 예외 아님). 이유: 공개 상한을 정할 수 없는 상태에서 저장된 거래일을 통째로 집계하면, **오늘 새벽 수집만 되고 아직 한 번도 재생하지 않은 거래일**이 일봉으로 미리 새어 나간다. 그것은 체결가 계약(MKT-002)과 어긋난다.
  - `READY` 세션이 있으면 그 세션의 `source_trading_date`(이하 `재생거래일`)를 기준으로:
    - `trading_date < 재생거래일` → 그 거래일의 분봉 **전부**가 집계 대상이다(이전 서비스일에 이미 전량 재생되어 공개된 과거 데이터, C-006).
    - `trading_date = 재생거래일` → **이미 마감·공개된 분봉만** 집계 대상이다. 공개 컷오프 규칙은 1분봉과 동일하다(09:01 이전에는 공개된 분봉이 0개, 09:01부터는 `현재 분 − 1분`까지).
    - `trading_date > 재생거래일` → 집계에서 **제외**한다(방어 규칙. 정상 운영에서는 존재하지 않아야 하지만, 존재하면 미공개 데이터다).
- [ ] **미완성(진행 중) 버킷 처리(확정)**: 진행 중인 거래일·주·월의 버킷을 **응답에 포함한다.** 그 버킷은 위 공개 상한을 통과한 분봉만으로 집계되므로 미공개 데이터가 섞이지 않는다.
  - 진행 중 버킷의 `close`는 "마지막으로 공개된 분봉의 종가"이며, 요청할 때마다 값이 커질 수 있다.
  - 예외: 공개된 분봉이 **0개**인 버킷은 만들지 않는다. 09:01 이전에 조회하면 재생거래일의 봉은 아예 없고 과거 거래일 봉만 나온다. 0으로 채운 봉·직전 종가로 채운 봉을 만들지 않는다.
  - 1분봉의 "미마감 분봉 미노출" 규칙과 모순되지 않는다 — 그 규칙은 **아직 마감하지 않은 개별 분봉을 노출하지 말라**는 것이고, 여기서 노출하는 것은 이미 공개된 분봉들만으로 계산한 값이다.
- [ ] **거래일이 없는 주·월(확정)**: 저장된 분봉이 하나도 없는 주·월은 **응답에 넣지 않는다.** 빈 봉을 만들어 채우지 않으며, 반환된 봉들의 `sourceTime`이 달력상 연속임을 보장하지 않는다. 소비자는 봉 사이가 비어 있을 수 있음을 전제해야 한다. (`stock_candles`는 서비스 운영일마다 직전 영업일 하나씩 쌓이므로, 서비스가 쉰 기간은 자연히 구멍이 된다.)
- [ ] **`from`·`to` 해석(1분봉과 다름 — 확정)**: `1d`·`1w`·`1M`에서는 `from`·`to`의 **날짜 성분**을 쓰고 시각 성분은 무시한다. 버킷은 그 **버킷 시작일**이 `[from의 날짜, to의 날짜]`(양끝 포함) 안에 있으면 포함한다. `from > to` 판정도 날짜 기준이다.
  - `1m`은 기존 계약(날짜 성분 무시, 시각 성분만 사용)을 **그대로 유지한다.** 두 규칙이 다른 이유는 명확하다 — 1분봉은 항상 재생 중인 단일 거래일 안에서만 조회되지만, 집계 봉은 여러 거래일에 걸친다.
- [ ] `from`·`to`를 둘 다 생략하면 공개 상한까지의 **최신 200개** 버킷을 반환한다.

### 코인 — 빗썸 위임 (1d · 1w · 1M)

- [ ] 데이터 출처는 빗썸 공개 캔들 REST의 `/v1/candles/days`·`/v1/candles/weeks`·`/v1/candles/months`다. 인증 없는 공개 시세이며 요청 시점에 조회한다.
- [ ] **저장·캐시하지 않는다.** 코인 일·주·월봉 테이블을 만들지 않고 Redis 키도 추가하지 않는다(MKT-008과 동일 원칙).
- [ ] 빗썸 응답은 최신→과거 내림차순이므로 시각 오름차순으로 뒤집어 반환한다(1분봉과 동일).
- [ ] 필드 매핑은 1분봉과 동일하다 — `opening_price`→`open`, `high_price`→`high`, `low_price`→`low`, **`trade_price`→`close`**(이름에 속아 현재가로 해석하지 않는다), **`candle_acc_trade_volume`→`volume`**(거래대금 `candle_acc_trade_price`와 혼동하지 않는다).
- [ ] 일·주·월봉 응답에만 있는 필드(`prev_closing_price`·`change_price`·`change_rate`·`first_day_of_period` 등)는 무시한다. **원본 응답을 그대로 내려주지 않는다**(MKT-006 원칙).
- [ ] **버킷 경계는 빗썸이 준 값을 그대로 쓴다(확정).** 서버는 빗썸 봉을 다시 자르거나 다시 묶지 않고, 응답의 `candle_date_time_kst`를 `sourceTime`으로 그대로 매핑한다. 우리는 중계자이고 코인 시세의 정본은 외부(빗썸)다.
  - **결과적으로 주식과 코인의 버킷 경계 정의가 다를 수 있다** — 주식은 우리가 KST 거래일로 자르고, 코인은 빗썸의 경계를 따른다. 서버는 이 둘을 억지로 맞추지 않는다. 이 차이는 의도된 것이며 `docs/api-contracts.md`에 명시한다.
  - 구현 시 실제 빗썸 응답의 `candle_date_time_kst` 경계값(예: `T00:00:00`인지 `T09:00:00`인지)을 **외부 스모크로 관측해 관측한 그대로** 계약 문서에 기록한다. 추측으로 적거나 서버에서 시각을 보정하지 않는다.
- [ ] 빗썸 조회가 실패하면(타임아웃·비정상 상태코드·파싱 불가) 502 `MARKET_DATA_PROVIDER_ERROR`를 반환한다. 마지막 값으로 대체하거나 빈 배열 200으로 성공을 위장하지 않는다.
- [ ] 자동 테스트는 Fake 구현을 쓴다. 실제 빗썸 호출 검증은 외부 스모크로 **구분해** 보고한다(C-005).

## 비즈니스 규칙

- **집계 봉은 파생값이지 정본이 아니다.** 정본은 주식 1분봉(`stock_candles`)과 빗썸 응답이며, 집계 결과를 저장하거나 주문 체결가로 쓰지 않는다. 주문(004·005)의 체결가 계약은 이 spec으로 바뀌지 않는다.
- **공개되지 않은 분봉은 어떤 `interval`로도 새어 나갈 수 없다.** 집계는 반드시 공개 상한을 통과한 분봉만 입력으로 받는다.
- **`1m` 경로는 변경 대상이 아니다.** 값·정렬·미마감 규칙·`from`·`to` 해석·빈 배열 조건 전부 이전과 같아야 한다.
- 주식 `volume`은 정수 거래량(합계)이고, 코인 `volume`은 소수 수량이다. 응답에서 소수 자릿수를 잘라내지 않는다.
- 봉 하나에 기여한 분봉이 0개면 그 봉은 존재하지 않는다. 값이 0인 봉과 봉이 없는 것은 다르다.

## 범위 제외

- 코인의 1분 외 짧은 간격(3·5·10·15·30·60·240분) — 빗썸이 지원하더라도 이번 계약에 넣지 않는다.
- 프론트엔드 차트의 기간 선택 UI — 별도 이슈(`FinPlay` 레포).
- 신규 Flyway 마이그레이션·신규 테이블·신규 Redis 키 — 기존 테이블 집계와 외부 위임만으로 처리한다.
- 집계 결과 캐싱(메모리·Redis) — 데이터 규모가 작아 필요 없다. 필요해지면 별도 이슈로 판단한다.
- 주식 일·주·월봉의 외부(KIS) 직접 수집 — 정본 1분봉 집계로만 만든다.
- 봉 개수 상한 200의 조정, 페이지네이션·커서 도입.
- 003의 다른 계약(현재가·SSE·재생세션·수집 배치) 변경.

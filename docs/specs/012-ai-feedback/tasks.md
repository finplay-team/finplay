# Tasks: 012 AI 피드백 — 이슈 #180 (주식 변동 탐지·개장 전 배치·카드 조회 API)

> **이 문서는 이슈 #180의 범위만 담는다.** spec 012 전체(이슈 8개)의 분할은 `./plan.md`가 정본이고, 값·규칙은 `./spec.md` §확정값이 정본이다. 여기에 값을 다시 적지 않는다 — 크론·타임존·스레드 풀은 §C-1, 구간과 근거창은 §C-2, 벽시계와 분봉의 구분은 §C-2-1, 공시 날짜 판정은 §C-3, 노출 게이트는 §C-5, 패키지 배치와 클래스 이름·배치 생성 순서는 §C-6, 설정 방침은 §C-7, 컬럼 타입은 §C-8, 탐지 수식은 §탐지 알고리즘(주식), `reveal_time` 계산은 §노출 판정, 근거 상한·절단은 §뉴스 매칭 범위, 실패 시 대응은 §실패 처리, 응답 필드는 `docs/api-contracts.md`다.
>
> 항목 하나 = implementer 1회 투입 = 커밋 1개. 테스트 레벨은 ADR-0003을 따른다 — 탐지·매칭·`reveal_time` 계산은 외부 의존이 없어 순수 단위, 리포지토리 파인더와 유니크 축은 `@DataJpaTest`, 배치 종단과 게이트는 고정 `Clock` + Testcontainers 통합, 컨트롤러 계약은 `@WebMvcTest`다.
>
> **이 이슈는 spec 012의 첫 컨트롤러를 만든다.** `docs/api-routes.md`·`docs/api-contracts.md` 갱신은 /feature 마무리의 planner(동기화 모드)가 같은 커밋 범위에서 맡는다 (CLAUDE.md 규칙 7). 6번 항목에 그 사실을 적어 뒀다.

## 이 이슈 전체에 걸리는 제약

- **여기서 값을 새로 정하지 않는다.** 임계값·크론·구간·상태값·클래스명이 필요하면 위 참조를 읽는다. spec에 없는 값·이름이 필요해 보이면 코드가 아니라 `spec.md`를 먼저 고친다 (CLAUDE.md 규칙 1·2). #167이 `NewsCollectionService`를 §C-6에 추가한 것이 선례다.
- **#147의 `NarrativeService` 하나만 주입한다.** 서술 확정 경로(생성 → 후검증 → 폴백)가 그 서비스 안에 있으므로 **생성기·검증기·프롬프트 조립기·템플릿 조립기를 직접 알 필요가 없다**(§C-6). 카드는 1단계 경로다 — 후검증에 걸리면 템플릿이고 재생성이 없다.
- **#160의 `PriceMoveEvent`·`PriceMoveEventSource` 엔티티와 두 리포지토리가 이미 있다. 새로 만들지 않는다.** 같은 뜻의 엔티티·enum을 하나 더 만들지 않는다.
- **머지된 `V13`을 수정하지 않는다** (ADR-0004). **이 이슈는 스키마를 바꾸지 않는 것이 기본이다** — 탐지·배치·조회는 이미 있는 컬럼에 쓰고 읽기만 한다. 바꿔야 한다고 판단되면 §C-8·§데이터 모델을 먼저 확인하고, 그래도 필요하면 spec을 고친 뒤 **새 번호**로 낸다. 컬럼이 바뀌면 `FeedbackSchemaConstraintsTest`(일곱 테이블의 컬럼 → NULL 허용 맵 **전체 비교**)가 먼저 깨지므로 기대 맵도 같은 커밋에서 고친다.
- **#167의 `collector/`·`NewsCollectionService`를 건드리지 않는다.** 이 이슈는 **이미 저장된 기사를 읽기만** 한다 — 수집은 이 배치에 포함하지 않는다(FEED-004). 수집기·수집 크론·질의어·제목 필터는 이 이슈 범위 밖이고, `NewsMatcher`가 이 이슈 소유다.
- **리포지토리에 지금 필요 없는 조회를 만들지 않는다.** 세 리포지토리(`MarketNewsItemRepository`·`PriceMoveEventRepository`·`PriceMoveEventSourceRepository`)의 주석이 "필요해진 이슈에서 하나씩 더한다"를 적어 두었다. **아래 완료 조건을 검증하는 데 필요한 파인더만** 그 항목에서 더한다. Part C·D의 구간 질의(#5), 보유 구간 카드 조회(#6), 코인 쿨다운·일일 상한(#8)은 각자의 이슈 소유다.
- **`feedback.detection` 설정 블록을 신설한다.** §C-7의 확정 방침을 따른다 — yml과 record `@DefaultValue` 양쪽에 값을 두고 드리프트를 잡는 테스트를 함께 둔다. `feedback.llm`(#147)·`feedback.news`(#167)가 선례다.
- **`cron` 기반 `@Scheduled`에는 `zone`을 붙인다**(§C-1). 이 이슈가 더하는 `@Scheduled`는 개장 전 배치 크론 **1개**다.
- **`spring.task.scheduling.pool.size`를 자기 몫만큼만 올린다**(§C-1). **현재 값은 7이고 기본 프로필의 실제 활성 `@Scheduled`도 7개다.** `application.yml` 주석이 개수 계산을 불변식으로 적어 두었으므로 **주석도 같은 커밋에서 갱신한다** — 이슈 #125가 정확히 이 개수를 잘못 센 사고였다.
- **`market`에 조회 메서드를 신설한다**(§C-6 표의 4종). **`feedback`은 다른 도메인의 repository·store를 직접 주입하지 않는다.** 기존 `getRevealedCandles`를 그대로 쓰면 배치가 빈 리스트를 받아 **예외 없이 매일 0건**이 된다(§코드 배치와 설정).
- **`RestClient` 빈을 새로 정의하지 않는다.** `KisHistoricalCandleClientImpl`의 필드 `@Qualifier`가 Lombok 생성자에 복사되지 않아 실효가 없고, 두 번째 빈이 생기는 순간 `NoUniqueBeanDefinitionException`으로 앱 전체가 죽는다 (`docs/agent-mistakes.md` 2026-08-04). 필요하면 `RestClient.Builder`를 받아 클래스 안에서 완성한다. **이 이슈는 새 외부 HTTP 호출을 만들지 않으므로 애초에 해당 자리가 없어야 한다.**
- **외부 API 키가 없어도 기동과 `./gradlew build`가 통과해야 한다** (ADR-0011, §실패 처리). 키 4종은 발급돼 있으나 방침은 그대로다 — **실제 외부 API를 호출하는 자동 테스트를 만들지 않는다** (PRD C-005).
- **원장에 쓰지 않는다.** 탐지·매칭·배치·조회 경로가 `price_move_events`·`price_move_event_sources` 밖의 테이블에 INSERT·UPDATE 하지 않는다. `instruments`·`stock_candles`·`stock_replay_sessions`·`market_news_items`는 **읽기만** 한다. 8개 이슈 공통 조건인 "원장 불변"이 이 이슈에서 취하는 형태다.
- **이 이슈의 탐지는 주식 전용이다.** 코인 탐지·감시·가격 스냅샷은 #8 소유다(§완료 조건 "코인 탐지" 절 7건 전부).

## 작업 항목

- [x] **1. `feedback.detection` 설정 블록과 `PriceMoveDetector` (순수 계산)**

  탐지 수식과 그것이 읽을 설정을 한 덩어리로 세운다. 뒤 항목 전부가 이 산출물을 입력으로 받으므로 순서상 맨 앞이다.
  - 설정 블록의 **키 경로와 값은 §C-7**이 정본이고, 바인딩 형태도 §C-7의 확정 방침이다 — record + `@DefaultValue` + yml 양쪽, 그리고 드리프트 테스트. `FeedbackLlmPropertiesTest`(record 기본값)와 `FeedbackLlmPropertiesIntegrationTest`(기동 컨텍스트의 `Environment` 키 경로) 쌍을 그대로 본뜬다. **이 블록은 시크릿이 아니므로 `@DefaultValue` 예외에 해당하지 않는다.**
  - `PriceMoveDetector`는 **분봉 리스트와 직전 거래일 종가를 받아 이벤트 리스트를 반환하는 순수 함수**다(§C-6). DB·시계·LLM·설정 조회를 안에서 하지 않는다 — 그래야 고정 픽스처로 단정할 수 있다.
  - 수식은 **§탐지 알고리즘(주식)의 의사코드 그대로**다. 장중 후보·병합·채택·시가 갭 모두 그 절이 정본이며 여기에 다시 적지 않는다.
  - **모든 인덱싱은 행 번호가 아니라 시각 기준이다**(같은 절 `[결측]`). 행 기반으로 짜면 결측 구간에서 점수가 조용히 부풀고, 순수 함수라 예외도 나지 않는다.
  - **시가·직전 종가·마지막 분봉을 리터럴 시각으로 찾지 않는다**(§C-2-1). "첫 분봉"·"마지막 분봉" 표현이 그대로 규칙이다 — 리터럴에 의존하면 갭 카드가 **매일 영구히 0건**이 되고 로그조차 남지 않는다.
  - 검증 — 단위(고정 분봉 픽스처) + 설정 드리프트 2종. **완료 조건 탐지 ①~⑤ 5건이 이 항목 소유다.** ③은 중간 분봉을 비운 픽스처로 **행 기반 인덱싱과 결과가 실제로 갈리는지**까지 단정한다(같은 값이 나오는 픽스처를 쓰면 아무것도 검증하지 못한다). ④는 첫 분봉이 개장 정각이 아닌 픽스처다.

- [x] **2. `market` 조회 메서드 4종 신설**

  `feedback`이 서비스 경유로만 쓸 수 있게 `market`에 조회 경로를 연다. **메서드 이름·반환·존재 이유는 §C-6의 표**가 정본이다(현재 재생세션, 서비스 날짜 ↔ 원본 거래일 변환, 하루치 분봉, 직전 거래일 마지막 분봉 close).
  - **`StockReplaySessionScheduler`의 기존 크론·트랜잭션에 손대지 않는다**(FEED-004). 이 항목은 조회만 더한다.
  - **게이트를 우회하는 두 메서드에는 호출 조건을 주석으로 남긴다**(§C-6 마지막 문단) — 배치에서 호출하는 것이 기본이고, 조회 경로에서는 §C-5의 게이트를 통과한 뒤에만 부른다. 판정은 호출부 책임이다.
  - `BusinessDayCalendar.previousBusinessDay`는 **기존 public 메서드**이므로 새로 만들지 않는다(§C-6). 시장 단위 `D-1`을 얻는 유일한 경로이며 종목별 직전 종가 조회로 대체할 수 없다.
  - **이 항목에서 `feedback` 쪽 코드를 건드리지 않는다.** 도메인이 다르고 충돌 주의 대상도 다르다.
  - 검증 — `StockReplayServiceTest`와 같은 레벨. **완료 조건을 직접 소유하지 않지만 배치 ①의 전제다** — `getFullDayCandles`가 **현재 재생 시각과 무관하게** 하루치를 돌려주는 것을 여기서 먼저 단정한다. 기존 `getRevealedCandles`와 같은 픽스처에서 결과가 갈리는지 보면 된다.

- [x] **3. `NewsMatcher` — 이벤트 시각 ↔ 기사 매칭**

  탐지된 구간에 붙일 근거 후보를 고른다. **`NewsMatcher`가 이 이슈 소유**이고 수집 경로(#167)는 건드리지 않는다.
  - 근거창은 **§C-2**다 — 장중 카드와 시가 갭이 서로 다른 범위를 쓴다. 공시 판정은 **§C-3**이며 **공시는 장중 카드에 매칭하지 않는다**(FEED-003, OpenDART가 접수일자만 주므로 분 단위 매칭이 불가능하다).
  - 상한과 절단 규칙은 **§뉴스 매칭 범위**다. 상한 값 자체는 §C-7에 있다.
  - `MarketNewsItemRepository`에 **이 매칭이 요구하는 구간 파인더만** 더한다. 파생 쿼리 이름 대신 `@Query`를 쓰는 이유가 기존 파인더 주석에 있다 — 단일 필드 프로젝션이 컴파일은 통과하고 슬라이스 테스트 전까지 드러나지 않는다.
  - 검증 — 단위(고정 기사 픽스처) + 파인더는 `@DataJpaTest`. **완료 조건 탐지 ⑥을 매처 수준에서 선확인한다** — 근거창 안에 기사가 없으면 빈 결과를 낸다. 카드를 만들지 않는다는 단정 자체는 4번이 확정한다.

- [x] **4. 카드 확정 경로 — 서술·`reveal_time`·저장**

  탐지 결과와 근거를 받아 카드 1건을 확정하고 저장한다. **이 이슈에서 새 행이 생기는 유일한 자리다.**
  - **`NarrativeService` 하나만 주입한다**(§C-6). 카드는 1단계 경로이므로 후검증에 걸리면 템플릿이고 재생성이 없다. `narrative_source`를 §C-4대로 기록한다.
  - **근거가 하나도 없으면 카드를 생성하지 않는다**(FEED-003). 근거 없는 문장은 LLM이 지어낸 것이 된다.
  - `reveal_time` 계산은 **§노출 판정**이 정본이다 — `eventType`별 식과 클램프가 그 절에 있다. **시가 갭 카드의 식에는 `windowEnd`가 들어가지 않는다.**
  - 저장 축과 중복 처리는 **§데이터 모델**과 §실패 처리다 — 유니크 제약으로 무시하고 기존 데이터를 유지한다. `event_type`이 유니크에 들어가야 하는 이유가 §데이터 모델 주석에 있다.
  - 근거 연결은 `price_move_event_sources`에 저장한다. `PriceMoveEventSourceRepository`에 필요한 파인더가 있으면 여기서 더한다.
  - **소유 클래스는 §C-6의 `PriceMoveCardService`다** (2026-08-04 추가 — 카드 확정을 `FeedbackBatchService`에 두지 않는 이유가 같은 절에 있다). 이름을 임의로 바꾸지 않는다.
  - 검증 — 단위 + `@DataJpaTest`. **완료 조건 5건이 이 항목 소유다.** 탐지 ⑥(근거 0건 → 카드 미생성), 탐지 ⑦(`@DataJpaTest`로 장중 첫 후보와 시가 갭 카드가 **같은 날 함께 저장**된다 — 유니크에 `event_type`이 없으면 나중에 삽입되는 쪽이 조용히 사라진다), 노출 게이트 ③④⑤(저장된 `reveal_time` 값이 §노출 판정의 세 규칙과 같다). ③은 첫 분봉이 개장 정각보다 늦은 픽스처에서도 성립해야 한다.

- [x] **5. 개장 전 배치 골격 — 크론·`READY` 확인·생성 순서·스레드 풀**

  하루치를 개장 전에 미리 만드는 경로를 세운다. **`plan.md`의 5·6·7번이 전부 이 골격 위에 얹히므로 여기서 흔들리면 뒤 셋이 함께 흔들린다.**
  - 진입점은 §C-6의 `FeedbackBatchService`이고 크론 키·값·`zone`은 §C-1이다. **기존 재생세션 확정 배치와 같은 크론·같은 트랜잭션에 이어 붙이지 않는다**(FEED-004에 두 가지가 동시에 깨지는 이유가 있다). 시작 시 재생세션이 `READY`인지 먼저 확인하고, 아니면 아무것도 하지 않는다.
  - 분봉·원본 거래일은 **2번이 만든 `market` 메서드로** 가져온다. `getRevealedCandles`를 쓰면 빈 리스트가 와서 **0건이 되고 예외는 안 난다.**
  - **생성 순서는 §C-6의 5단계 그대로 세운다.** 다만 **이 이슈가 채우는 자리는 카드(3·4단계)뿐이고 요약·브리핑(1·2·5단계)의 내용 생성은 `plan.md` 5번 소유다.** 순서를 뒤에 바꾸면 배치 골격을 두 번 만들게 되므로 **골격과 그 순서는 여기서 확정하고 빈 자리를 5번이 채운다.**
  - **LLM 호출 하나가 실패해도 다음으로 넘어간다**(FEED-004·§실패 처리). 배치 전체를 실패시키지 않는다.
  - **같은 서비스 날짜에 두 번 실행돼도 중복 생성되지 않는다** — 유니크 제약 + 존재 시 건너뜀이다.

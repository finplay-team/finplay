# Git 컨벤션 — 브랜치 · 커밋 · PR

브랜치를 만들거나 커밋·PR을 작성할 때 이 문서를 따른다. 코드 작성 규칙은 `docs/conventions/code.md`, 이슈·리뷰 운영 규칙은 `docs/conventions/team.md`에 있다.

## 브랜치 전략 (dev 통합 브랜치 — 2026-07-23 팀 결정, GitHub Flow에서 변경)

- `main`: 시연·심사 시점의 스냅샷 브랜치. **직접 푸시 금지** (보호 규칙) — `dev`에서 PR로만 머지한다.
  - **2026-08-12 정정 (ADR-0021, 이슈 #345).** 그전까지 이 자리는 "배포·시연용 안정 브랜치"였다. CD가 `dev` 머지를 트리거로 삼으면서 **배포되는 것은 `main`이 아니라 `dev`가 됐다.** `main`을 트리거로 두면 배포마다 `dev → main` PR을 사람이 하나 더 만들어야 해서 "머지 이후는 사람이 손대지 않는다"는 결정과 어긋난다(ADR-0021 §결정 1, 대안 (e)).
- `dev`: 통합 브랜치이자 GitHub 기본 브랜치. 모든 기능 PR의 대상. **여기 머지되면 그대로 배포된다** — `dev`에 들어간 것은 즉시 공개 URL에 뜬다.
  - 그래서 **노출 시점을 통제해야 하는 기능은 머지 시점으로 통제한다.** 리뷰어는 "코드가 맞는가"와 함께 "지금 공개돼도 되는가"를 본다.
  - `dev` 대상 PR의 CI(`./gradlew build`)가 공개 URL 앞의 유일한 자동 게이트다 (`ai/specs/010-deployment/spec.md` §CI).
- 작업 브랜치는 항상 최신 `dev`에서 분기한다.
- 문서·하네스 소규모 작업을 포함한 모든 변경은 `dev` 대상 PR로 병합한다. `dev` 직접 커밋은 허용하지 않는다.

## 브랜치 네이밍

```
<타입>/<이슈번호>-<영문-요약>
```

예: `feat/16-price-query`, `fix/79-stock-feed-config`, `docs/17-krx-transition`

- **이슈번호는 0으로 채우지 않는다** — `feat/16-...`이며 `feat/016-...`이 아니다 (2026-07-28 확정).
  - spec 폴더가 `001`~`010` 3자리를 쓰기 때문에 3자리 브랜치는 spec 번호로 오독된다. 실제로 `feat/008-auth-me`(이슈 #8, spec은 002-auth-account)가 spec 008-community로, `feat/010-oauth-callback`(이슈 #10, spec은 002)이 spec 010-deployment로 읽히는 충돌이 있었다.
  - GitHub이 이슈를 `#16`으로 표기하므로 브랜치도 같은 숫자를 쓴다.
- 요약은 소문자 영문 kebab-case로 2~4단어.
- **한국어·개인 이름·날짜를 브랜치명에 넣지 않는다.** 금지 예시 — `namdongyeob/mvp-api-7`, `namdongyeob/리뷰`, `docs/notion-api-spec-sync-20260728`.
- 대응 이슈가 있으면 번호를 반드시 넣는다. 이슈가 없는 작업만 번호를 생략해 `<타입>/<요약>`으로 쓴다.

허용 타입은 커밋 타입과 동일하다.

| 타입 | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `test` | 테스트만 추가·수정 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 빌드·설정·하네스 등 그 외 |

에이전트 워크트리가 만드는 임시 브랜치(`worktree-agent-*` 등)는 PR 대상이 아니며 이 규칙을 적용하지 않는다.

## 커밋 메시지 (Conventional Commits)

```
feat: 회원 가입 API 추가
fix: 주문 조회 시 N+1 문제 수정
```

- 타입은 위 표와 같다.
- 제목은 한국어 50자 이내. 하나의 커밋 = 하나의 논리적 변경.
- 커밋 제목에 이슈 번호를 넣지 않는다 — 이슈 연결은 PR 본문의 `Closes`가 담당한다.
- spec의 `tasks.md`처럼 작업 항목이 나뉘어 있으면 **완료한 작업 항목별로 커밋을 분리한다.** 서로 독립적으로 검토하거나 되돌릴 수 있는 production 코드, 테스트, API 문서·정본 동기화를 한 커밋에 모두 묶지 않는다.
- 한 작업 항목을 완성하기 위해 반드시 함께 바뀌어야 하는 파일은 같은 커밋에 둔다. 예를 들어 controller와 그 요청·응답 DTO, 해당 테스트는 하나의 API 작업 단위가 될 수 있고, controller 변경에 따른 `ai/api-routes.md`·`docs/api/` 동기화도 그 커밋에 포함할 수 있다. 파일마다 기계적으로 쪼개는 것은 요구하지 않는다.
- PR을 올리기 전 `git log --stat origin/dev..HEAD`로 각 커밋이 한 작업 단위를 설명하는지 확인한다. 여러 작업이 섞였다면 push 전 분리하고, 이미 열린 본인 PR이라면 리뷰가 시작되기 전에 이력을 정리해 `--force-with-lease`로 갱신한다.

## PR 제목

```
<타입>: <한국어 요약> (#이슈번호)
```

예: `feat: 종목 현재가 조회 및 공통 가격 계약 구현 (#16)`

- 이슈 참조는 **`(#16)` 한 가지로 통일한다** (2026-07-28 확정). `(Issue #54)`·`(이슈 #79)`처럼 섞어 쓰지 않는다.
- **이슈 제목을 그대로 복사하지 않는다** — `[MVP][인증] 로그아웃 API 구현` 형태 금지. PR 제목은 항상 커밋 타입으로 시작한다.
- 대응 이슈가 없으면 `(#번호)`를 생략한다.

## PR 본문

본문 형식의 정본은 **`.github/PULL_REQUEST_TEMPLATE.md`** 다. GitHub이 PR 생성 시 자동으로 채워 주며, 여기에 별도 템플릿을 복제하지 않는다. CLI로 만들 때(`gh pr create --body-file`)도 그 파일을 기반으로 채운다.

작성 시 반드시 지킬 항목은 다음 둘이다.

- **`Closes #이슈번호`** — 템플릿 "관련 이슈" 절에 채운다. 예외는 둘이다. ① 대응 이슈가 없는 문서·하네스 PR. ② **이슈를 부분적으로만 해결하는 완화 PR** — 이 경우 `Closes`를 걸면 근본 원인 추적이 이슈와 함께 묻히므로, 이슈 번호는 참조만 하고 왜 닫지 않는지를 본문에 적는다 (2026-08-02 PR #127 리뷰).
- **빌드 검증 SHA** — 체크리스트의 해당 칸에 `git rev-parse HEAD` 값을 적는다. `/review-pr`이 이 SHA를 근거로 build 재실행을 건너뛰므로, 비워 두면 리뷰 단계에서 전체 빌드가 다시 돈다. 이후 커밋을 푸시하면 갱신한다.
- 실행하지 않은 테스트를 했다고 적지 않는다 — 실측 결과만 쓴다.

## 머지 조건

- 리뷰 승인 1명 이상.
- **`dev` 머지 버튼이 곧 배포 실행 버튼이다** (2026-08-12, ADR-0021). 머지하면 파이프라인이 이미지 빌드부터 ALB 전환까지 자동으로 수행하며, 그 뒤로 사람이 확인하거나 승인하는 단계가 없다. 배포하고 싶지 않은 변경은 **머지하지 않는 것**이 유일한 통제 수단이다.
- **Merge commit**을 사용한다 — GitHub 머지 버튼의 `Create a merge commit`. PR 안의 커밋이 `dev`에 그대로 남는다.
  - **2026-08-07 정정 (문서를 관행에 맞춤).** 그전까지 이 자리에 "Squash merge를 사용한다"고 적혀 있었으나 팀이 실제로 써 온 방식은 merge commit이다. `dev` 히스토리를 훑으면 PR #229·#240·#241·#249·#251·#253·#256이 전부 `Merge pull request` 커밋으로 들어와 있고, 문서 표기를 따른 PR 세 건(#254·#257·#258)만 한 커밋으로 눌려 있다. 섞여 있으면 히스토리를 읽는 방식이 PR마다 달라지므로 다수 관행 쪽으로 통일한다. 이미 머지된 세 건은 되돌리지 않는다.
  - 커밋이 `dev`에 그대로 남으므로 **커밋을 논리 단위로 나누는 것이 squash일 때보다 중요하다** (커밋 메시지 절 참고).
- PR을 올리기 전 로컬 `./gradlew build` 통과는 작성자 의무다 (CI 자동 검증은 배포 단계에서 도입 — 2026-07-24 튜터 피드백).
- **새 Flyway 마이그레이션을 포함한 PR은 머지 직전에 번호를 재확인한다** (2026-08-16, 이슈 #394). PR 생성 시점에 다음 빈 번호를 확인해도, 리뷰 대기 중 다른 PR이 먼저 머지되면 그 번호가 선점될 수 있다 — `ai/specs/README.md`의 spec 폴더 번호 재확인 관행과 같은 이유다. CI(`ci.yml`)가 "PR의 신규 마이그레이션이 base 브랜치의 최고 번호보다 큰지"를 자동 검사하지만, base가 CI 실행 이후에 또 움직이면(재실행 전까지) 놓칠 수 있으므로 **머지 버튼을 누르기 직전 `git ls-tree origin/dev -- src/main/resources/db/migration`으로 마지막 재확인**을 병행한다. 놓치면 어떻게 되는지는 이슈 #394 참고 — 리뷰·승인을 거친 PR #381이 이 번호 역전(V36이 이미 배포된 V37보다 낮음)만으로 프로덕션 배포를 반복 실패시켰다. **그래도 놓쳤을 때는 배포 워크플로(`deploy.yml`)가 `dev` 푸시 직후 한 번 더 대조해 빌드 전에 멈추고 원인을 이름으로 알려 준다** (2026-08-20, 이슈 #449). 이건 사후 감지라 배포를 되살려 주지는 않는다 — 예방은 여전히 이 재확인의 몫이다.
